Main topic Killer Application
핵심 성과: MUSTARD는 멀티-GPU·멀티노드에 걸친 정적(static) task graph를 실행할 때, host CPU를 그래프 초기화 1회에만 관여시키고 이후의 의존성 추적·데이터 전송·부하분산·커널 스케줄링을 전부 GPU 디바이스 측에서 수행하는 최초의 device-side 멀티노드 실행 모델이다.

기존 CUDA Graph 기반 접근은 프로그래머가 태스크를 수동으로 디바이스에 배정해야 했고(런타임 지식 없이), 그 결과 유휴 GPU가 있어도 특정 GPU에 부하가 몰리는 문제(Figure 1의 Task 7 사례)가 있었다. MUSTARD는 온라인 스케줄링으로 이 문제를 해결하면서도 CUDA Graphs 수준의 저오버헤드를 유지한다.

결과: 64-GPU 멀티노드에서 SLATE 대비 평균 5.83배, 단일노드에서 LU 평균 1.66배 / Cholesky 평균 1.29배 속도향상.
Original Abstract, p.384
Mustard offers a clean solution for executing CUDA graphs across multiple GPUs on multiple nodes without requiring modifications to GPU kernel code or the adoption of new runtime mechanisms or APIs.
Main topic 필요한 이유 (Why It's Needed)
기존 접근들의 한계

1. CPU-managed 런타임 (StarPU, PaRSEC, Legion): work-stealing 등으로 부하분산은 잘 하지만, host가 커널을 launch하고 런타임 컴포넌트를 계속 orchestrate해야 해서 오버헤드가 큼. StarPU는 GPU 전용 실행 대비 최대 13배 느림(§2.1 인용, 실측은 §5.1.2 Fig.5a: 4-GPU에서 16.95x slowdown).
2. CUDA Graphs / hipGraph: launch 오버헤드는 낮지만, 부하분산과 GPU 간 통신 orchestration이 프로그래머 책임이고 단일 노드 내에서만 동작함.
3. Persistent megakernel (Juggler 등): device-side 실행이긴 하나 register pressure·thread divergence·하드웨어 스케줄러 미지원 문제가 있고, 멀티-GPU megakernel 구현은 존재하지 않음.

핵심 스코프 선언: 이 논문은 처음부터 정적 그래프로 범위를 한정한다 — 그래프 구조 자체가 런타임에 바뀌는 동적(dynamic) 그래프는 다루지 않는다.
Original §2, p.385
This work focuses on static task graphs. Although dynamic graphs offer more flexibility by allowing changes in graph structure, most scientific, linear algebra and graph analytics applications can be expressed in form of a static graph.
Main topic 해결책 (Solution)
핵심 기법: Graph Enrichment

> "The idea behind graph enrichment is to incorporate all the functionality required for task graph scheduling into the graph itself." (§3.1.1, p.387)

CUDA Graph의 원래 계산 정점 사이에 런타임 기능을 담당하는 보조 정점을 삽입한다:
- DU (Dependency Update): 원격 디바이스의 의존성 카운터를 NVSHMEM atomic으로 감소
- DW (Dependency Wait): busy-waiting으로 카운터가 0이 될 때까지 대기
- SP (Share Pointer) / RD (Read Data): 디바이스 간 데이터 포인터 공유·읽기
- ⊕/⊖ (Occupancy Increase/Decrease): 디바이스 점유량(스레드/블록 수) 추적

이렇게 하면 런타임 로직이 그래프 구조 자체에 인코딩되어, host 없이 GPU가 자기 그래프를 그대로 실행하는 것만으로 스케줄링·통신·부하분산이 이뤄진다.
Original §3.1.1, p.387
The idea behind graph enrichment is to incorporate all the functionality required for task graph scheduling into the graph itself.
Main topic 결과 (Results)
정량적 근거

A100 GPU 8장 x 노드(최대 8노드=64 GPU), EPYC 7742 듀얼소켓, NVLink 3.0 환경에서:

- 스케줄링 오버헤드: 무연산 랜덤 그래프에서 멀티-GPU CUDA Graph 대비 최대 $50.48\times$ 개선(작은 그래프), 큰 그래프에서도 $1.69\times$
- 단일노드 LU/Cholesky: StarPU·SLATE를 항상 능가, cuSOLVER와 대등하거나 우세
- 멀티노드(최대 64 GPU): SLATE 대비 $2.81$–$8.28\times$, StarPU 대비 $4.75$–$75.2\times$

> "In the multi-node case, MUSTARD reaches performance close to the hardware's theoretical peak even on smaller matrices." (§1, p.385)

Main topic 결론 (Conclusion)
결론: MUSTARD는 host CPU의 개입 없이 부하분산과 통신 관리를 수행하는 최초의 device-side 멀티-GPU/멀티노드 task graph 실행 모델이다. 다만 이 모든 성과는 정적 그래프라는 명시적 스코프 안에서만 성립하며, 저자들도 미래 과제로 AMD ROCm 지원과 더 많은 응용 사례 확장만 언급할 뿐, 동적 그래프 구조로의 확장은 논의하지 않는다.

이는 device-side 실행이 host 제어를 완전히 대체하는 시점이 '그래프 구조가 고정되어 있다'는 조건에 강하게 의존한다는 것을 보여준다.
Original §6, p.395
MUSTARD is designed for executing task graphs on multi-GPU systems, prioritizing load balancing and communication management without relying on host CPU control.

Gap / Idea CUDA Graphs' Single-Node Ceiling
CUDA Graphs의 근본적 한계

> "load balancing and management of inter-GPU communications between multiple devices remains contingent on the programmer's decisions and is only possible within a single node" (§2.2, p.386)

즉 CUDA Graph 자체가:
- 멀티노드를 지원하지 않음
- cudaSetDevice로 정점을 디바이스에 수동 배정해야 함
- 태스크 실행시간을 모른 채 정적으로 배정 $\rightarrow$ suboptimal scheduling (Figure 1의 Task 7 사례)

MUSTARD가 채우는 빈틈은 정확히 이 지점 — 하지만 그래프 구조가 아니라 그래프 위의 스케줄링만 동적으로 만든다.

Method Device-Side Graph Launch & 120-Subgraph Limit
Device-Side Kernel Launch

기존 방법들의 문제:
- Dynamic parallelism: 오버헤드 크고 divide-and-conquer 전용, CUDA 12에서야 재도입
- Persistent kernel / megakernel: 하드웨어 스케줄러 미사용, register pressure 가중

MUSTARD의 해법: device-side CUDA Graph launch — 이미 초기화된 cudaGraph를 실행 중인 GPU 커널(정점)에서 직접 launch.

> "device-side graph launch comes with a limitation, which requires the number of graphs submitted to a device to be no more than 120." (§3.2.2, p.389-390)

120개 미만이면 정점 하나하나가 별도 subgraph가 될 수 있지만, 초과 시 직렬/강결합 정점을 병합해야 하며 이 과정에서 병렬성이 줄어든다(§4 Limitations).
Method GPU-Side Scheduler (Algorithm 2) + NVSHMEM
GPU-Side Scheduler (Algorithm 2, p.391)

```
function SCHEDULER(Queue q, Subgraph[] S, Occupancy[] O, deviceID)
while q.itemsDequeued != S.size:
if !O[deviceID].isBusy():
sID = q.dequeue()
cudaGraphLaunch(S[sID])
```

각 디바이스가 자신의 큐에서 준비된 subgraph를 dequeue해 device-side launch로 실행하는 초경량 스케줄러. 큐는 Broker queue를 NVSHMEM atomic으로 재구현해 멀티-GPU에서도 consistent하게 유지.

멀티노드 통신: 노드 내에서는 cudaMemcpy, 노드 간에는 NVSHMEM을 사용해 GPU가 host 개입 없이 직접 D2D 전송.
Memo Why NVSHMEM Atomics for Cross-Node Deps
설계 결정: 왜 NVSHMEM atomic인가

의존성 카운터 갱신이 여러 컴퓨트 노드에 걸쳐 정확한 순서로 이뤄져야 함. CUDA Cooperative Groups는 커널 내부(단일 디바이스) 동기화만 지원하고, cudaDeviceSynchronize()는 host 측에서만 호출 가능해 device-side 스케줄링과 맞지 않음.

NVSHMEM은 디바이스 코드 안에서 원격 GPU 메모리에 원자적으로 접근할 수 있게 해줘서, host 왕복 없이 멀티노드 의존성 갱신(DU$\rightarrow$DW)을 가능하게 하는 유일한 실용적 선택이었음(§3.1.2, p.388).

Claim Near Theoretical Peak, Host-Free
"Host-free, near-peak" 주장

> "MUSTARD is designed for executing task graphs on multi-GPU systems, prioritizing load balancing and communication management without relying on host CPU control." (§6, p.395)

실험적으로 뒷받침: 멀티노드에서 하드웨어 이론적 peak에 근접(§1, p.385), 작은 행렬에서도 이 효율 유지. 즉 device-side 실행이 오버헤드 관점에서는 host 개입을 거의 완전히 대체했다는 근거.
Gap / Idea Static-Only Scope & No Cross-Node Dynamic Load Balancing
남은 한계: 정적 스코프 + 노드 간 동적 부하분산 불가

> "In MUSTARD, multi-node execution is only possible without dynamic load balancing." (§4, p.391)

- 그래프 구조가 런타임에 바뀌는 동적 그래프는 명시적으로 스코프 밖
- 멀티노드에서는 정적 파티셔닝만 가능 — 노드 간 동적 재배치는 불가
- device-side graph launch 자체가 디바이스당 최대 120 subgraph로 제한

이 세 지점이 이 논문이 스스로 인정한 미해결 영역.
Memo H3 Connection: Software Per-GPU Scheduler vs FPGA Control Plane
H3(GPU당 FPGA 제어 평면 가설)과의 관계

MUSTARD의 멀티-GPU 확장은 이미 "GPU마다 독립적인 스케줄러 커널이 자기 큐를 처리하고, NVSHMEM으로 GPU 간 직접 통신"하는 분산 제어 구조를 소프트웨어로 구현하고 있다 — 이는 H3가 상상한 "GPU당 독립 제어 평면"과 거시적으로 유사.

하지만 결정적 차이: MUSTARD의 제어 루프는 GPU 자신의 SM/스레드 자원을 점유하는 커널인 반면, H3는 GPU 컴퓨팅 자원과 분리된 전용 하드웨어(FPGA)를 제안. 또한 MUSTARD는 그래프 구조가 고정된 정적 그래프만 다루는 반면, H3가 겨냥하는 데이터-의존적 동적 분기(LLM decode의 EOS 판정 등)는 이 논문의 스코프 밖에 명시적으로 남아 있음 — 과장 없이 말하면, MUSTARD는 H3의 경쟁작이 아니라 H3가 아직 비어 있는 지점에 정확히 서 있음을 확인해주는 참고점.
