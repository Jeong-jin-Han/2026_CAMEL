# Root Crash Consistency of SGX-style Integrity Trees in Secure Non-Volatile Memory Systems

> **HPCA 2023** · cluster/reliability · Source: [Root Crash Consistency of SGX-style Integrity Trees in Secure Non-Volatile Memory Systems.pdf](<Root Crash Consistency of SGX-style Integrity Trees in Secure Non-Volatile Memory Systems.pdf>)

저자: Jianming Huang, Yu Hua (corresponding author) — Wuhan National Laboratory for Optoelectronics, School of Computer, Huazhong University of Science and Technology

## TL;DR
Secure NVM 시스템은 counter-mode encryption과 함께 SGX-style Integrity Tree(SIT)로 데이터 무결성을 지키는데, leaf에서 root까지 변경을 전파하는 동안(crash window) 시스템이 죽으면 on-chip root가 NVM의 최신 leaf와 불일치해져 정상 데이터를 공격으로 오탐하는 root crash inconsistency 문제가 생긴다. 이 논문은 SIT의 parent counter가 child 8개 counter의 합이라는 관찰을 이용해, intermediate node를 건드리지 않고 두 개의 on-chip root(Running_root, Recovery_root)만 즉시 갱신하는 ShortCut UpdatE(SCUE)를 제안한다. 동시에 leaf로부터 root를 재구성할 때 발생하는 SIT 특유의 복잡한 parent-child 의존성(BMT와 달리 low-level 노드가 high-level 노드를 필요로 함)을 counter-summing 재구성으로 풀어, 크래시 후에도 leaf만으로 SIT를 복구할 수 있게 한다. Gem5+NVMain 평가에서 SCUE는 insecure baseline 대비 write latency 1.12x, 실행시간 1.07x 오버헤드만으로 root crash consistency와 보안을 모두 제공한다.

## 문제 & 동기
SIT에서 leaf(counter block)가 갱신되면 그 변경이 parent counter/HMAC을 거쳐 root까지 hash로 전파(propagate)돼야 검증 가능한데, 이 전파에는 다단(수십 레벨) 해시 계산이 필요해 상당한 지연(latency)이 든다. 이 전파가 끝나기 전에 crash가 나면 NVM에는 최신 leaf가 반영됐지만 on-chip register의 root는 옛 값 그대로라, 재부팅 후 leaf로부터 재구성한 root와 저장된 root가 달라져 공격이 없어도 복구가 실패한다(p.152-153, 156). 게다가 SIT는 BMT와 달리 한 노드를 만들려면 그 parent 노드(counter 값)가 필요한 low-level→high-level 역방향 의존성을 가져, leaf만으로 tree 전체(특히 root)를 재구성할 수 없다는 두 번째 문제도 있다(p.153, 156).

> [!quote]- 📄 원문 표현 (paper)
> - "One hash computation has to consume 40 cycles [18], [31], [41]. This becomes exacerbated due to the high integrity tree in large NVM, e.g., tens of levels in the integrity tree for the 64GB NVM." (p.152)
> - "If a system failure occurs during the crash window, the propagation process of the modifications aborts. ... the root is inconsistent with the user data upon crashes, i.e., root crash inconsistency." (p.156)
> - "Unlike BMT, as shown in Fig. 4, constructing one tree node in SIT needs its parent node as input, i.e., low-level nodes depend on high-level nodes." (p.156)

## 핵심 통찰 (Key Insight)
1. **Parent counter = child counter들의 합(dummy counter)** — SIT에서 child node의 counter가 1 증가하면 parent counter도 정확히 1 증가하며, 결국 parent counter 값은 child node 내 8개 counter의 합과 같다. 이 산술적 관계를 이용하면 parent node 전체를 읽지 않고도 flush되는 child node의 counter 합("dummy counter")만으로 HMAC 계산과 이후 재구성이 가능해져, intermediate node를 건드릴 필요가 사라진다.
   > [!quote]- 📄 원문 표현 (paper)
   > - "We observe that in one SIT node, increasing the child counter causes the increment of the parent counter. The parent counter hence is the sum of the corresponding child counters." (p.153)
   > - "Dummy counter is generated by summing all counters in the tree node." (Fig.7 caption, p.157)

2. **Running_root와 Recovery_root의 이원화** — 시스템 실행 중 데이터 검증에 쓰는 Running_root와, 크래시 후 복구 시 root crash consistency를 보장하는 Recovery_root를 분리해, leaf가 persist될 때 intermediate node를 읽지 않고도 Recovery_root의 해당 counter만 즉시 +1 하면 crash window가 완전히 제거된다.
   > [!quote]- 📄 원문 표현 (paper)
   > - "SCUE leverages two roots, which actively overlooks most intermediate nodes and only modifies parent node and Recovery_root." (Fig.6 caption, p.156)
   > - "Running_root is used for data security during system running, and the Recovery_root is used for the integrity tree recovery." (p.158)

3. **Lazy computing으로 HMAC 계산을 write critical path에서 제거** — cache 안의 ancestor 노드는 counter만 증가시키고 HMAC은 실제로 NVM에 flush될 때만 계산해, write 시마다 매번 hash를 재계산하지 않는다.
   > [!quote]- 📄 원문 표현 (paper)
   > - "We propose Lazy Computing in SCUE to remove the hash_latency in the propagation path from leaf nodes to root." (p.156)

## 설계 / 메커니즘 (Design)
- **Lazy/Eager 대비 SCUE 갱신 (Fig.6, p.157)**: Lazy 스킴은 persist된 leaf의 parent만 갱신하고 root는 갱신 안 해 root crash inconsistency에 그대로 노출된다(§II-D4). Eager 스킴은 leaf→root 전 경로를 매 write마다 갱신해 안전하지만 오버헤드가 크다. SCUE는 leaf의 parent(검증용)와 Recovery_root만 갱신하고 나머지 intermediate node는 "overlook"한다.
- **Dummy counter 생성 (Fig.7, p.157)**: 하나의 tree node가 cache에서 NVM으로 flush될 때, 그 node 안의 8개 counter를 합산해 dummy counter를 만들고 이를 parent counter로 사용해 HMAC을 계산한다. 즉 flush되는 노드의 실제 parent를 cache에 갖고 있지 않아도 HMAC 계산이 가능해져, write critical path에서 ancestor 노드 read가 사라진다.
- **Write 동작**: leaf node A가 persist될 때 dummy parent counter로 A의 HMAC을 계산하고 동시에 Recovery_root의 해당 counter를 +1 한다. 이후(critical path 밖에서) A의 실제 parent node B를 읽어 dummy counter로 B의 counter를 갱신한다(lazy 스킴과 동일한 sum 갱신 방식). Running_root도 modified child node의 8-counter 합으로 갱신된다(p.157).
- **Counter-summing SIT 재구성 (Fig.8, p.158)**: 크래시 후 leaf부터 bottom-up으로 재구성한다. Level-1 node의 counter는 그 node가 담당하는 8개(정확히는 $8K$~$8K+7$번째) leaf의 dummy counter를 합산해 만들고, 그 counter들과 leaf의 HMAC을 재해시해 검증한다. 같은 방식으로 Level-2, ..., root까지 반복해 SIT 전체(및 Recovery_root)를 leaf에서부터 순수하게 복원한다.
- **공격 탐지 (Table I, p.159)**: roll-forward 공격(counter를 더 큰 값으로 변조)은 leaf HMAC 재계산 불일치로 탐지되고, roll-back 공격(더 작은 값으로 변조)은 재구성된 Recovery_root가 저장된 Recovery_root와 달라져 탐지된다. Roll-forward+roll-back을 동시에 섞어 Recovery_root를 속이려 해도 forward 성분은 HMAC이 여전히 잡아낸다. Replay attack(옛 counter+HMAC 쌍을 통째로 되돌림)은 HMAC 자체는 일치하지만 Recovery_root 재구성 counter가 stored Recovery_root와 어긋나 탐지된다(p.158-159).

> [!quote]- 📄 원문 표현 (paper)
> - "As shown in Fig. 8, we aggregate 8Kth to 8K+7th (K is a natural number) dummy counters to form the Kth Level-1 node." (p.157-158)
> - "In summary, in SCUE, the root is instantaneously updated by increasing the corresponding counter in root by 1 when the leaf node is persisted. Thus, the crash window is completely removed." (p.157)
> - "Rolling back counters in leaf nodes causes the counter in the reconstructed Recovery_root to mismatch the counter in the stored Recovery_root. Therefore, the attacks are detected." (p.159)

## 평가 (Evaluation)
Gem5+NVMain (co-simulator, 8-core x86-64, 16GB PCM NVM, 9-level SIT, 8-ary 64B block, hash latency 기본 40 cycles, 256KB 보안 메타데이터 캐시)로 SPEC2006 8개 매크로벤치마크와 array/btree/hash/queue/rbtree 5개 persistent workload를 평가(Table II, p.159). 비교 대상은 PLP(BMT용 eager 스킴을 SIT에 적용), BMF-ideal(nvMC 무제한 가정), Lazy(root crash 보장 못 함), insecure Baseline이다.

- **Write latency (Fig.9, p.160)**: PLP는 Baseline 대비 평균 2.74x. Lazy/BMF-ideal/SCUE는 각각 Baseline 대비 평균 1.29x/1.21x/1.12x — SCUE가 가장 낮다.
- **실행시간 (Fig.10, p.160)**: PLP는 Baseline 대비 1.96x slowdown, Lazy는 1.17x, BMF-ideal은 1.11x, SCUE는 1.07x slowdown으로 최저.
- **Hash latency 민감도 (Fig.11-12, p.161)**: hash latency를 20→160 cycle로 늘리면 SCUE의 write latency는 평균 1.20x(최대 1.36x) 증가하지만, 실행시간은 hash 계산 횟수를 1회로 줄인 덕에 160 cycle에서도 1.14x 증가에 그친다 — 더 강한(느린) 해시를 써도 성능 저하가 제한적임을 보여준다.
- **복구 시간 (Fig.13, p.161)**: 4MB 메타데이터 캐시 기준 SCUE-STAR(STAR의 bitmap line 활용) 약 0.05s, SCUE-AGIT(Anubis의 shadow table 주소만 활용) 약 0.17s.
- **메모리 접근 수 (p.161-162)**: 9-level SIT에서 PLP는 Lazy 대비 평균 약 7.04x의 메모리 접근을 유발하는 반면, BMF-ideal은 Lazy 대비 약 8.7% 접근을 절감.
- **하드웨어 오버헤드 (p.162)**: SCUE는 64B on-chip non-volatile register 2개(Running_root, Recovery_root, 총 128B)만 필요. 반면 PLP는 PTT(616B)+ETT(48B), BMF-ideal은 16GB NVM 기준 256MB nvMC가 필요.

> [!quote]- 📄 원문 표현 (paper)
> - "On average, the write latency in PLP is 2.74x than that in Baseline. ... the write latencies in the Lazy/BMF-ideal/SCUE scheme are 1.29x/1.21x/1.12x than that in Baseline." (p.160)
> - "PLP leads to a 1.96x slowdown than Baseline on average ... while SCUE produces a 1.07x slowdown." (p.160)
> - "For a 4MB metadata cache, the recovery time is about 0.05s [for SCUE-STAR] ... The recovery time is about 0.17s for a 4MB metadata cache [for SCUE-AGIT]." (p.161)

## 핵심 용어 (Key terms)
- **SGX-style Integrity Tree (SIT)**: 한 노드에 8개 counter와 1개 HMAC을 두어 MT+CME를 결합한 integrity tree. BMT보다 병렬성·보안성이 높고 저장 오버헤드가 낮음.
- **Counter Mode Encryption (CME)**: major/minor counter로 OTP(one-time padding)를 만들어 데이터를 암호화하는 방식. 복호화 지연을 read 지연 뒤에 숨김.
- **Root crash inconsistency (crash window)**: leaf 변경이 root까지 전파되기 전에 발생하는 crash로 인해, 재부팅 후 재구성된 root와 on-chip 저장 root가 불일치해 정상 데이터도 공격으로 오탐되는 문제.
- **Running_root / Recovery_root**: SCUE가 도입한 두 개의 on-chip root. 전자는 실행 중 데이터 검증용, 후자는 크래시 후 root crash consistency 보장/복구용.
- **Dummy counter**: 한 tree node를 구성하는 8개 counter의 합. 실제 parent node를 읽지 않고도 parent counter 역할을 대신해 HMAC 계산과 재구성에 사용.
- **Counter-summing reconstruction**: leaf의 dummy counter를 8개씩 묶어 합산함으로써 Level-1, Level-2, ... root까지 bottom-up으로 SIT를 재구성하는 방법.
- **eADR (Extended ADR)**: 크래시 시 CPU 캐시와 write pending queue까지 NVM으로 flush하는 Intel 기술. root crash inconsistency는 완화하지만 근본적으로 해결하지 못함.
- **PLP (Persist Level Parallelism)**: BMT용 eager 갱신 스킴을 SIT에 적용한 비교 대상. 파이프라인으로 ancestor node를 갱신하나 오버헤드가 큼.
- **BMF(-ideal) (Bonsai Merkle Forest)**: 큰 BMT를 여러 개의 작은 2-level tree로 나눠 root들을 on-chip(또는 이상적으로 무제한 nvMC)에 두는 스킴.
- **Roll-forward / Roll-back / Replay attack**: 각각 counter를 더 크게/더 작게 변조하는 공격과, 예전 (counter, HMAC) 쌍 전체를 되돌리는 공격.

## 강점 · 한계 · 열린 질문
- **강점**: SIT 고유의 parent-counter=child-counter-합이라는 산술적 성질을 정확히 찾아내 root 갱신과 tree 재구성 문제를 동시에 낮은 오버헤드(2개의 64B register)로 해결. eADR로도 못 푸는 문제임을 명확히 논증하고(§III-C), 다양한 baseline(PLP/BMF-ideal/Lazy)과 hash latency 민감도까지 폭넓게 평가.
- **한계**: 평가는 시뮬레이션(Gem5+NVMain) 기반이며 실제 SGX 하드웨어에서의 검증은 없음. 빠른 복구(fast recovery)는 명시적으로 다루지 않고 STAR/Anubis 등 기존 기법에 위임한다고 밝힘(p.161, "we do not consider the fast recovery... orthogonal to our SCUE"). Recovery_root 갱신이 정확히 몇 bit/entry로 최적 구현되는지, 매우 높은 tree fan-out이나 non-8-ary 구성에서도 동일 이득이 유지되는지는 논문 범위 밖.
- **열린 질문**: counter overflow(56-bit counter, NVM lifetime 대비 충분히 큼, p.154)와 SCUE의 상호작용, 그리고 멀티코어/멀티소켓 환경에서 Running_root/Recovery_root 갱신의 동시성 오버헤드는 본문에서 자세히 다루지 않음.

## ❓ Q&A (자가 점검)
> [!question]- SIT는 왜 BMT처럼 leaf에서부터 바로 재구성할 수 없는가?
> BMT는 한 노드가 자신의 child 노드들을 해시해서 만들어지므로 child만으로 재구성 가능하지만, SIT는 한 노드를 만들 때 그 노드의 parent node를 input으로 필요로 하는 반대 방향 의존성(low-level이 high-level에 의존)을 갖기 때문이다(p.156).

> [!question]- SCUE가 crash window를 완전히 없앨 수 있는 핵심 트릭은 무엇인가?
> Leaf가 persist될 때 dummy counter(해당 노드의 8개 counter 합)로 HMAC을 계산하고 동시에 Recovery_root의 대응 counter를 +1 하는 것뿐이며, 이 과정에 intermediate ancestor node를 읽거나 갱신할 필요가 없다(p.157).

> [!question]- Running_root와 Recovery_root의 역할 차이는?
> Running_root는 시스템 구동 중 캐시에 없는 ancestor를 대신해 read 데이터를 검증하는 데 쓰이고, Recovery_root는 크래시 후 SIT를 재구성했을 때 root crash consistency를 보증하는 데 쓰인다(p.158).

> [!question]- Replay attack은 HMAC이 일치하는데 어떻게 탐지되는가?
> Replay는 옛 (counter, HMAC) 쌍을 그대로 되돌리므로 HMAC 검증은 통과하지만, counter 값이 줄어든 것이므로 leaf로부터 재구성한 Recovery_root의 해당 counter가 실제 저장된 Recovery_root 값과 달라져 탐지된다(p.159).

> [!question]- eADR은 왜 root crash inconsistency 문제를 완전히 해결하지 못하는가?
> eADR은 크래시 시 캐시/WPQ 데이터를 NVM으로 flush하는 능력만 제공할 뿐, 크래시 이후 NVM 데이터를 읽고 처리(intermediate node를 읽어 HMAC을 계산)하는 것은 지원하지 않기 때문에 root 자체는 갱신되지 않는다(p.156).

> [!question]- 실험에서 SCUE가 BMF-ideal보다도 나은 이유는 무엇인가?
> BMF-ideal은 이상적으로(nvMC 무제한 가정) intermediate node 전파를 없앤 것이지만 여전히 counter block을 읽고/써야 하는 반면, SCUE는 dummy counter로 단 한 번의 HMAC 계산만 하고 flush되는 노드를 read 없이 처리하므로 write critical path가 더 짧다(p.160-161).

> [!question]- Hash latency를 4배(40→160 cycle)로 늘려도 SCUE 실행시간이 크게 늘지 않는 이유는?
> SCUE는 write마다 필요한 해시 계산 횟수를 1회로 줄였기 때문에, hash latency 자체가 늘어도 전체 write latency/실행시간에 미치는 영향이 제한적이다(p.161, Fig.11-12).
