## 7. 배경지식 — NN training
- **Update는 element-wise**(파라미터마다 독립) → 이게 flatten·CSD 분배·SIMD의 근거
- **Adam**: `m ← β1·m+(1−β1)·g`, `v ← β2·v+(1−β2)·g²`, `θ ← θ−η·m̂/(√v̂+ε)` (momentum=1차, variance=2차 moment)
- **Tensor Parallelism(TP)**: multi-GPU 확장 실험에 사용(§VIII-A)
- 참고: **node_037**(Adam 왜 m·v 둘 다), **node_024**(AXPBY=general averaging), **node_096**(multi-GPU=TP)
- ⚠️ variance = **2nd raw moment** E[g²]이지 진짜 분산 아님

## 7b. 배경지식 — Gradient clipping (Adam 뒤)

**무엇인가**
- gradient가 너무 커서 학습이 폭주(**exploding gradient**)하는 걸 막는 안전장치
- **clip-by-norm**: 벡터 전체를 한 스칼라로 축소해 **L2 norm을 threshold 이하로** — `g ← g·min(1, τ/‖g‖)` → `‖g‖ ≤ τ`
- **방향 보존**(모든 원소 같은 배율), 크기(norm)만 bound
- ⚠️ **합=1 정규화(softmax)가 아님** — "norm(크기)을 제한"하는 것. 원소 크기는 제각각 유지

**왜 쓰나 (Adam이 있는데도)**
- Adam이 원소별로 크기를 O(1)로 정규화하지만 → **transient spike**(나쁜 batch), **학습 초기 v 불안정**, **전역 step 크기**는 못 잡음
- 그래서 대형 LLM(GPT-3·PaLM)은 **global clipping을 안전망으로** 씀 (optional·hyperparameter)
- **NaN/Inf(loss scaling)와 다른 문제**: NaN/Inf = fp16 **overflow**(값이 Inf/NaN) / clipping = **finite지만 너무 큰** gradient

**★ 핵심 = 전역(global) 연산 → Smart-Infinity와 직결**
- clip 하려면 **전체 모델 gradient의 norm**(∑g²)이 필요 → **update 전에 모든 gradient가 다 있어야** 함
- ⇒ gradient offload와 update를 **overlap 못 하는 barrier** 발생 → 그래서 (overlap 대신) **압축(SmartComp)** 으로 우회 (슬라이드 19의 복선!)
- clip scalar c는 GPU가 norm으로 확정 → **update 시 CSD FPGA가 c·g로 적용**(Adam 비선형이라 CSD에서, host 우회)

- 참고: **node_093**(clipping 상세·어디서·norm 누적), **node_005**(overlap barrier), **node_073**(BW·미분 전파)
- 발표 팁: 이 슬라이드가 **슬라이드 19(SmartComp 동기)의 복선** — "clipping이 전역 norm을 요구 → overlap 불가 → 압축 필요"로 이어짐

## 7c. 배경지식 — Mixed precision (gradient clipping 뒤)

**개념**: FW/BW 연산은 **fp16**, weight 갱신 누적은 **fp32** — 섞어서(mixed) 씀

**왜 FW/BW = fp16?**
- **속도**(Tensor Core ~2배) + **메모리 절반**(2 bytes). 연산이 대량이라 fp16이 유리

**왜 update 누적 = fp32? (underflow 관점 — 핵심)**
- weight 갱신 `Δw = η·m̂/(√v̂+ε)` 가 weight보다 훨씬 작음 (**Δw ≪ w**)
- fp16으로 `w += Δw` 하면 작은 Δw가 **반올림돼 사라짐**(swamping/underflow) → 학습 정체
- **fp32 master copy**에 누적하면 작은 갱신도 보존
- optimizer state(momentum·variance)도 값이 작아(특히 v=g²) fp16이면 underflow → **fp32 필수**

**underflow vs overflow (fp16의 두 위험)**
- fp16 = 2 bytes (mantissa 10-bit, exponent 5-bit) → **범위·정밀도 둘 다 좁음**
- **underflow**: 너무 작은 값 → **0** (작은 gradient·weight update 소실)
- **overflow**: 너무 큰 값 → **Inf** (큰 gradient가 fp16 범위 초과)

**loss scaling (underflow 대응책)**
- fp16 backward에서 작은 gradient underflow → **loss에 scale factor S 곱함** → gradient도 S배 커져 fp16 범위 안으로 → update 전 **÷S로 unscale**
- S 너무 크면 overflow → **NaN/Inf 체크 → 그 step skip + S 축소** (dynamic loss scaling)
- ⚠️ "loss scale"은 **배율 S**이지 loss 값이 아님

**★ 메모리 결과 = 6M의 근원 (본론 연결)**
- **fp16 param (M)** + **fp32 optimizer states** (master 2M + momentum 2M + variance 2M = **6M**) + **fp32 gradient (2M)**
- → optimizer state(6M)가 커서 GPU 메모리 부담 → **storage-offload를 하는 이유**. 그리고 gradient도 fp32(2M)라 **압축 대상 = 2M**

- 참고: **node_043**(FP16→FP32 왜), **node_045**(underflow/overflow 예시), **node_042**(gradient=FP32=2M), **node_005**(loss scaling), **node_083**(tier별 상주)
- 발표 팁: 이것도 본론 복선 — "**fp32 = 정밀도(underflow 방지) / 압축 = traffic 감소**"는 **다른 축**(슬라이드 20에서 강조). fp32 6M이 커서 offload, 그게 이 논문의 출발점

## 9. 배경지식 — Interconnect (PCIe / AXI) + 대역폭

**① PCIe (system interconnect) — 병목의 무대**
- host ↔ device를 잇는 **공유 버스**. 모든 device(GPU·SSD·CSD)가 이 링크를 나눠 씀 → **여기가 병목**
- SmartSSD = **PCIe Gen3 x4**
- **공유 uplink 대역폭 ≈ 16 GB/s (고정)** — device를 아무리 늘려도 이 천장은 안 커짐 (§II, Fig)
- 단일 경로(1 GPU/1 device) 실효 ≈ **10~12 GB/s** (ZeRO-Infinity)
- 단일 SSD host-facing 대역폭 = **a few GB/s (~4 GB/s)** → RAID0로 4개면 4×4=16으로 **PCIe 포화**(Fig 3b)

**② CSD 내부 대역폭 — Smart-Infinity의 핵심 무기**
- CSD는 **내부 PCIe switch**를 가져 **SSD ↔ FPGA를 직접(P2P)** 연결 → **공유 PCIe를 안 거침**(host 우회)
- 내부 대역폭 ≈ **8 GB/s per CSD**, 여러 개면 **aggregate = 8 × (#CSD) GB/s** → **CSD 수에 선형 증가** (§II, Fig)
- 대비: **공유 PCIe 16 GB/s는 고정 / 내부는 8×N** → CSD가 많아지면 내부 대역폭이 공유 PCIe를 **훨씬 초과**
  - (예: 10 CSD면 내부 80 GB/s ≫ PCIe 16 GB/s)
- ⚠️ **단일 CSD는 boost 없음**(내부 8 < PCIe 16) — 여러 CSD를 합쳐야 이김. 이게 "여러 CSD" 설계의 이유
- → Smart-Infinity가 *"aggregated internal CSD bandwidth instead of limited system interconnect"* 를 쓰는 근거

**②-b PCIe switch (CSD 내부 P2P를 가능케 하는 부품)**
- **PCIe용 라우터**: upstream 포트(→host) 1개 + downstream 포트(→SSD·FPGA) 여러 개
- **P2P**: downstream 두 장치(SSD↔FPGA)가 **switch 내부로 직접** 통신 → **upstream(host) 링크를 안 씀**
- ⇒ SSD↔FPGA 전송이 **공유 host PCIe를 소비 안 함** → 각 CSD 내부 전송이 서로 독립 → **aggregate 선형↑**
- ⚠️ **Gen3(속도)와 무관**: switch는 **경로(라우팅)**, Gen3은 **속도(세대)** — 별개 개념
- SmartUpdate의 "**6M optimizer state가 host로 안 감**"의 물리적 근거 = 이 내부 switch P2P (§II-B)

**③ AXI (FPGA on-chip 버스)**
- Advanced eXtensible Interface(ARM AMBA). **FPGA 칩 내부** IP 블록 연결 — Fig 7의 **DRAM(accelerator memory) ↔ updater/decompressor**
- on-chip이라 **매우 고대역·저지연**(고정 GB/s 수치는 논문 언급 없음). PCIe(칩 밖)와 층위가 다름

**④ 메모리 계층 대역폭 감 (한눈에)**
- GPU HBM **~TB/s** ≫ CPU DRAM **~100 GB/s** ≫ **공유 PCIe uplink ~16 GB/s(고정)** ≫ 단일 NVMe SSD **~4 GB/s(Gen3 x4)**
- **CSD 내부(SSD↔FPGA P2P) = 8×N GB/s(선형↑)** — N이 크면 공유 PCIe(16)를 **넘어섬** ← Smart-Inf가 여기로 우회
- ⚠️ 주의: ZeRO-Infinity의 "NVMe ~25 GB/s"는 DGX-2의 **여러 NVMe aggregate**(단일 SSD 아님). **이 논문 단일 SmartSSD = ~4 GB/s**. NVMe는 프로토콜이라 속도값이 아니고, 실제는 **PCIe 세대(Gen3 x4=4)+NAND**가 결정
- 즉 **storage(단일 SSD ~4)가 병목** → Smart-Inf는 **공유 PCIe(16, 고정) 대신 CSD 내부(8×N, 선형↑)** 를 씀

- 참고: **node_094**(AXI·주소공간·control/data plane), **node_039**(NVMe vs PCIe), **node_070**(대역폭 완전 분해), **node_017**(aggregate 내부 대역폭), **node_040**(RAID0 4개 포화 = 16÷4)
- ⚠️ 핵심 대비 한 줄: **"공유 PCIe = 16 GB/s 고정(N 무관) vs CSD 내부 = 8×N GB/s(선형↑)"** — 이게 Fig 3b 포화를 넘는 방법

## 10. 배경지식 — FPGA
- **CPU와의 차이**: CPU=명령어 fetch/decode(temporal 순차) / FPGA=**bitstream으로 회로가 됨**(spatial 병렬, 명령어 없음). "누가 명령?" → **런타임 명령 아님**, 회로 설계를 미리 구움 + CPU가 coarse launch만
- **SIMD**: PE당 **16 AXPBY** 병렬
- **FPGA DRAM(DDR4 4GB)** = device 주소공간(BAR/DMA/P2P로 접근) ↔ **host DRAM**(OS+MMU) — 분리·비coherent
- **BRAM** = on-chip scratchpad(chunk S) — cache 아님(명시 관리)
- 참고: **node_094**(CPU vs FPGA·주소공간·회로), **node_050**(가속기=연산+메모리, MMU/cache 없음), **node_078**(BRAM≠DRAM)

## 10b. 배경지식 — DeepSpeed

**DeepSpeed = 이 논문이 쓰는 학습 프레임워크 (라이브러리)**
- Microsoft의 대규모 딥러닝 학습 라이브러리, **PyTorch 위**에서 동작 (§VI [24])
- 제한된 자원으로 **큰 모델을 학습**하게 해주는 최적화 모음 (메모리 절약·offload)
- 핵심 = **ZeRO**(모델 상태 메모리 중복 제거) + **offload**(optimizer state를 CPU/NVMe로)

**FW/BW를 하는 단위 = block (= layer)**
- layer(submodule) param을 필요할 때 **모아서(allgather) 계산 → 곧 버림(release)**
- 큰 layer는 **memory-centric tiling**으로 tile로 쪼갬 → 임의 크기 layer 처리 가능

**DeepSpeed가 제공하는 mixed-precision 학습 기능** (앞 7c와 연결)
- **mixed precision**: FW/BW = fp16, 누적 = fp32
- **loss scaling**: 작은 gradient underflow 방지 (loss ×S → BW → ÷S), **매 iteration**
- **NaN/Inf skip**: overflow면 그 step **skip + scale 축소** (dynamic loss scaling)
- **gradient clipping**: 전역 norm으로 폭주 방지
- **autocast**: softmax 등 불안정 op만 fp32

**offload 계열** (선행연구, 슬라이드 12~14에서 상세)
- **ZeRO-Offload**: optimizer state → CPU / **ZeRO-Infinity**: → CPU+NVMe

- 참고: **node_078**(용어), **node_005**(loss scaling·NaN/Inf), **node_056**(ZeRO 계보), **node_079**(ZeRO-Inf 분할)
- 발표 팁: 여기선 **"DeepSpeed가 뭘 해주는지"만** 배경으로 깔기 — **FW/BW=layer 단위 + mixed precision(loss scaling·NaN/Inf·clipping)** 이 본론에서 쓰일 재료. (*Smart-Inf가 무엇을 바꿨는지*는 본론에서)

## 11. ML training (GPU 단독)
- FW: `Act = f(Param, X)` (X=배치 데이터, 이후 층은 직전 Act)
- BW: chain rule로 Param+Act → **Grad**
- Update: Grad로 optimizer state·param 갱신
- 참고: **node_073**(FW/BW dataflow·chain rule)

## 12. ML training (ZeRO-Offload)
- **Param·Act·FW/BW = GPU** / **optimizer states(6M)·grad = CPU host, update도 CPU**(built on ZeRO-2)
- per-step 이동 = Grad(GPU→CPU)+새 Param(CPU→GPU). **6M은 CPU에 붙박이(안 건넘)**
- **한계**: param이 GPU에 다 있어야 → 모델 ≤ 단일 GPU 용량
- 참고: **node_074**(왜 CPU update·ZeRO-Offload 배치·그림 검증)
- ⚠️ ZeRO-Offload는 Param·Act가 **GPU**(host 아님) — ZeRO-Infinity와 헷갈리지 말 것

## 13. ML training (ZeRO-Infinity)
- built on **ZeRO-3** + offload engine(CPU/NVMe). **host = fp16 Param+Act**, **optimizer states = NVMe(SSD)**
- param을 layer 단위로 GPU에 stream, 거대 layer는 **memory-centric tiling**, **bandwidth-centric partitioning**(allgather, PCIe 병렬 BW∝dp)
- 참고: **node_079**(분할 방식), **node_084**(가정 사다리), **node_056**(계보)

## 14. 선행 연구 요약 — 가정 사다리
- **ZeRO-Offload**(DRAM에 6M 다 담김, CPU update) → 용량 초과 → **ZeRO-Infinity**(NVMe로) → **Smart-Infinity**(NVMe에 두되 update까지 CSD 안에서)
- 시뮬레이터(GradPIM·OptimStore)와 달리 **상용 실물**
- 참고: **node_084**(사다리), **node_058**(선행 비교표), **node_034**(시뮬 대비)

## 15. ZeRO-Infinity 문제점 (동기)
- storage-offload는 매 iteration **(6+2)M을 공유 PCIe로 왕복** → 학습시간 **>80%가 전송**(Fig 3a)
- **RAID0로 SSD 늘려도 4개 넘으면 speedup 포화**(Fig 3b) — **공유 PCIe가 천장**(~2.3×). 천장 ≈ PCIe BW ÷ 1-SSD BW
- 참고: **node_013**(Fig 3a >80%), **node_014**/**node_040**(RAID0 포화), **node_091**(Fig 3 읽기), **node_011**(88% 전송)
- **전개**: ①데이터 이동 없애기(SSD→host 안 함) ②SSD 안에서 update ③CSD 늘면 내부 BW 합산으로 선형↑

## 16. Smart Infinity — SmartUpdate
- **update 연산을 CSD 내부 FPGA로 이동** → optimizer state(6M)가 **PCIe를 안 건넘**(내부 P2P). (6+2)M→**2M**
- **flatten**: 파라미터를 shape·layer 무시하고 1D로 편 뒤 **CSD에 균등분배**(element-wise라 가능, **architecture-agnostic**)
- **쪼개고 분배하는 주체 = host CPU 소프트웨어**(DeepSpeed 통합); update 연산 = owner CSD FPGA
- 참고: **node_003**(SmartUpdate), **node_022**(flatten→분배→P2P update), **node_081**(flatten 정의, ≠TP), **node_080**/**node_087**(누가 쪼개나=host CPU)
- ⚠️ flatten ≠ TP: TP는 coupled matmul(통신 필요), flatten은 element-wise(통신 0)

## 17. Smart Infinity — Internal data transfer (동기)
- SmartUpdate 후 **SSD↔FPGA DRAM 내부 이동**을 어떻게 겹칠까?
- subgroup을 **tasklet**으로 처리 — naive는 순차(느림) 또는 overlap시 **device OOM**
- 참고: **node_004**(handler), **node_062**(tasklet·Fig 5), **node_059**(왜 OOM)

## 18. Internal data transfer — 해법
- **2 thread(CPU)**로 buffer 관리: Param을 **우선 writeback**(GPU가 다음 FW/BW에 필요), momentum·variance는 **지연 writeback**
- **최대 subgroup 크기로 buffer 사전할당 → 재사용**(재할당 회피) + swap overlap → OOM 없이 겹침
- 참고: **node_018**(2-thread·지연 writeback), **node_019**(3가지 이득)

## 19. Smart Infinity — Gradient compression (동기)
- SmartUpdate가 6M 없앴지만 **gradient(2M)는 여전히 공유 PCIe** → CSD 늘수록 **새 병목**
- **overlap(offload∥update)으로 숨기고 싶지만 불가**: ①**NaN/Inf 체크**(loss scaling) ②**gradient clipping**(전체 gradient의 **global norm** 필요) → 둘 다 update 전 **전체 gradient** 요구 + SSD write BW < read
- ⇒ 못 숨기니 **트래픽 자체를 줄인다 = 압축**
- 참고: **node_005**(overlap 왜 안 되나·NaN/Inf·clipping), **node_093**(clipping)
- ⚠️ 압축은 두 이유를 "해결"하는 게 아니라 **다른 축(줄이기)으로 우회**. barrier는 그대로

## 20. Gradient compression — 방법
- **GPU에서 magnitude 기반 Top-K**: block별로 sort → 상위 **1%** 선택 → **(value list, index list)** 로 offload
- 크기 = **2% × 2M** (top 1%인데 index+value 쌍이라 ×2)
- 참고: **node_020**(Top-K), **node_092**(GPU 압축 위치·왜 GPU sort·block별), **node_089**(왜 gradient 오차에 관대 — sparsity+error compensation)
- ⚠️ 압축은 gradient만(error-tolerant), param은 안 함(모델 상태라 lossless 필수)

## 21. Gradient decompression
- FPGA가 (value,index)를 받아 **0으로 채운 D 벡터에 val[j]를 idx[j] 위치로 scatter** → 원래 길이 복원(나머지 0)
- **산술 없는 addressing**(index가 곧 주소) → lightweight FPGA에 적합
- decompress 목적 = **element-wise Adam이 full length를 요구**해서(clipping 아님!)
- 참고: **node_025**(scatter), **node_007**(Fig 7 decompressor)
- ⚠️ decompress는 rescale 아님(순수 scatter), clipping도 아님(shape 복원)

## 22. 논문 표현 정리 — M
- **M = FP16 파라미터 크기**(2 bytes×P). fp16 param=M, fp32 각 텐서=2M
- optimizer states = master(2M)+momentum(2M)+variance(2M) = **6M**, fp32 gradient = **2M**
- 참고: **node_083**(단위·tier 상주), **node_036**/**node_042**(6M 유도)

## 23. 기호 (D, S, layer)
- **D = subgroup(tasklet) 크기** = FPGA DRAM(4GB)에 맞춤. subgroup i = 인덱스 `[i·D, (i+1)·D−1]`
- **S = chunk 크기** = BRAM에 맞춤(FPGA 연산 단위)
- **FW/BW block = layer(submodule)** 단위(DeepSpeed/ZeRO-Inf 소관) / **update subgroup = flat, layer 무관**
- 참고: **node_078**(glossary), **node_086**(block vs subgroup), **node_007**(D/S)
- ⚠️ FW/BW block만 layer, update chunk는 "메모리에 맞는 flat 크기"(§II가 "block e.g. layers"로 느슨히 써서 헷갈림)

## 24. Smart Infinity — 가정
- **host DRAM 상주**: fp16 Param(M) + Activation, per-iteration으로 Data X
- **SSD 상주**: fp32 optimizer states(6M) — iteration 간 지속
- **Grad(2M)**: BW에서 생성 → SSD offload(host DRAM에선 해제) → update서 소비(transient)
- 참고: **node_083**(tier별 상주·Grad 생애주기)
- ⚠️ "Grad만 존재"는 부정확 — optimizer states(6M)도 상시 존재(SSD). Param은 host, X·Act·Grad는 per-iteration

## 25. ML training (Smart Infinity) — FW
- FW/BW는 **layer block 단위**, DeepSpeed 기반, 거대 layer는 **memory-centric tiling**(지금은 한 layer가 GPU에 들어간다고 가정)
- `X, Param1 → FW → Act1` / `Act1, Param2 → FW → Act2` … (입력 X는 그림에서 생략 — 작고 전송 병목 아님)
- 참고: **node_073**(dataflow·X 생략 이유), **node_086**(tiling), **node_079**

## 26. ML training (Smart Infinity) — BW
- BW: Param+Act → chain rule → Grad (뒤 layer부터 앞으로)
- Grad는 block별 생성 → 즉시 SSD로 offload
- 참고: **node_073**

## 27. ML training (Smart Infinity) — Update
- owner CSD FPGA가 optimizer state+grad로 element-wise Adam → param 갱신
- 참고: **node_007**(updater), **node_003**

## 28. 가속기 (compress 통합) — index/store
- decompressor: **index list에 이미 주소가 있어 PE가 주소 연산 불필요**, 해당 주소에 **store(scatter)** 만
- size대로 복원된 grad는 **SSD로 안 돌아가고 바로 param update에 사용**
- 참고: **node_007**(scatter·why no PE), **node_025**

## 29. 가속기 — S 압축·update·writeback
- S 덩어리 압축(복원) 끝나면 **momentum·variance update**(AXPBY) → 그걸로 **param update**(Update 블록: √v̂·역수·뺄셈, 비선형이라 별도 블록)
- 갱신된 optimizer state·param은 **DRAM 저장 → SSD writeback**(단계 ⑤⑥, memory write지 연산자 아님)
- 참고: **node_007**(Fig 7 dataflow·AXPBY·Update 블록·store ⑤⑥)
- ⚠️ 방향: **g가 m·v를 갱신 → m·v가 param을 갱신** (논문 "optimizer states applied to gradients"는 AXPBY 하드웨어 표현, loose)

## 30. 가속기 — Internal P2P handler
- **Internal P2P Handler(§IV-B)** = SSD↔FPGA DRAM 전송 관리(CPU 2 thread) = **control plane**. 데이터는 SSD↔FPGA **직접**(내부 PCIe switch) = data plane
- 참고: **node_094**(control/data plane), **node_004**

## 31. Grad/Param 나누는 주체
- **flatten·균등분배·owner CSD 라우팅 = host CPU 소프트웨어**(DeepSpeed gradient offloading path 수정). update 연산만 CSD FPGA
- 참고: **node_087**(누가 flatten=host CPU), **node_094**(D: gradient 쪼개기=host)

## 32–35. Grad block 나누는 과정 (BW 후)
- BW가 block별 Grad 생성 → GPU에서 **압축 전 full gradient로 clip norm(∑g²) 누적** + NaN/Inf 체크(host/GPU 전역) → **top-K 압축** → **owner CSD로 라우팅**(flatten ownership, block이 CSD 경계 가로지르면 쪼개짐)
- clip scalar c는 GPU가 확정 → **update 시 CSD가 c·g 곱해 적용**(Adam 비선형이라 CSD updater가, host 우회)
- 참고: **node_093**(clip 어디서·streaming norm·block offload인데 어떻게 적용), **node_066**(P2P는 SSD↔FPGA leg만), **node_022**
- ⚠️ full gradient는 **norm(스칼라)에만** 쓰고 GPU에서 소비/압축 — update는 top-k. "clipping엔 full 필요 vs update는 top-k"는 모순 아님(단계 다름)

## 40. Discussion (내 분석)
- **[강]** DRAM 충분하면 offloading 불필요 → **큰 모델은 용량 초과라 SSD 강제**가 전제 (**node_085**)
- **[강]** Single GPU면 LoRA가 대안일 수 있음 (**node_060/061**)
- **[중]** overlap 불가의 **결정적 원인은 NaN/Inf가 아니라 clipping**(NaN/Inf는 GPU서 0처리로 우회 가능해도 clipping의 global norm은 못 우회) (**node_093/005**)
- **[중]** 갱신 param을 fp16으로 down-cast해 보내면 upstream 2M→M로 절반인데 논문은 fp32(2M) 그대로 (**node_046**)
- **[경]** "accelerator-assisted compression"이라 하지만 **압축은 GPU**, accelerator는 decompress (**node_088**)
- **[경]** overlap 설명하며 "clipping 때문에 gradient 다 모아야"라 해놓고, 정작 이 논문 스킴에선 clipping 적용 세부를 안 보임(모으기만) (**node_093**)

## 41. 추가 아이디어 (내 연구 접점)
- 지금은 **CSD → host mem → GPU**로 param을 읽어옴. **Direct-GPU/CXL로 CPU 개입 없이** 읽으면?
