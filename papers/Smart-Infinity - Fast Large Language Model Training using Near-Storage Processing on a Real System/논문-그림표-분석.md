## A. 배경·문제 (동기)

### ★ Fig 1 — storage-offloaded LLM training 개념도 (FW/BW/Update)
- **무엇**: 배경인 storage-offload 학습의 (a)FW (b)BW (c)Update 3단계. 무엇이 host↔SSD로 오가나
- **핵심**: update 단계에서 **(6+2)M이 공유 PCIe를 왕복** → 병목의 무대
- **활용**: 배경 슬라이드. (입력 데이터 X·layer chaining은 생략됨 — node_073)
- 관련: **node_073, node_083, node_012**

### ▽ Fig 2 — CSD 환경 (SmartSSD topology)
- **무엇**: 여러 CSD가 PCIe switch로 연결된 시스템. 내부 SSD↔FPGA P2P
- **핵심**: **내부 대역폭은 CSD 수에 선형↑, 공유 PCIe는 고정**
- **활용**: 배경(PCIe switch·P2P) 설명 시 1장. 아니면 생략
- 관련: **node_065, node_094**

### ★ Fig 3 — (a) 시간 breakdown (b) RAID0 포화 ← **동기의 핵심**
- **무엇**: (a) 모델 크기별 학습시간 분해 → **update+전송이 80%+** / (b) RAID0로 SSD 늘려도 **4개에서 speedup 포화**
- **핵심**: **전송이 병목 + RAID0로는 공유 PCIe 천장(~2.3×)을 못 넘음** → near-storage 필요
- **활용**: 동기 슬라이드 **필수**. "왜 이 논문이 필요한가"의 답
- 관련: **node_013, node_014, node_040, node_091**

### Table I — interconnect traffic 변화 ((6+2)M → 2M → c%×2M)
- **무엇**: Smart-Infinity 적용 시 공유 링크 통과 트래픽 요약
- **핵심**: **SmartUpdate가 (6+2)M→2M, SmartComp가 2M→c%×2M** — 논문 전체를 한 표로
- **활용**: 방법 요약으로 강력. 본편에 넣으면 흐름 명확
- 관련: **node_016, node_042**

## B. 방법 설명 (SmartUpdate / handler / SmartComp / 가속기)

### ★ Fig 4 — Update procedure (baseline vs SmartUpdate)
- **무엇**: baseline(6M optimizer가 host로 왕복) vs SmartUpdate(CSD 내부 P2P로 update, 2M만 공유 링크)
- **핵심**: **update 연산을 CSD로 옮겨 6M을 공유 PCIe에서 제거**
- **활용**: SmartUpdate 설명 **필수**
- 관련: **node_003, node_065, node_066**

### ★ Fig 5 — (a) Naive vs (b) Internal data transfer handler
- **무엇**: (a) tasklet 순차 실행 / (b) 2-thread + 사전할당 buffer로 param 우선 writeback·overlap
- **핵심**: **param 우선 writeback + m·v 지연 → 전송·compute overlap (OOM 없이)**
- **활용**: handler(O) 설명. 그림은 복잡하니 **핵심(param 우선·overlap)만** 짚기
- 관련: **node_004, node_018, node_062, node_059**

### ★ Fig 6 — SmartComp overview
- **무엇**: (a) GPU가 gradient 압축(top-k) → (b) CSD FPGA가 decompress 후 update
- **핵심**: **압축은 GPU / 복원은 FPGA. 공유 링크 트래픽 2M→c%×2M**
- **활용**: SmartComp 설명 **필수**
- 관련: **node_005, node_020, node_092, node_025**

### ★ Fig 7 — Microarchitecture (Updater + Decompressor)
- **무엇**: Updater PE(16 AXPBY, Mmt·Grad·Var·Param buffer) + Top-K Decompressor(scatter)
- **핵심**: **AXPBY로 Adam(선형) + Update 블록(비선형) / decompressor는 산술 없는 scatter**
- **활용**: 가속기 구조 슬라이드. AXPBY·scatter 중심으로
- 관련: **node_007, node_024, node_025**

### ▽ Fig 8 — Framework overview (User/Middleware/Hardware)
- **무엇**: HLS 템플릿(user) + DeepSpeed 연동(middleware) + FPGA(hardware) 구성
- **핵심**: **DeepSpeed drop-in + HLS로 커스텀 optimizer 지원** (feasibility·실용성)
- **활용**: 구현 슬라이드 1장 또는 backup. "off-the-shelf·drop-in" 강조용
- 관련: **node_008, node_026**

## C. 결과 (실험)

### ★ Fig 9 — Training time breakdown + speedup (BASE·SU·SU+O·SU+O+C) ← **핵심 ablation**
- **무엇**: **(a) GPT-2 + (b) BERT** 두 모델, 각 여러 크기(GPT-2 최대 8.4B)에서 각 기법(SU/O/C)을 쌓으며 시간 분해 + speedup
- **핵심**: **SU→SU+O→SU+O+C로 기여 분해**, update+전송(회색)이 단계마다 급감. 최대 **1.85~1.98×**(10 SSD). **범위인 이유 = GPT-2·BERT·여러 크기 전체에 걸친 값** (§VII-C line 1741 "for all models tested, trend almost identical")
- **활용**: **결과 슬라이드 필수.** "각 기법이 얼마나 기여하나 + 모델 무관"
- 관련: **node_095, node_027** — §VII-C

### ★ Fig 10 — Scalability (16.6~33B 대형 모델)
- **무엇**: 큰 모델에서 BASE·SU+O·SU+O+C 시간·speedup
- **핵심**: **모델 커져도 speedup 유지(consistent/stable, ↑ 아님)** — 통신량이 파라미터 수에 비례해 통신 비중 유지되기 때문. baseline은 대형서 upload/offload로 더 악화. 33.0B서 1.37×(6SSD)/1.88×(10SSD). **CSD 많을수록는 별개로 이득↑**(Fig 11a)
- **활용**: **결과 필수** (Fig 9와 묶어도 됨). "대형서도 이득 안 사라짐"
- **주의**: "모델 클수록 이득↑"은 과장 — 논문은 "stable/consistent". 이득↑인 축은 **CSD 수(Fig 11a)·GPU 등급(Fig 11b, A100>A5000)**
- 관련: **node_095** — §VII-D

### ▽ Fig 11 — (a) #SSD 확장성 (A5000 vs A100) (b) 10-SSD breakdown
- **무엇**: GPU tier별(중급 A5000·고급 A100) CSD 1→10 확장, 고급 GPU에서 speedup 더 큼
- **핵심**: **다른 GPU에서도 성립 + 고급 GPU일수록 이득↑**(GPU 빠르면 전송 병목 비중↑)
- **활용**: backup 또는 "GPU 무관하게 성립" 한 줄
- 관련: **node_027, node_030**

### ▽ Fig 12 — 다른 optimizer (SGD·AdamW 등)
- **무엇**: SmartUpdate를 Adam 외 optimizer에 적용
- **핵심**: **AXPBY 기반이라 다양한 optimizer 범용** (moving average 꼴이면 됨)
- **활용**: backup 또는 "일반성" 한 줄
- 관련: **node_024, node_031**

### ▽ Fig 13 — 다른 모델 (BLOOM·ViT)
- **무엇**: decoder(BLOOM)·vision(ViT)에도 적용
- **핵심**: **모델 종류 무관** (flatten이 architecture-agnostic이라)
- **활용**: backup 또는 "다른 모델도" 한 줄
- 관련: **node_022, node_031**

### ▽ Fig 14 — 모듈 throughput vs NVMe read/write
- **무엇**: updater/decompressor 처리량 vs SSD read·write 대역폭
- **핵심**: **updater가 SSD보다 빠름(>7GB/s) → 가속기가 병목 아님** (SSD·전송이 병목)
- **활용**: backup. "FPGA가 느려서 문제되지 않음"의 근거
- 관련: **node_030**

### ▽ Fig 15 — Performance/$ (GFLOPS/$)
- **무엇**: baseline vs Smart-Infinity의 비용당 성능 (서버 ~$45,000 + storage 등)
- **핵심**: **상용 CSD로 비용 효율(GFLOPS/$) 개선** = feasibility·경제성
- **활용**: backup 또는 "비용 효율" 한 줄 (Cost 렌즈)
- 관련: **node_030**

### ▽ Fig 16 — 압축비 sensitivity (Top-K %)
- **무엇**: 압축비(10%→1%) 변화에 따른 학습시간
- **핵심**: **더 압축할수록 빨라지고, 정확도는 크게 안 상함** (2%=default가 균형)
- **활용**: backup. 압축비 tradeoff 질문 대비
- 관련: **node_089, node_092**

### ★ Fig 17 — Multi-GPU congested topology (TP)
- **무엇**: (a) GPU·storage가 같은 PCIe expansion 공유하는 congested topology / (b) 1~3 A4000 GPU, TP speedup
- **핵심**: **multi-GPU(TP)로도 확장, 제한된 PCIe에서도 1.66~1.86×**
- **활용**: multi-GPU 슬라이드 (짧게). "single 넘어 확장됨"
- 관련: **node_096**
