Main topic Killer Application
SSD 내부 하드웨어 원가를 31.50% 깎으면서, 성능은 오히려 5.02% 더 높인다. 그것도 응용 프로그램 수정 없이, 기존 블록 인터페이스(block interface) SSD 그대로.

XHarvest가 푸는 것은 하나의 딜레마다. 고성능 SSD는 I/O 폭주(I/O burst) 를 견디려고 값비싼 연산 자원(computation)과 DRAM을 잔뜩 집적하지만, 그 폭주는 어쩌다 한 번 온다. Alibaba 4,000대 서버의 8일 트레이스에서 I/O 대역폭 사용률이 25% 미만인 시간이 전체 runtime의 96.64% 다. 즉 SSD 안의 가장 비싼 자원이 대부분의 시간 동안 놀고 있다. 이것이 논문이 말하는 cost-utilization dilemma다.

세 축이 동시에 성립해야 remarkable하다:

① 비용(cost) — 내부 연산 자원은 conventional SSD 대비 25%만, 내부 DRAM은 FTL 매핑 테이블의 10%만 수용할 만큼만 남기고 나머지를 제거. 1TB SSD 기준 하드웨어 원가 31.50% 절감.

② 성능(performance) — 모자란 몫은 I/O burst가 왔을 때만 호스트 CPU/메모리를 동적으로 수확(dynamic resource harvesting) 해서 메운다. macrobenchmark에서 ConvSSD 대비 대역폭 +5.02%, 50th latency -37.84%.

③ 보안(security) — 호스트에서 도는 펌웨어(firmware)를 TEE(Intel SGX enclave) 안에 가둬 벤더의 독점 알고리즘 유출을 막고, CXL 3.1의 TSP(TEE Security Protocol) 로 enclave-SSD 사이 트래픽까지 암호화한다.

선배 격인 OCSSD(Open-Channel SSD) 는 ①만 달성하고 ②③에서 무너져 Linux 5.15에서 LightNVM/pblk가 제거됐다. XHarvest의 핵심 주장은 "세 축을 동시에 잡는 방법이 이제야 존재한다"는 것이고, 그것을 가능하게 한 재료가 CXL(cache-coherent 통합 메모리) 와 TEE다.
Original Abstract, p.1
The evaluation results show that XHarvest reduces the hardware cost by 31.50% while achieving the same or even higher performance than conventional SSDs.
Main topic 필요한 이유 (Why)
기존 접근들은 세 겹으로 실패한다.

1층 — conventional SSD의 cost-utilization dilemma.
PCIe 5.0 SSD는 PCIe 3.0 SSD(3.5 GB/s) 대비 14 GB/s를 내려고 연산 능력이 4.43$\times$ 필요하고, ONFi 5.0은 flash backbone을 4채널 800MT/s에서 16채널 2400MT/s로 늘렸다. FTL 매핑 테이블은 7.5TB SSD에 10GB DRAM을 요구한다. 그 결과 1TB SSD 원가에서 연산 자원이 30%, DRAM이 10% 를 차지한다. 그런데 그 자원이 필요한 순간은 전체 시간의 극히 일부다(대역폭 80% 이상 사용은 runtime의 0.28%).

2층 — OCSSD는 이 원가를 없앴지만 호스트를 망가뜨렸다.
OCSSD는 내부 연산/DRAM을 통째로 제거하고 LightNVM + pblk로 호스트에서 FTL을 돌린다. 하지만 (i) 정적(static) 호스트 메모리 예약이 응용과 상시 경합하고 — Alibaba 서버 응용은 메모리 용량의 약 90%를 상시 점유, 저부하 구간에서는 95% 이상 — (ii) 중간 I/O 부하에서 runtime의 27.33% 동안 CPU 사용률이 높아 CPU 경합도 발생하며, (iii) 오픈소스 펌웨어라 firmware confidentiality가 깨진다. 그래서 Linux 5.15에서 deprecate됐다.

3층 — "적당히 남기자"는 naive solution도 안 된다.
내부에 moderate DRAM + 약한 ARM 프로세서를 남기는 절충안은 세 난제를 남긴다: (1) memory contention과 cost efficiency의 trade-off, (2) hampered host-SSD collaboration — PCIe는 호스트와 SSD를 서로 다른 cache-coherency domain으로 갈라 놓아 FTL 처리량이 95.81% 떨어진다, (3) compromised host CPU exploitation — 보호되지 않은 호스트 펌웨어 실행. 그리고 이걸 그냥 SGX enclave에 넣으면(SGXnaive) ecall/ocall 때문에 4K read 기준 96.13% 가 더 무너진다.

Main topic 해결책 (Solution)
XHarvest의 설계 원리는 한 문장이다: "평상시는 내부 자원으로 격리(isolation), 폭주 때만 호스트 자원을 빌린다(harvesting). 빌리는 통로는 CXL, 빌린 곳의 신뢰는 TEE가 보장한다."

기본 자원 예산(Base). conventional SSD 대비 연산 능력 25%, FTL 매핑 테이블의 10% 를 담을 수 있는 내부 DRAM만 남긴다. 저부하 구간에서는 이 내부 자원만으로 I/O를 처리해 응용과 완전히 격리된다.

네 개의 기둥:

① Secure CPU harvesting (§5.1) — 암호화된 펌웨어 바이너리를 SSD 안에 저장하고, load detector가 폭주를 감지하면 호스트 daemon thread가 enclave를 띄운다. SSD가 attestation으로 enclave의 무결성과 진짜 SGX 프로세서 여부를 검증한 뒤에야 복호화 키를 넘긴다. enclave는 CPU 코어 하나에 pin되어 SSD의 request queue를 polling한다.

② CXL-driven efficient communication (§5.2) — ecall/ocall(20K CPU cycle 이상)과 OS I/O stack을 통째로 우회한다. SSD 내부 메모리에 ring buffer를 두고 64B 메시지 + ready bit로 통신하며, cache coherence가 가시성을 보장한다. 전송 구간은 CXL 3.1 TSP의 AES-GCM으로 암호화된다.

③ Memory harvesting (§5.3) — CXL.mem/CXL.cache로 호스트 EPC + SSD 내부 DRAM을 하나의 주소 공간으로 묶어 통합 FTL cache를 만든다. translation page 단위로 LRU 교체, hash table 인덱스로 조회하며, 엔트리가 어느 쪽에 있든 load/store 명령 하나로 접근한다.

④ Harmonized host-SSD coordination (§5.4) — enclave와 내부 펌웨어의 연산 능력 비(평가에서 1:6)에 맞춰 flash channel과 메모리를 나누고, 논리 주소 공간을 2MB 단위(translation page 하나가 덮는 범위)로 쪼개 round-robin으로 배분한다. 그리고 5ms 창의 부하 감지로 harvesting을 켜고 끈다.
Original §4, p.6
In particular, XHarvest retains only moderate internal resources within the SSD to ensure base performance during common low I/O loads and removes remaining underutilized resources. By default, XHarvest reserves 25% of the computing power of the conventional SSD and memory that can accommodate 10% of the FTL mapping table.
Main topic 결과 (Results)
평가 환경. dual Intel Xeon 8562Y+ (32 cores / 2.8 GHz), 480GB DDR5, Linux 5.15, SGX 2.25, fio 3.16. CXL.mem/CXL.cache는 cross-NUMA 접근(local/numa 102/175 ns, 즉 CXL 유발 지연 75 ns)으로, PCIe/NVMe는 NVMeVirt로 에뮬레이션한다. 에뮬레이션된 SSD는 read/write 25/50 us, 8채널 12die, 펌웨어는 4K random에서 2000K IOPS.

Main topic 결론 (Conclusion)
무엇이 열리는가.
XHarvest는 CXL을 SSD의 새로운 데이터 경로(data path) 가 아니라 새로운 제어 경로(control path) 로 쓴다. 즉 "컨트롤 플레인을 호스트에 위임한다"는 것이 이 논문이 CXL-SSD 계열과 구분되는 지점이고, 저자들은 이것을 "장치에서 호스트로 안전한 연산을 위임하는 새로운 컴퓨팅 패러다임" 이라고 부른다.

실용성 주장. XHarvest는 새 하드웨어를 발명하지 않는다. NVMe/CXL 표준을 그대로 따르고, CXL.io는 PCIe와 동등하게 같은 PHY 레인 위에서 처리되므로 펌웨어 수정만으로 구현된다(펌웨어 5K LOC + enclave 3K LOC, OS/응용 수정 없음). 이미 상용화된 기술(CXL, TEE) 위에 서 있다는 점을 저자들은 산업 호환성의 근거로 든다.

한계는 정직하게 세 가지.
(1) 정작 설계의 정당성을 지탱하는 CXL 3.1 TSP는 통합 가능한 하드웨어가 없어 그 오버헤드를 평가에서 생략했다.
(2) CXL 자체가 실물이 아니라 cross-NUMA로 에뮬레이션됐다(75 ns는 CXL 스펙의 최종 지연 목표치).
(3) 호스트 자원이 부족한 경우의 fallback은 부분적으로만 다뤄진다 — enclave를 못 띄우면 펌웨어가 2순위로 호스트 메모리를 수확하고, 호스트 메모리가 없으면 내부 자원만으로 버틴다(casa에서 ConvSSD 대비 +8.37% latency).

한 줄 요약. "비싼 자원을 장치에 상주시키지 말고, 필요할 때 호스트에서 빌려라 — 단 빌리는 순간의 신뢰와 대역폭 문제를 CXL과 TEE가 대신 풀어준다."
Original §8, p.14
In this work, we propose XHarvest, which harnesses CXL and SGX to facilitate dynamic, efficient, and secure host resource harvesting. XHarvest employs TEE to shield the host-based firmware execution while leveraging the CXL to build a unified and efficient metadata cache. Our evaluation results reveal that XHarvest achieves 31.50% cost savings and 5.02% higher throughput over conventional SSDs.

Memo 설계 결정: 왜 연산 25% / 메모리 10%인가
XHarvest의 기본 구성(Base)은 conventional SSD 대비 연산 능력 25%, FTL 매핑 테이블의 10% 를 담을 내부 DRAM이다. 0%(=OCSSD)도 100%(=ConvSSD)도 아닌 이 중간값이 이 논문에서 가장 임의적으로 보이는 선택이지만, 이유는 구조적이다.

0%가 아닌 이유 — 내부 자원이 0이면 저부하 구간에서도 호스트를 써야 하고, 그 순간 응용과의 경합이 상시화된다(OCSSD의 실패). moderate 내부 자원은 "평상시 격리(isolation)"를 사는 값이다.

100%가 아닌 이유 — 폭주는 runtime의 0.28%(대역폭 80% 이상)뿐이다. 그 0.28%를 위해 원가의 40%(연산 30% + DRAM 10%)를 상주시키는 것이 dilemma의 정의다.

참고 원가 파라미터(§6.2, p.11): NAND flash $5.248 / 128GB, 메모리 $7.5/GB, SSD 컨트롤러 $23, 기타(패키징 등) $4. SSD는 통상 NAND 1TB당 1GB 메모리를 FTL 매핑 테이블용으로 탑재한다.

$$\text{Cost}_{\text{SSD}} = \text{Cost}_{\text{NAND}} + \text{Cost}_{\text{DRAM}} + \text{Cost}_{\text{ctrl}} + \text{Cost}_{\text{other}}$$

이 네 항 중 XHarvest가 건드릴 수 있는 것은 뒤의 두 항뿐이고, 그래서 절감률이 용량에 따라 달라진다(node: 원가 분해 참조).
Claim 왜 'harvesting'이 성립하는가 — burst interleaving
"호스트 자원을 빌린다"는 아이디어가 단순한 희망이 아니라 관측된 통계에 기반한다는 것이 이 논문의 출발점이다. 두 가지 구조적 사실이 근거다.

① burst interleaving (Figure 3c). 모든 SSD가 동시에 폭주하지 않는다. I/O 대역폭 사용률 50% 이상인 active VM이 동시에 5개를 넘는 시간은 runtime의 2.20% 뿐이다. 여러 VM이 하나의 SSD를 공유하는 일반적 배치까지 감안하면 동시 활성 SSD 수는 더 제한된다. $\Rightarrow$ 여러 SSD가 있어도 동시 메모리 수요는 작다. 그래서 온디맨드(on-demand) 할당이 성립한다.

② CPU는 I/O가 바쁠 때 오히려 논다 (Figure 3d). I/O 부하가 85$\sim$100%로 올라가면 CPU 사용률 Low(0$\sim$40%) 구간이 45.69% 로 지배적이 된다(저자들은 CPU waiting을 원인으로 본다). $\Rightarrow$ SSD가 가장 연산이 필요한 바로 그 순간에 호스트 CPU가 가장 한가하다.

두 관측을 합치면 harvesting의 조건이 나온다: 필요한 시점(I/O burst)과 여유가 생기는 시점(host CPU idle)이 겹치고, 동시에 필요로 하는 주체 수(active SSD)는 적다. OCSSD의 정적(static) 예약이 틀린 이유도 여기서 나온다 — 정적 예약은 이 시간축 구조를 아예 활용하지 못한다.

Reference OCSSD / LightNVM · pblk — 왜 커널에서 삭제됐나
논문이 직접 인용하는 선행 아키텍처. XHarvest의 존재 이유는 이 실패의 해부에서 나온다.

무엇이었나. OCSSD(Open-Channel SSD)는 flash read/write 같은 기본 NAND 제어 기능만 남기고 컨트롤러 전체를 제거한다. flash 관리는 Linux의 LightNVM 서브시스템에 위임하고, 그 위에서 pblk가 호스트 기반 오픈소스 펌웨어로 동작하며 전체 FTL 매핑 테이블을 호스트 메모리에 상주시킨다.

왜 실패했나 — 세 축.
1. 자원 경합: 정적/과다한 호스트 메모리 예약이 응용과 직접 경쟁. 서버당 500TB 이상 저장 용량을 다는 요즘 배치에서는 여러 SSD의 예약이 합산되어 더 심해진다.
2. CPU 경합: 응용도 호스트 CPU를 쓴다. Alibaba 서버는 중간 I/O 트래픽 구간에서 runtime의 27.33% 동안 CPU 사용률이 높다.
3. firmware confidentiality 붕괴: request scheduling, wear-leveling 전략, GC 알고리즘은 벤더의 영업 비밀이다. 오픈소스 커널 구현에는 넣을 수 없으므로 성능/기능 향상이 막히고 채택이 좌절된다.

"내부 DRAM과 약한 ARM 프로세서를 적당히 남기자"는 절충안(Figure 1b)이 왜 그대로는 안 되는지 — 논문 §3.2가 정의하는 세 난제. XHarvest의 각 설계 요소는 이 셋과 1:1로 대응한다.

① memory contention $\leftrightarrow$ cost efficiency trade-off
내부 DRAM을 늘리면 호스트 메모리 점유가 줄어 경합이 완화되지만 원가가 오른다. 줄이면 반대다. 게다가 naive solution은 OCSSD의 정적(static) 예약 방식을 그대로 물려받아 I/O 부하와 무관하게 항상 메모리를 점유한다. 다중 SSD 배치에서는 예약이 합산되어 악화된다.
$\Rightarrow$ XHarvest의 답: 동적 harvesting (평상시 0, 폭주 때만 점유).

② hampered host-SSD collaboration
PCIe에서는 SSD 내부 DRAM이 호스트와 다른 cache-coherency domain에 있다. 호스트는 복잡한 OS stack을 거쳐야 메타데이터를 가져올 수 있고(OS stack 10 us vs 단일 메모리 접근 200 ns), non-coherent이므로 DMA로 복사해야 하며, DMA의 4KB 단위는 8B 매핑 엔트리와 어긋나 불필요한 전송을 낳는다. 결과가 FTL 처리량 95.81% 저하다.
$\Rightarrow$ XHarvest의 답: CXL.mem/CXL.cache 기반 통합 메모리 + CXL-driven 메시지 통신.

③ compromised host CPU exploitation
호스트 기반 FTL은 CPU를 쓸 수 있지만 오픈소스 구현이라 펌웨어 기밀성이 무너진다.
$\Rightarrow$ XHarvest의 답: TEE(SGX enclave) 안에서의 암호화 펌웨어 실행 + attestation.

왜 "CXL이어야만 하는가"의 정량적 근거. 논문이 §3.2와 §6.3에서 흩어 놓은 숫자를 모으면 세 겹의 세금이 보인다.

① 소프트웨어 세금 — OS stack
SSD 내부 DRAM이 별도 cache-coherency domain에 있으므로 호스트는 OS stack을 통해서만 메타데이터를 얻는다.
$$t_{\text{OS stack}} \approx 10\ \mu s \quad \text{vs} \quad t_{\text{memory access}} \approx 200\ ns$$
약 50배 차이다.

② 복사 세금 — DMA
non-coherent이므로 메타데이터를 호스트 main memory로 DMA 복사해야 한다. 중복 복사와 전송 오버헤드가 발생한다.

③ 입도(granularity) 세금 — 4KB vs 8B
DMA는 대량 전송(4KB)에 최적화돼 있는데, FTL 매핑 엔트리는 8B다. 어긋난 입도 때문에 필요 없는 엔트리까지 실려 온다. §6.3의 측정: FTL cache hit ratio 100%인 DLSSD에서 요청당 8KB의 트래픽이 발생하고, 그 결과 SRAM FTL cache까지 오염된다(cache pollution). hit ratio 25%에서는 지연의 97.28% 가 FTL 항목이다.

CXL이 지우는 것. CXL.mem/CXL.cache는 cache line 단위 load/store로 device memory에 직접 접근하게 해 ①②③을 한 번에 없앤다. 실제로 XHarvest는 DLSSD 대비 요청당 트래픽을 33.97%(XH-SSD) / 33.89%(XH-Host) 줄인다.

Method Memory harvesting — EPC + SSD DRAM을 하나의 FTL cache로
§5.3. CXL의 cache-coherent 통합 메모리 위에 두 층짜리 FTL cache를 세운다.

enclave에 의한 수확 (Figure 10a). enclave는 호스트 메모리(EPC)와 secure CXL traffic 경유의 SSD 내부 메모리를 모두 접근할 수 있으므로 둘을 합친 combined FTL cache를 만든다.
- SSD는 전체 FTL 매핑 테이블을 translation page라는 특수 flash 페이지에 저장한다. 한 페이지에 인접 LPN들의 매핑 엔트리 여러 개가 들어 있다.
- 초기화 시 enclave가 적당량의 EPC를 확보하고(= 호스트 메모리 수확), SSD 내부 메모리 일부도 함께 관리한다.
- flash에서 translation page를 다시 읽는 비용을 줄이기 위해 LRU(least recently used) 교체 정책으로 시간 지역성(temporal locality)을 활용한다.
- 빠른 조회를 위해 버퍼된 페이지를 추적하는 hash table 인덱스를 유지한다. 조회 성공 시 엔트리가 EPC에 있든 SSD 내부 메모리에 있든 상관없이 load/store 명령 하나로 즉시 접근한다 $\leftarrow$ 이것이 CXL 통합 주소 공간이 주는 결정적 단순화다.
- miss면 LRU victim을 축출한 뒤 목표 페이지를 올린다.

SSD(펌웨어)에 의한 수확 (Figure 10b). 펌웨어도 내부 메모리 + 호스트 메모리로 FTL cache를 구성할 수 있다. 단 펌웨어는 EPC가 아닌 일반 호스트 메모리만 쓸 수 있으므로 보안 기능이 없다. 그래서 (i) 버퍼된 매핑 엔트리를 직접 암호화하고 (ii) CRC 또는 ECC로 무결성 검증을 붙여 메타데이터 손상을 탐지한다.

우선순위. enclave의 연산 능력이 우월하므로 enclave가 1순위, 호스트 CPU 자원이 부족해 enclave를 띄울 수 없을 때 펌웨어가 2순위로 호스트 메모리를 수확한다. 즉 harvesting은 all-or-nothing이 아니라 단계적 fallback 구조를 갖는다.

Method Harmonized host-SSD coordination — 1:6 자원·부하 분할
§5.4. CPU와 메모리를 동시에 수확하면 enclave와 내부 펌웨어가 동시에 I/O를 처리하게 되고, 그러면 메모리와 flash channel을 두고 서로 경합한다. 이 새로운 경합을 없애는 것이 coordination framework다.

자원 분할 (resource allocation). enclave(호스트 CPU 코어 1개)와 SSD 펌웨어는 연산 능력이 크게 다르다. 프레임워크는 flash channel과 메모리(SSD 내부 + 호스트)를 각자의 연산 능력에 비례해 배분한다. 논문 평가에서 그 비율은 펌웨어 : enclave = 1 : 6.
- flash channel 분할은 쓰기 요청의 충돌을 막는 것이 목적이다.
- 읽기 요청은 이 분할을 따르지 않고 해당 PPN이 속한 채널로 그냥 간다(읽기는 충돌을 만들지 않으므로).

부하 분할 (load partitioning). 자원을 나눠도 부하가 그 비율로 오지 않으면 소용없다. 그래서 논리 주소 공간을 2MB 단위로 쪼갠다 — 이 크기는 translation page 하나가 덮는 연속 주소 공간과 정렬된 값이다. 그리고 자원 비율에 따라 round-robin으로 배분한다.

$$1:6 \;\Rightarrow\; \text{7개 단위마다 첫 번째는 SSD, 나머지 6개는 enclave}$$

왜 2MB인가 (설계의 결정적 디테일). 단위를 translation page 경계에 맞췄기 때문에, 한 쪽이 담당하는 주소 영역의 메타데이터는 그 쪽 FTL cache에만 모인다. 만약 임의 크기로 잘랐다면 같은 translation page를 양쪽이 각각 캐시해 중복 적재와 일관성 문제가 생겼을 것이다. 즉 이 값은 성능 튜닝 상수가 아니라 캐시 소유권을 깔끔하게 나누기 위한 구조적 상수다.

This mechanism divides the logical address space into 2MB units, aligning with the continuous address space covered by a single translation page.
Method Dynamic enclave launch — 5ms 창, 60% 임계값, 임계 경로 분리
언제 수확을 켜고 끄는가 (§5.4). "동적"이라는 단어를 실제로 성립시키는 부분.

감지. SSD 안의 load detector가 시간 창(예: 5ms) 안의 I/O 부하를 감시한다. 부하가 임계값(예: 60%)을 넘으면 호스트 메모리에 미리 할당해 둔 flag 변수를 세운다.

$$\text{Load}(T_w) > \theta \quad\Rightarrow\quad \text{harvest},\qquad T_w = 5\ \text{ms},\ \ \theta = 60\%$$

폴링 비용. 호스트 daemon thread는 이 flag를 낮은 빈도(예: 1ms마다)로 polling한다. CPU 소비는 0.1% 수준으로 무시할 만하다.

임계 경로 분리 (핵심 트릭). enclave 인스턴스화는 느리다. 폭주를 감지한 뒤에 만들기 시작하면 그 사이 SSD가 과부하에 빠지고 지연 스파이크가 난다. 그래서:
1. 호스트 부팅 시점에 daemon이 미리 enclave를 만들고 펌웨어를 적재해 둔다.
2. 다만 EPC는 아직 할당하지 않는다 — 응용과의 메모리 경합을 피하기 위해서다. 그리고 enclave에서 빠져나와 polling만 계속한다.
3. 고부하가 감지되면 ecall로 다시 들어가 그때 EPC를 FTL cache용으로 할당한다.
4. I/O 부하가 떨어지면 enclave가 FTL cache를 점진적으로 flush back하고 메모리를 반납한 뒤 ocall로 daemon에 복귀한다.

이 설계가 사는 지점. "만들어 두되 점유하지는 않는다"가 정확히 naive solution의 ①번 난제(정적 예약 vs 원가)에 대한 답이다. 비용이 큰 것은 enclave 생성 시간이고, 경합을 만드는 것은 EPC 점유인데, 이 둘을 시간축에서 분리해 각각 다른 시점에 지불한다. 평가(Figure 23)에서 enclave 대기로 인한 SSD 과부하는 5ms 이내로 제한되고, 60초 규모에서 tail latency 영향은 무시할 수준이다.

Question 왜 공유 메모리를 통째로 암호화하지 않고 TSP를 골랐나?
이 논문에서 가장 배울 만한 판단. 문제는 "CXL 공유 메모리가 손상된 OS에 노출된다"였고, 가장 자명한 답은 "EPC처럼 공유 메모리 전체를 암호화한다"였다. 논문은 이 답을 거부한다.

거부 이유 (논문의 논거). 공유 메모리를 통째로 암호화하면, SSD 펌웨어가 자기 내부 메모리에 있는 메타데이터를 읽을 때조차 암/복호화 비용을 낸다. 즉 신뢰 경계 안쪽의 접근에까지 세금을 매기는 셈이다.

대신 선택한 것. enclave와 SSD를 둘 다 trusted entity로 인정하고, 보호 대상을 "저장된 데이터"에서 "전송 중인 트래픽" 으로 옮긴다. 그 도구가 CXL 3.1의 TSP이며, AES-GCM은 바이트당 약 1 CPU cycle로 CXL 메모리 접근 지연 대비 약 5% 만 더한다.

남는 질문들:
- 신뢰 경계를 전송 구간으로 옮기면, SSD 내부 DRAM 자체에 대한 물리적 공격(예: 장치 분해, 인터포저)은 어떻게 되는가? 논문은 TSP가 "physical attacks를 막기 위해 트래픽을 암호화한다"고만 말하고 장치 내부 메모리의 물리 보호는 다루지 않는다.
- "SSD는 본질적으로 trusted entity"라는 전제는 펌웨어가 손상되지 않았음을 가정한다. attestation은 enclave 쪽 무결성을 검증하지만, 역방향(호스트가 SSD를 검증)에 대해 논문은 CMA의 상호 인증을 든다 — 다만 그 검증의 근거가 되는 SSD 측 신뢰 루트(root of trust)에 대한 서술은 없다.
- 만약 향후 TSP 하드웨어가 예상보다 비싸다면, 이 "전송만 보호" 전략의 5% 가정이 유지될까? (평가에서 이 오버헤드는 아예 생략됐다 — 별도 gap 노드 참조.)

Reference 관련 연구 좌표 — ZNS · LMB · BlockFlex · Pond · CXL-SSD · IceClave
논문 §7이 스스로 그린 좌표계. XHarvest의 신규성이 어디에 있는지 이 배치가 정확히 말해 준다.

원가 효율 스토리지 축
- ZNS SSD — 내부 메모리를 없애고 flash block을 coarse-grained zone으로 묶어 호스트 측 매핑 테이블을 작게 만든다. 하지만 append-only write 제약이 사용성과 채택을 제한한다. XHarvest는 주류 block-interface SSD를 겨냥하며 응용 수정이 필요 없다.
- LMB — CXL로 DMA를 대체해 DRAMless SSD의 호스트 기반 FTL cache를 개선한다. 그러나 고정 메모리 예약을 그대로 물려받고 SSD 내부의 연산 자원 문제를 보지 않는다.
- BlockFlex — 클라우드에서 놀고 있는 flash 용량을 수확한다. XHarvest는 대상이 다르다 — 연산·메모리 자원을 수확한다.

CXL 축
- Pond — VM을 위한 CXL 기반 공유 메모리 풀로 DRAM 원가를 줄인다.
- CXL-SSD 계열 — flash와 DRAM을 CXL로 결합해 SSD 안의 새로운 데이터 경로(data path) 를 만들고 고용량·고성능 SCM 장치를 지향한다.
- XHarvest의 차별점 — 같은 목표를 공유하되 CXL을 새로운 제어 경로(control path) 로 쓴다. 즉 제어 경로를 호스트에 위임해 SSD 내부 자원 의존을 줄인다.

TEE 축
- Intel SGX 외에 AMD SEV, ARM TrustZone, RISC-V Keystone이 유사 기능을 제공하며, 적절한 SDK 이식으로 XHarvest 포팅이 가능하다는 것이 저자들의 입장.
- 선행 TEE 연구는 데이터베이스 보호, 그리고 TrustZone으로 in-storage computing을 보호(IceClave) 하는 등 주로 데이터 보안에 집중했다. XHarvest는 TEE를 CXL의 새 기능(TSP) 과 결합해 호스트 기반 SSD 펌웨어 실행 자체를 보호하고, 저자들은 이를 "장치에서 호스트로의 안전한 연산 위임"이라는 새 컴퓨팅 패러다임으로 규정한다.

얼마나 큰 구멍인가 — 논문 내부에서 추정할 수 있는 범위:
- 저자들이 인용하는 근거는 AES-GCM이 바이트당 거의 1 CPU cycle이며 CXL 메모리 접근 지연 대비 약 5% 의 지연 오버헤드라는 것(§5.2).
- 그리고 §6.3 측정에 따르면 통신 트래픽 자체가 요청당 256B, MAC은 전송당 12B로, 실제 데이터 전송 대비 4KB 요청에서 +7.64%, 64KB 요청에서 +0.47% 뿐이다.
- 따라서 "marginal"이라는 저자들의 표현은 근거가 아주 없지는 않다. 다만 직접 측정된 것이 아니다.

함께 놓아야 할 두 번째 층. CXL 자체도 실물이 아니라 cross-NUMA(75 ns) 로 에뮬레이션됐다. 즉 이 논문의 성능 수치는 두 겹의 가정 위에 있다 — (i) 성숙한 CXL 하드웨어, (ii) 오버헤드가 무시할 만한 TSP.

따라서 열려 있는 질문. 논문의 세 축(cost / performance / security) 중 security 축만 유일하게 end-to-end로 측정되지 않았다. 실물 TSP 하드웨어에서 31.50% 원가 절감과 +5.02% 성능이 동시에 유지되는지는 후속 검증 대상이다. 이 논문을 재현하거나 확장하려는 사람에게 가장 먼저 손댈 지점이 여기다.

Question SGX 의존성과 '호스트가 먼저 굶주릴 때' 문제
논문이 답한 부분과 답하지 않은 부분을 구분해 보자.

① SGX 의존성 — 논문의 답은 "이식 가능하다".
§7은 AMD SEV, ARM TrustZone, RISC-V Keystone이 유사한 보안 기능을 제공하므로 적절한 SDK로 마이그레이션하면 포팅이 가능하다고 말한다. 다만 각 TEE의 보호 메모리 모델이 EPC와 다르다(예: SEV는 VM 단위 암호화, TrustZone은 secure world 분할). XHarvest의 memory harvesting은 "enclave가 EPC를 FTL cache로 직접 쓴다"는 EPC 고유 성질에 기대고 있어, 이 이식이 실제로 얼마나 자명한지는 논문에 측정된 바 없다. 열린 질문이다.

② 호스트 메모리가 부족하면? — 부분적으로 답했다.
- 설계 차원: enclave를 띄울 CPU 자원이 없으면 펌웨어가 2순위로 호스트 메모리를 수확한다(§5.3). 그마저 없으면 moderate 내부 자원만으로 동작한다.
- 측정 차원: XHarvest w/o HostMem 실험에서 최악의 경우도 ConvSSD 대비 +8.37%(casa) 수준에 머문다. 같은 조건에서 DLSSD w/o HMB는 +83.28% 로 무너진다.
- 그러나 EPC 용량 자체의 한계(SGX의 EPC는 유한하며 초과 시 페이징으로 급격히 느려진다)에 대한 분석은 없다. 평가는 SSD당 128MB로 고정돼 있어, 대용량 SSD가 더 큰 FTL cache를 원할 때 EPC가 병목이 되는 지점이 어디인지 알 수 없다.

③ 응용이 CPU를 정말 다 쓰고 있는 순간에는?
논문의 근거는 "I/O 부하가 85$\sim$100%일 때 CPU Low 구간이 45.69%로 지배적"이라는 통계다. 뒤집어 말하면 나머지 54.31%의 시간에는 그렇지 않다. 저자들도 "고 I/O 부하에서 CPU 자원이 부족한 경우는 드물다"고만 말한다. 통계적 논거이지 보장이 아니라는 점은 기억해 둘 만하다.
Gap / Idea 논문이 다루지 않은 것 — 크래시 일관성과 호스트 측 메타데이터의 운명
PDF 전체를 훑어도 crash consistency / power-loss recovery / durability에 대한 서술은 없다. 이것은 비판이 아니라 후속 연구를 위한 좌표다. 왜 문제가 되는지 구조적으로 짚어 둔다.

무엇이 위태로운가. XHarvest에서 dirty FTL 매핑 엔트리가 호스트 측 EPC에 존재할 수 있다. 즉 SSD의 전원과 무관한 도메인에, SSD의 정합성을 결정하는 메타데이터가 놓인다. 전통적 SSD라면 이 메타데이터는 전원 손실 보호 커패시터가 있는 장치 내부에만 있었다.

논문이 말하는 것.
- I/O 부하가 떨어지면 enclave가 FTL cache를 점진적으로 flush back하고 메모리를 반납한 뒤 ocall로 나간다(§5.4). 즉 정상 종료 경로는 정의돼 있다.
- 펌웨어가 일반 호스트 메모리에 캐시할 때는 CRC 또는 ECC로 무결성 검증을 수행해 메타데이터 손상을 탐지한다(§5.3). 즉 손상 탐지는 있다.

논문이 말하지 않는 것.
- 비정상 경로: 호스트 전원 손실, 커널 패닉, enclave 강제 종료 시 EPC 안의 dirty 엔트리는 어떻게 되는가?
- 탐지(CRC/ECC)는 손상을 알려줄 뿐 복구하지 않는다. 복구 프로토콜(저널링, 체크포인트 주기)에 대한 서술이 없다.
- 부하 급감 시의 flush back이 얼마나 걸리는지, 그 사이에 크래시가 나면 어떤 창(window)이 열리는지에 대한 정량화가 없다.

연구 아이디어. dynamic harvesting의 "릴리스" 경로를 crash-consistent하게 만드는 것 — 예컨대 harvest 구간 동안의 매핑 갱신을 SSD 내부 저널에 로그하고, EPC는 순수 읽기 캐시로만 쓰거나, TSP의 MAC을 무결성뿐 아니라 버전 관리에 재사용하는 방향. XHarvest가 열어 놓은 "장치 제어 경로를 호스트에 위임한다"는 패러다임 전체가 이 질문을 상속받는다.
