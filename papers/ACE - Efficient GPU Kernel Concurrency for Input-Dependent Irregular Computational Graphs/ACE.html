ACE: Efficient GPU Kernel Concurrency for Input-Dependent Irregular Computational Graphs
Click a node to select
Main topic Killer Application
작은 커널(small kernel)들로 인한 GPU underutilization

딥 강화학습(deep RL) 물리 시뮬레이션 엔진과 dynamic DNN(입력에 따라 실행 경로가 달라지는 신경망)은 thread/thread block 수가 매우 적은 작은 커널들로 구성된다. 각 CTA가 서로 다른 시나리오를 시뮬레이션하기 때문에 큰 커널로 합치면 thread divergence가 커져서, 애플리케이션은 대신 짧고 많은 커널로 프로그래밍된다. 그 결과 achieved occupancy(활성 warp 비율)가 평균 34~39%에 불과해 GPU 컴퓨트 자원의 상당 부분(최대 65%)이 놀게 된다.

이 커널들 중 다수는 서로 독립적이어서 concurrent(동시) 실행이 가능하지만, 문제는 그 의존관계(computational graph)가 입력마다 runtime에만 결정된다는 점이다.
Original Abstract, p.258
GPUs are widely used to accelerate many important classes of workloads today. However, in this work, we observe that several important emerging classes of workloads, including simulation engines for deep reinforcement learning and dynamic neural networks, are unable to fully utilize the massive parallelism that GPUs offer.
Main topic 필요한 이유 (Why It's Needed)
기존 방법들은 input-dependent + irregular 의존성을 다루지 못한다

CUDA Graph / AMD ATMI 같은 DAG(directed acyclic graph) 프레임워크는 커널 간 의존성을 미리 정의된 그래프로 표현해 동시 실행을 가능케 하지만, 입력마다 전체 그래프를 새로 구축해야 하므로 준비 오버헤드(preparation overhead)가 크다. Multi-stream 방식은 그래프를 여러 스트림으로 수동 분할해야 하는데, 불규칙(irregular)한 의존성은 stream 경계에서 빈번한 동기화(synchronization)를 요구해 오버헤드가 크다. Persistent threads(PT)는 동질적 커널에서만 효과적이고, CUDA Dynamic Parallelism(CDP)/Device Enqueue(DE)는 부모-자식 1:1 의존성만 지원해 다중 부모 의존성을 표현하지 못한다.
Original §1, p.259
The challenge with this approach is that the DAG needs to be constructed in full (with dependencies, kernel launches, and barriers determined) before the application is executed on the GPU, for each input.
Main topic 해결책 (Solution)
Scheduling window 안에서만 의존성을 검사하는 out-of-order kernel scheduling

ACE의 핵심 아이디어는 CPU의 out-of-order 명령어 스케줄링(instruction scheduling)에서 착안해, 전체 computational graph 대신 이미 launch된 커널들 중 작은 고정 크기의 창(scheduling window) 안에서만 의존성 검사를 수행하는 것이다. 프로그래머/라이브러리 작성자가 각 커널의 read/write 메모리 세그먼트를 annotation으로 제공하면(ACE_wrapper), 런타임은 새 커널이 window에 들어올 때 겹침(overlap) 검사를 통해 upstream(선행) 커널을 식별하고, 그 upstream 리스트가 비면 즉시 ready로 표시해 동시 launch한다.

두 가지 구현: ACE-SW(순수 소프트웨어, CUDA stream 다중 스레드 런타임)와 ACE-HW(scheduling window 관리를 GPU 하드웨어 SRAM으로 옮겨 CPU-GPU 동기화를 줄이는 하드웨어-소프트웨어 협력 방식).
Original §3.2, p.262
With ACE, the key idea is to instead perform the dependence checking and scheduling within a small window of kernels at runtime similar to out-of-order instruction scheduling.
Main topic 결과 (Results)
실제 하드웨어 + GPU 시뮬레이터에서 최대 2.19배 속도 향상

Intel 11700K + RTX3060(ACE-SW 실측)과 Accel-Sim 기반 RTX3070/RTX4090급 시뮬레이션(ACE-HW)으로 평가했다. Deep RL 물리 시뮬레이션(Brax), dynamic DNN(InstaNAS 등), static DNN(NASNet 등) 세 부류 모두에서 achieved occupancy와 실행 속도가 유의미하게 향상되었고, ACE-HW가 ACE-SW보다 일관되게 더 큰 이득을 보였다(커널 완료마다의 CPU 동기화가 없기 때문). CUDA Graph는 동적 워크로드에서는 그래프 구성 오버헤드로 오히려 slowdown, 정적 워크로드에서는 ACE와 대등했다.
Original Abstract, p.258
We demonstrate speedups of up to 2.19× (1.56× on average) by improving GPU utilization with concurrent kernel execution.
Main topic 결론 (Conclusion)
Host 개입을 "줄이지만" 완전히 없애지는 않는다

ACE는 low-overhead runtime scheduling과 dependency check를 결합한 최초의 automatic concurrent execution 프레임워크라고 저자들은 주장한다. ACE-HW는 커널 완료-이벤트 단위의 CPU-GPU 동기화를 제거해 host 개입을 크게 줄이지만, CPU 소프트웨어 런타임(입력 FIFO 큐 관리, `scheduled_list` 대비 의존성 체크)은 여전히 필요하다. 또한 ACE가 다루는 의존성은 커널 간 메모리 read/write 겹침이라는 정적으로 판별 가능한 관계이며, 커널이 만들어낸 값 자체에 따라 분기하는 제어(예: LLM decode 루프의 EOS 판정)는 다루지 않는다 — 저자들도 dynamic batching/kernel fusion 등은 "orthogonal to our approach"라고 명시한다.
Original §8, p.269
We introduce ACE, the first framework that enables automatic concurrent kernel execution with low overhead runtime scheduling and dependency checks.

Claim DAG 구성 / 동기화 오버헤드가 지배적
Brax 시뮬레이션에서 CUDA Graph 방식의 DAG 구성 시간이 전체 실행시간의 평균 47%(Fig.8)에 달한다 — 즉 매 입력마다 그래프를 새로 만드는 비용이 실제 계산 시간에 맞먹는다. Multi-stream + 이벤트 동기화 방식은 커널 launch + CPU 실행 + sync 오버헤드가 커널당 5~20µs(Fig.9) 수준으로, 커널 자체가 작을수록(수 µs) 상대적으로 더 치명적이다.

Reference Baseline: CUDA Graph / ATMI / CDP
CUDA Graph[1] / AMD ATMI[2]: 커널 의존성을 DAG로 명시, ATMI는 64바이트 barrier packet을 command queue에 삽입해 의존 커널의 launch를 블록. 그러나 barrier packet은 GPU 내 실행 중인 커널의 현재 상태 정보를 담지 않아 추가적인 runtime reordering을 못한다.

CDP[3] / Device Enqueue[7]: 부모 커널이 자식 커널을 device에서 직접 launch — 부모-자식 1:1 의존성만 표현 가능해, 다중 선행 커널에 의존하는 워크로드(RL sim, dynamic DNN)에는 부적합.
Original §1, p.259
CUDA dynamic parallelism [3] (CDP) or AMD's device enqueue [7] (DE) enables parent kernels to launch child kernels, only allowing data dependencies between one parent and its children.
Method Scheduling Window 컨셉
고정 개수(N)의 최근 launch된 커널만 window에 유지하며, 각 커널의 상태를 pending / ready / executing 세 가지로 추적한다. 새 커널이 window에 들어올 때 write segment를 window 내 다른 커널들의 read/write segment와 비교해 겹치면 upstream(선행) 리스트에 추가한다. 어떤 executing 커널이 완료되면 그 커널을 upstream으로 갖던 모든 커널의 리스트를 갱신하고, 리스트가 비면 ready로 표시해 즉시 concurrent launch한다.

Original §3.2, p.262
A fixed number of kernels in the original stream (scheduling window) are evaluated for dependencies. When a kernel completes execution, we evaluate which kernels within the scheduling window are now ready for execution.
Method ACE-SW: 소프트웨어 전용 구현
애플리케이션 레벨 런타임으로, 두 모듈로 구성:

1. Window 모듈: 입력 FIFO 큐 관리 + Algorithm 1(read/write segment 겹침으로 의존성 판정) + 상태(pending/ready/executing) 갱신.
2. Scheduler 모듈: 설정 가능한 수의 스레드가 각각 독립 CUDA stream을 갖고, ready 커널을 poll해 launch한 뒤 `StreamSync`로 완료를 기다림(Algorithm 2, Fig.17).

프로그래머는 `ACE_wrapper`의 `get_addresses` 함수로 read/write segment만 정의하면 되고, CUDA 런타임이 kernel launch 직전에 이를 호출해 가상주소를 populate한다.

한계: `StreamSync`가 스케줄러 스레드를 블로킹 — 즉 CPU가 커널 완료마다 여전히 개입.
Original §1, §4.2, p.259/264
ACE-SW is implemented as a user-level runtime that is called by the application. ... ACE-SW however still incurs synchronization overheads from communication between the CPU and kernel launch.
Method ACE-HW: 하드웨어 협력 구현
Scheduling window 관리 자체를 GPU 하드웨어(SRAM, N개 슬롯, 슬롯당 8-bit kernel id + (N-1)개 upstream id + 2-bit 상태)로 옮긴다. CPU 소프트웨어 런타임은 여전히 입력 FIFO 큐 + `scheduled_list`(GPU 상태의 stale할 수 있는 CPU측 캐시)를 유지하며 의존성을 미리 계산해 GPU로 보내지만, GPU 내 upstream load module이 이 stale 정보를 스스로 정제(완료된 커널 제거, 최신 커널 반영)하고 ready 커널을 dispatch — 커널 완료 이벤트마다의 CPU 동기화가 사라진다.



Original §3.1, p.262
Our approach is specifically designed to mitigate this scheduling cost by avoiding direct communication from the GPU to the CPU, thereby reducing potential overheads.

Gap / Idea Host 개입이 완전히 사라지지 않음
ACE-HW조차 CPU 소프트웨어 런타임(입력 FIFO 큐 관리, `scheduled_list` 유지·의존성 사전계산)을 완전히 없애지 않는다. 사라지는 것은 "커널 완료마다의 동기화"뿐이고, "커널을 큐에 넣고 의존성을 체크하는 주체로서의 host"는 계속 CPU에 남아있다.

또한 ACE의 의존성 판정은 메모리 read/write 주소 범위 겹침이라는 정적으로 결정 가능한(deterministic) 함수다 — 커널이 만들어낸 값 자체(예: 스칼라 결과)에 따라 분기하는 제어는 이 프레임으로 표현되지 않는다.
Original §4.3, p.265
the software runtime performs dependency checks with the scheduled_list to determine the upstream kernels. Note that since the scheduled_list may be stale, this upstream list needs to be further updated before insertion into the scheduling window
Memo H3 연결 메모
내 H3(GPU 옆 FPGA 제어 평면이 host의 kernel 스케줄링/launch 결정을 대신)와의 관계:

- align되는 부분: "host-GPU 통신을 줄여 input-dependent 상황에서 GPU 활용도를 높인다"는 큰 방향. ACE-HW가 scheduling window를 GPU 하드웨어로 옮긴 설계는 FPGA 제어 평면의 축소판처럼 보임.
- align되지 않는 부분: ACE의 의존성은 정적으로 판별 가능한 메모리 겹침 관계. 내가 표적으로 삼는 LLM decode 루프의 EOS 판정/continuous batching은 커널 실행 결과값에 따른 조건부 제어로, ACE의 프레임(read/write segment overlap)으로는 표현 불가능.
- 이 논문은 "host 개입을 줄이는" 사례이지 "없애는" 사례가 아님 — 정직하게 구분해서 인용할 것.
Reference Related Work: "orthogonal"한 기법들
저자들은 §7에서 dynamic batching, kernel fusion 등을 "orthogonal to our approach"라고 명시적으로 구분한다 — 즉 ACE는 이런 기법들과 결합 가능하지만 그 자체를 대체하지는 않는다는 뜻. 내 연구가 다루려는 LLM decode 제어(continuous batching 편입/이탈, KV 배치)가 바로 이 "orthogonal" 영역에 위치한다는 점이 흥미로운 근거가 될 수 있음.

또한 CPU task-based 스케줄링(task superscalar 등)과 비교하며 저자들은 "CPU의 병목은 의존성 체크 지연, GPU의 병목은 launch/완료 신호 지연"이라고 명확히 구분한다 — 이 구분이 H3에서 FPGA가 정확히 어떤 지연을 줄여야 하는지 설계할 때 참고할 만하다.
Original §7 / §1, p.269 / p.259
The primary bottleneck in these applications is the long latency for dependency checks. ... The primary bottleneck with GPUs is the latency for launch/signal completion of kernels rather than dependence checking.
