Main topic Killer Application
DirectCXL가 푸는 문제는 메모리 분해(memory disaggregation)를 CXL.mem으로 직접 실현해, RDMA 기반 분해의 데이터 복사·network 개입 오버헤드를 없애는 것이다. 그리고 이걸 실제 하드웨어로 만든 최초 사례다(상용 CXL 2.0 IP가 없어 CXL controller·switch·RISC-V host를 전부 자작).

Killer application 1 — 복사 없는 원격 메모리: host의 `load`/`store`가 LLC에서 곧바로 CXL flit으로 변환돼 원격 HDM에 도달. RDMA처럼 원격→host 데이터 복사가 없어 원격 메모리의 '진짜 성능'이 드러난다.

Killer application 2 — CPU cache까지 활용: 원격 메모리인데도 host CPU cache에 캐시돼, cache hit면 local DRAM과 동일한 4-cycle 지연.

Killer application 3 — 실물 CXL 2.0 disaggregation testbed: FPGA CXL memory blade + CXL switch(fabric manager) + RISC-V host를 묶어 RDMA와 정량 비교한 첫 real-system 분석.

결과: 64B load 지연이 RDMA 대비 8.3×, 실 워크로드에서 RDMA swap 대비 3× 빠름.
Original Abstract, p.1
DIRECTCXL's latency is shorter than the best latency of RDMA by 6.2x, on average. For real-world applications, DIRECTCXL exhibits 3x better performance than RDMA-based memory disaggregation, on average.
Main topic 필요한 이유 (Why It's Needed)
메모리 분해는 메모리 활용률·탄력성·자원관리 효율 때문에 주목받지만, 기존 방식은 전부 RDMA(또는 유사 network)로 원격↔host 데이터를 옮긴다.

(1) Page-based (swap): kswapd 아래 드라이버가 page fault 시 원격으로 swap. 투명하나 page fault 처리·I/O amplification·context switching 비용.

(2) Object-based (KVS): KV store로 원격 접근. page swap은 피하나 소스 대규모 수정 + 메모리 노드 연산(해싱) 필요.

공통 병목: RDMA는 양쪽에 MR 등록, MTT 주소변환, RNIC 간 데이터 복사(one-sided도 DMA 2회)가 필수라, 지연이 local DRAM보다 수 자릿수 커진다. 즉 '원격 메모리를 쓰려면 복사하고 network를 태워야 한다'가 근본 한계.
Original §2.2, p.3
all these approaches use RDMA (or a similar network protocol), which is essential to cache the data and pay the cost of memory operations for network handling.
Main topic 해결책 (Solution)
DirectCXL는 원격 메모리를 host system bus에 붙은 local DRAM처럼 다룬다.

1. HDM을 host 메모리에 매핑: CXL device 내부 DRAM = HDM. host kernel driver가 BAR·HDM 크기를 PCIe transaction으로 질의해 host 예약 메모리에 매핑. `load`/`store` → CXL RP가 CXL flit으로 변환 → CXL controller가 HDM base를 빼서 주소 변환 → DRAM controller. SW 개입·복사 없음.

2. CXL switch + Virtual Hierarchy(VH): USP/DSP + fabric manager(FM)가 crossbar를 재구성해 host↔device 경로(VH) 생성. ★ 각 VH는 단일 경로만 제공해 어떤 host도 HDM을 공유하지 않도록 보장(=분할, 공유 아님).

3. cxl-namespace runtime: 상용 CXL OS가 없어 자작. HDM을 segment(cxl-namespace)로 쪼개 mmap으로 app에 노출. `/dev/directcxl` ioctl로 관리.

4. FPGA 프로토타입: 16nm FPGA CXL memory blade(8 DDR4=64GB), 자작 RISC-V 4-core(LLC에 CXL RP), CXL switch — 전부 밑바닥 구현.
Original §3.2, p.4
Once a virtual hierarchy is established between a host and CXL device(s), applications running on the host can directly access the CXL device by referring to HDM's memory space.

Main topic 결론 (Conclusion)
DirectCXL는 host processor complex와 원격 메모리를 CXL.mem으로 직접 연결해, 워크로드가 host cache를 누릴 수 있으면 DRAM급 성능을, 실 워크로드에선 RDMA 대비 평균 3×를 낸다. '원격 메모리를 복사 없이 load/store로'가 실물에서 성립함을 증명했다.

의의: [[SkyByte]] 등 CXL.mem 기반 memory-semantic 설계의 하드웨어 토대. CXL flit·HDM 매핑·RP/switch 구현의 실제 레퍼런스.

향후/한계: (1) 커널의 효율적 CXL 메모리 관리 확장, SoC 실리콘화가 future work. (2) CXL IPs가 지연의 77.8% — 실리콘 전까진 tail이 Local 대비 2.8×. (3) ★ VH가 host↔HDM을 1:1 격리해 coherence 문제를 회피 — 여러 host가 같은 HDM을 공유하는 multi-node coherence는 범위 밖(CXL 2.0 한계). (4) storage 결합(persistence/GC) 없이 순수 DRAM 분해.
Original §5, p.7
we propose DIRECTCXL that connects host processor complex and remote memory resources over CXL's memory protocol (CXL.mem). ... the disaggregated memory resources of DIRECTCXL can exhibit DRAM-like performance when the workload can enjoy the host-processor's cache.
Claim RDMA vs CXL 근본 차이: 복사 없음 + LLC→flit 직변환
DirectCXL가 RDMA를 8.3× 이기는 두 근본 이유. (1) DirectCXL는 host↔memory를 PCIe로 직결하는 반면 RDMA는 InfiniBand↔PCIe 프로토콜 변환이 필요. (2) DirectCXL는 LLC의 load/store를 곧바로 CXL flit으로 변환하는 반면 RDMA는 반드시 DMA로 메모리를 read/write한다(one-sided도 DMA 2회 → PCIe transfer·메모리 접근 2배). 그래서 RDMA 지연의 78.7%(2129 cyc)가 InfiniBand network에서 나온다. DirectCXL엔 그 network·복사 계층 자체가 없다.
Original §4.1, p.6
DirectCXL can translate memory load/store request from LLC into the CXL flits whereas RDMA must use DMA to read/write data from/to memory.
Claim RDMA 병목 해부: network 78.7%, small payload는 library
RDMA 지연을 분해하면(Fig.7a) payload가 1KB보다 작을 땐 user-level InfiniBand library(libibverbs/libmlx4)가 주 병목(평균 4158 cyc), payload가 커지면 MR로의 데이터 복사(Copy)가 실행시간의 28.9%까지 증가. Memory·Network는 RDMA와 유사 추세. 즉 RDMA는 (a) network 왕복, (b) SW library 개입, (c) MR 복사 — 세 겹의 비용을 못 피한다. DirectCXL 분해엔 (Fig.7b) SW도 data copy도 없다.
Original §4.1, p.6
Library is the primary performance bottleneck in RDMA when the size of payloads is smaller than 1KB (4158 cycles, on average).

Method HDM을 host 시스템 메모리에 매핑 (RP → flit → 주소변환)
CXL device 내부 DRAM은 HDM(host-managed device memory)으로 노출된다. host kernel driver가 device의 BAR·HDM 크기를 PCIe transaction으로 질의해 host 예약 시스템 메모리에 매핑하고, device에 '어디 매핑됐는지'를 알린다.

host가 HDM을 `load`/`store`하면 → 해당 CXL RP가 요청을 CXL flit으로 변환 → CXL controller가 HDM base 주소를 빼서(deduct) 내부 DRAM 주소로 번역 → DRAM controller가 서비스 → CXL switch·FlexBus 통해 host로 반환. SW 개입·메모리 복사가 전혀 없어 낮은 지연.
Original §3.2, p.4
the CXL controller translates the incoming addresses by simply deducting HDM's base address from them ... since HDM accesses have no software intervention or memory data copies, DIRECTCXL can expose the CXL device's memory resources to the host with low access latency.
Method CXL switch + Virtual Hierarchy — ★ no host sharing an HDM
CXL switch는 USP(upstream)/DSP(downstream) 포트와 fabric manager(FM)로 구성. FM이 내부 crossbar를 재구성해 각 USP를 다른 DSP에 연결 → virtual hierarchy(VH) 생성(root=host → terminal=CXL device). CXL device는 여러 controller/DRAM으로 multiple logical device를 정의해 각자 HDM을 서로 다른 host에 노출.

★ 결정적: 각 VH는 하나의 경로만 제공해 어떤 host도 HDM을 공유하지 않도록 보장한다. 즉 여러 host가 붙어도 각 HDM은 한 host 전용(분할=pooling)이지 공유(sharing)가 아니다 — coherence 문제가 애초에 발생하지 않는 구조.
Original §3.1, p.4
each CXL virtual hierarchy only offers the path from one to another to ensure that no host is sharing an HDM.
Memo 혼동 정리: multi-host(물리 연결) ≠ HDM 공유(논리)
영상에서 '스위치에 여러 host + 여러 device'를 봤는데 왜 'single host'라 하나? → 둘 다 참이다. 'single host'는 host 수가 아니라 '한 HDM을 한 host만 본다(공유 없음)'는 뜻. 세 레벨을 분리하면 명확하다.
레벨DirectCXL뜻
① 물리 연결multi-host, multi-device스위치에 여러 host+device (← 영상)
② 메모리 소유HDM 1조각 = host 1개각 host가 전용 슬라이스 (분할=pooling)
③ coherent 공유없음여러 host가 같은 영역 동시 캐싱 = 안 함

같은 device가 여러 host에 붙는다(①)는 것과 같은 HDM을 여러 host가 공유한다(③)는 것은 완전히 다르다. DirectCXL은 device를 multiple logical device로 쪼개 각 조각(HDM)을 서로 다른 host에 주므로 ①은 되지만 ③은 안 된다.

주차장 비유: 차 여러 대(host)가 한 주차장(device/switch)을 쓰지만(①), 한 칸(HDM)엔 한 대만(②). 두 대가 같은 칸에 겹쳐 서로 조율(③)하는 게 진짜 '공유'인데, 그건 CXL 2.0엔 없다(CXL 3.0 back-invalidate 필요).
Original §3.1, p.4
different hosts can be connected to a CXL switch and a CXL device. Note that each CXL virtual hierarchy only offers the path from one to another to ensure that no host is sharing an HDM.
Method cxl-namespace software runtime (mmap)
상용 CXL OS가 없어 DirectCXL runtime을 자작. HDM 주소공간을 여러 segment(cxl-namespace)로 쪼개, app이 이를 memory-mapped file(mmap)로 접근하게 한다. PCIe enumeration 시 driver가 `/dev/directcxl`를 만들고 ioctl로 namespace를 관리(HDM segment table = offset·size·refcount, spinlock/rwlock 헤더). PMDK(NVMe namespace식, 고정 크기·파일시스템 경유)보다 단순·유연 — 전통 memory segment에 가까워 파일시스템 없이 직접 노출.
Original §3.2, p.4
we support DIRECTCXL runtime that simply splits the address space of HDM into multiple segments, called cxl-namespace. DIRECTCXL runtime then allows the applications to access each CXL-namespace as memory-mapped files (mmap).
Method FPGA 프로토타입: 자작 CXL controller·switch·RISC-V RP
상용 CXL 2.0 IP가 없어 전부 밑바닥부터 구현. CXL memory blade AIC = 16nm FPGA + 8 DDR4(64GB), CXL controller + 8 DRAM controller. Host = 자작 RISC-V 4-core OoO, LLC에 CXL RP 구현. softcore 100MHz, CXL/PCIe IP(RP/EP/Switch) 250MHz. RISC-V가 ACPI 미지원이라 device tree로 CXL 2.0 enumeration(RP 위치·예약 주소)을 처리. 4 CXL device(32 DRAM)를 PCIe backplane으로 4 host에 노출, switch가 FM으로 VH 생성.
Original §3.3, p.5
To the best of our knowledge, there are no commercialized CXL 2.0 IPs for the processor side's CXL engines and CXL switch. Thus, we built all DIRECTCXL IPs from the ground.
Result 64B 8.3× · memory hierarchy 6.2× · cache hit 4-cycle
1:1 연결에서 64B read 지연 분해(Fig.6): DirectCXL 328 cycles vs RDMA 2705 cycles = 8.3×. RDMA는 DMA 2회로 PCIe 전송·메모리 접근이 2배, InfiniBand network가 지연의 78.7%.

Memory hierarchy(Fig.8): Local·DirectCXL는 cache hit 시 4 cycles. RDMA best-case 2027 cycles = DirectCXL 대비 6.2×, L1 대비 510.5× 느림. DirectCXL tail latency는 Local 대비 2.8×지만 곡선은 유사(같은 DRAM + network 없음). RDMA는 CPU cache 이득을 못 받아 Local 대비 평균 36.8× 나쁨.
Original §4.1, p.6
The best-case performance of RDMA was 2027 cycles, which is 6.2x and 510.5x slower than that of DirectCXL and L1 cache, respectively.
Result 실 워크로드: Swap 대비 3×, KVS 대비 2.2×
DLRM·MemDB·Ligra 실행시간(Fig.10, Swap 정규화): DirectCXL가 Swap 대비 3×, KVS 대비 2.2× 빠름.

- Swap: 실행의 51.8%를 kswapd+FastSwap 드라이버에 소모(LRU 기반 잦은 page 교환). 그래프(Ligra)는 4KB page를 옮겨 8B 포인터를 읽어 2.2× 손해.
- KVS: DLRM/MemDB에선 page가 아니라 정확한 embedding/value만 로드해 Swap보다 나으나, 소스 수정 필요(MIS/BFS/CC/BC는 KVS로 불가) + 메모리 노드 해싱 비용.
- DirectCXL는 소스 수정·원격 연산 없이 둘 다 이김.
Original §4.3, p.7
DirectCXL without having a source modification and remote-side resource exhibits 3x and 2.2x better performance than Swap and even KVS, respectively.

Memo 계보/발표축: CXL.mem 직접 접근의 실물 원점
DirectCXL는 [[SkyByte]]·[[Hello Bytes, Bye Blocks - PCIe Storage Meets Compute Express Link for Memory Expansion (CXL-SSD)]]와 같은 KAIST CAMELab 계보다. 이 논문이 'CXL.mem으로 device 메모리를 load/store하면 RDMA를 압도한다'를 실물 FPGA로 증명했고, 그 위에서 CXL-SSD 비전(Type-3)과 SkyByte(memory-semantic co-design)가 자란다.

내 'SSD 이중역할 × transparent co-design' 발표축에서 DirectCXL은 인터커넥트 축의 원점 — storage가 아니라 순수 DRAM 분해지만, 'network·복사를 없애고 load/store로 원격 메모리를'라는 CXL.mem의 본질을 가장 깨끗하게 보여준다. RDMA와의 8.3× 대비는 세미나에서 'CXL이 왜 RDMA가 아닌가'의 정량 근거로 쓰기 좋다.
Gap / Idea 내 연구방향: VH의 no-sharing 격리를 풀면?
DirectCXL의 VH는 host↔HDM을 1:1로 격리해 'no host is sharing an HDM'을 보장한다 — 그래서 coherence 문제가 발생하지 않는다(회피). 이게 곧 CXL 2.0 disaggregation의 성격이자 한계다: pooling(분할)이지 sharing(공유)이 아니다.

내 방향(multi-node coherence)은 이 격리를 의도적으로 푼다 — 여러 host가 같은 HDM을 동시에 캐싱하며 공유하면, VH의 단일 경로 보장이 깨지고 directory + back-invalidate(HDM-DB, CXL 3.0)가 필요해진다. DirectCXL의 자작 FPGA testbed(CXL controller/switch/RISC-V RP)는 이 multi-host coherence를 실험할 실물 플랫폼의 원형이 될 수 있다. → [[CXL Multi-node Coherence]], [[CXL Overview]]
Claim sharing coherence는 Type(CXL.cache) coherence와 직교하는 별개 축
'Type-1이 device를 host cache처럼 coherent하게 만드는데, 거기에 sharing을 더하면 Type-1과 별개로 coherence 문제가 또 생기지 않나?' → 정확한 직관. coherence 축이 둘이고 서로 직교한다.

축 A — device 캐싱 coherence (intra-host, 단일 도메인): device가 host 메모리를 캐시할 때(CXL.cache=Type-1/2, bias)의 일관성. 한 host 안에서 CPU 캐시들 + device 캐시를 맞춘다. single-host에서도 필요.

축 B — multi-host sharing coherence (cross-host): 여러 host가 같은 메모리 영역을 동시에 캐싱할 때. host 경계를 넘으니 축 A로는 못 풀고 device가 directory+back-invalidate로 처리(HDM-DB, CXL 3.0).

두 축은 합성된다 — 각 host 내부는 축 A(native+CXL.cache)가, host들 사이는 축 B(back-invalidate)가.

그럼 모든 Type이 sharing coherence 필요? — 정확히는: 공유되는 건 memory(HDM)다. HDM은 Type-2/3만 가진다(Type-1은 HDM 없이 host mem을 캐시만 함 → 풀로 공유할 자기 메모리가 없음). 따라서 sharing coherence(축 B)는 HDM을 가진 device(Type-2/3)에서 그 device가 back-invalidate로 담당한다. Type-1의 캐시 사본도 무효화 대상이지만, 그건 '그 host'가 back-invalidate 받을 때 그 host 도메인 안에서 함께 처리된다(device가 Type-1 agent를 따로 추적하지 않음).

요약: sharing이 더해지면 Type과 무관하게 새 coherence(축 B)가 생기는 게 맞다. 단 그 부담은 '공유되는 HDM을 가진 device(Type-2/3)'가 back-invalidate로 진다.
