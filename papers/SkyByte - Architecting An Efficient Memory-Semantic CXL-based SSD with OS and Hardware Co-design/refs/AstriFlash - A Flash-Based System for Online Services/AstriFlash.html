Main topic Killer Application
AstriFlash가 푸는 문제는 online service가 값비싼 DRAM 대신 50× 싸지만 1000× 느린(≈50µs) flash를 main memory로 쓰게 하되, DRAM-급 throughput과 99%tile tail latency를 지키는 것이다. 열쇠는 HW/SW co-design으로 demand paging 오버헤드를 없애는 것.

Killer application 1 — flash를 memory로, cost 20×↓: host DRAM을 flash 용량의 3%짜리 hardware-managed set-associative cache(4KB page 단위)로 써 hot fraction을 담고, backing flash가 전체 dataset을 담는 2-tier. 요청 분포가 skewed라 소량 DRAM이 대부분 요청을 흡수.

Killer application 2 — paging 오버헤드를 core-side + memory-side로 나눠 둘 다 제거: memory-side는 OS를 빼고 accelerated hardware DRAM-cache miss handler로, core-side는 OS context switch(~5µs) 대신 100ns user-level thread switch(switch-on-miss)로 flash 접근을 다른 job과 overlap.

Killer application 3 — µs급 stall을 견디는 microarchitecture: OoO core가 DRAM-cache miss 시 committed store를 되돌리는 SB speculation(ASO 확장), 100s concurrent miss를 추적하는 in-DRAM Miss Status Row, forward-progress·priority(aging) scheduler.

결과: DRAM-only 대비 throughput 95% 유지, 99%tile tail latency 준수, memory cost 20× 절감.
Original §I, p.2
AstriFlash provides a flash-based system for online services where a fast-but-expensive DRAM contains the hot fraction, and a slow-but-cheaper flash contains the dataset, thus reducing the memory cost by 20x. Our evaluation shows that AstriFlash achieves ∼95% of the throughput of a DRAM-only system while maintaining the 99th-percentile latency.
Main topic 필요한 이유 (Why It's Needed)
datacenter는 tail latency 때문에 dataset을 비싸고 확장 안 되는 DRAM에 둔다. NAND flash는 $/GB 50× 저렴하지만 지연이 1000×(≈50µs). 많은 online service가 ms급 SLO라 몇 µs flash 접근을 흡수할 수 있어 flash-as-memory가 타당하다.

진짜 장애물은 flash가 아니라 demand paging이다. paging은 원래 ms급 disk용이라, µs급 flash에는 오버헤드가 치명적이다. 각 코어가 5-25µs마다 DRAM miss를 내는데, paging은 이를 감당 못 한다.

AstriFlash는 paging 오버헤드를 둘로 해부한다.

(1) memory-side — flash-access 스케줄·용량 관리: page fault마다 OS storage stack(~10µs), page table 갱신, global TLB shootdown(broadcast, 코어 수에 안 스케일, >10µs).

(2) core-side — task 관리·문맥 전환: OoO가 50µs를 못 숨겨 OS가 page fault마다 context switch(각 ~5µs).

기존 제안은 보통 한 종류만 최적화 → AstriFlash는 둘을 동시에(synergistically) 없앤다.
Original §II.C, p.3
as modern devices (e.g., flash) exhibit μs-scale access latencies, paging becomes a critical performance bottleneck. We categorize these overheads into memory-side representing flash-access scheduling and memory-capacity management, and core-side representing task management and context switches.
Memo Tail latency란? — 무엇이고 왜 online service에 치명적인가
Tail latency(꼬리 지연) = 평균이 아니라 지연 분포의 높은 백분위수(p99 / p99.9) 응답 지연. '가장 느린 소수'가 만드는 분포의 꼬리다.

왜 평균이 아니라 tail을 보나 — fan-out 때문: datacenter의 사용자 요청 1개는 보통 수백~수천 개의 하위 요청(sub-request)으로 fan-out돼 여러 서버·데이터로 흩어진다. 사용자 체감 응답은 그중 가장 느린 하나가 결정한다. 그래서 개별 접근의 1%만 느려도, fan-out이 100~1000이면 거의 모든 사용자 요청이 최소 하나의 느린 접근을 만난다 → 개별 p99가 곧 사용자 체감 지연을 지배한다(Dean & Barroso, *The Tail at Scale*). 그래서 SLO는 평균이 아니라 p99/p99.9로 규정된다.

왜 여기서(flash-as-memory) tail이 튀나: flash는 DRAM보다 $\approx 1000\times$ 느리다($\approx 50\,\mu\text{s}$). dataset을 flash에 두면 요청 대부분은 작은 DRAM cache에서 hit하지만(skewed 분포), DRAM을 miss해 flash로 가는 소수가 정확히 꼬리를 만든다. 게다가 demand paging의 불규칙한 OS 오버헤드(context switch $\sim 5\,\mu\text{s}$, TLB shootdown $> 10\,\mu\text{s}$)가 이 꼬리를 예측 불가하게 부풀린다.

그래서 datacenter가 dataset을 통째로 비싼 DRAM에 두는 이유 = 꼬리를 낮게 유지하려고. AstriFlash의 목표이자 성공 기준 = 값싼 flash를 쓰면서도 p99 tail을 DRAM급으로 지키는 것(결과: p99 1.02×, 2% 손실 — 「Service/Tail latency」 노드 참조). 즉 'tail latency'는 이 논문이 왜 필요하고 무엇으로 승패를 판정하는지 그 자체다.

내 관점(multi-host): 여러 host가 공유하는 CXL 메모리에선 cross-host coherence 왕복(back-invalidate)이 새로운 tail 원천이 된다 — 한 host의 접근이 다른 host의 무효화 완료를 기다리는 순간 꼬리가 생긴다.
Original Abstract, p.1
Modern datacenters host datasets in DRAM to offer large-scale online services with tight tail-latency requirements.
Main topic 해결책 (Solution)
AstriFlash는 두 insight로 paging의 양쪽 오버헤드를 없앤다(§III).

insight① core-side 제거 (user-level switch-on-miss): online service 응답 지연은 queuing이 지배한다. 경량 thread switch가 있으면 단일 물리 서버가 논리적 multi-server queuing(M/M/k)처럼 동작 — pending flash를 기다리는 older 요청이 서버를 비워 head-of-line blocking 제거. DRAM-cache miss 시 OS context switch가 아니라 100ns user-level thread switch로 flash 접근을 useful work와 overlap.

insight② memory-side 제거 (accelerated miss handler): OS paging은 SW(page table)·HW(TLB shootdown broadcast) 동기화 때문에 높은 miss 빈도에서 근본적으로 확장 불가. flash를 memory-map하고 관리를 hardware-managed DRAM cache(frontside/backside controller)에 캡슐화해 OS를 제거.

Fig.4 3설계: (a) OS-Swap(전통 paging, 58%), (b) Flash-Sync = FlatFlash(동기 대기, 27%), (c) AstriFlash(switch-on-miss, 95%).

구현 요소: DRAM cache 4KB page 단위(tag를 DRAM에), in-DRAM Miss Status Row(100s miss), SB speculation(ASO 확장), handler/resume register + forward-progress bit, priority scheduling with aging, DRAM flat+cached 분할(page table을 DRAM에 상주).
Original §III.A, p.3-4
AstriFlash 1) uses lightweight user-level thread switches to hide flash accesses and maintain tail-latency constraints, and 2) eliminates traditional OS paging overheads using an accelerated DRAM miss handler.

Main topic 결론 (Conclusion)
AstriFlash는 HW/SW co-designed µs-scale switch-on-miss architecture로 demand paging을 제거해, flash에서 직접 서비스하면서 DRAM-급 성능을 내고 memory cost를 20× 절감하는 미래 TB급 memory system 해법이다.

의의 & [[SkyByte]]와의 관계: '긴 저장장치 지연을 문맥 전환으로 숨긴다'는 원리를 [[SkyByte]](HPCA'25)와 공유하지만 전환의 위치·granularity가 정반대다. AstriFlash는 SSD를 black box로 두고 4KB page를 통째로 당기며, 은닉은 core 내부 user-level HW thread switch로 한다. SkyByte는 OS↔SSD 컨트롤러를 co-design해 cacheline 단위로 내려가고 coordinated context switch를 쓴다. 실제로 AstriFlash의 Flash-Sync baseline이 FlatFlash이고, SkyByte는 AstriFlash를 반례로 들어 자기 차별점을 세운다.

한계 / 열린 질문: (1) switch-on-miss·SB speculation·MSR이 전부 single-host microarchitecture 안에 닫힘 — multi-host 공유는 미해결. (2) page(4KB) granularity의 낭비(skew 강할 때) → SkyByte cacheline log가 공격. (3) SC-강제 + speculation의 검증 복잡도. (4) 저부하에선 tail이 오히려 나쁨(request 병렬성 의존).
Original §VIII, p.11
We proposed AstriFlash, a flash-based system for online services that eliminates traditional demand paging overheads by employing a hardware/software co-designed μs-scale switch-on-miss architecture.
Claim 왜 flash-as-memory인가: 50×싸고 1000×느림 + skew + 3% DRAM
AstriFlash의 경제적 전제.

- flash는 DRAM 대비 $/GB 50× 저렴, 그러나 지연 1000×(≈50µs) — 전부 flash로 바꾸면 성능 붕괴.
- online service는 ms급 SLO라 몇 µs flash 접근을 흡수 가능.
- object popularity·요청 분포가 skewed → hot fraction만 DRAM에.

분석(§II.A): CloudSuite에서 DRAM miss ratio는 DRAM이 flash의 3%에서 평탄해진다.

$$BW_{Flash} = BW_{DRAM} \times MissRate \times \frac{PageSize}{CacheBlockSize}$$

3% 기준 64코어에 60GBps flash BW 필요 → PCIe Gen5(128GBps)+다중 SSD로 충족. 채택: 1TB flash + 3%(32GB) DRAM cache → flash가 50× 싸므로 memory cost 20×↓.
Original §II.A, p.2
the miss rates flatten around 3% of DRAM capacity, which requires 60 GBps of flash bandwidth for a 64-core system ... As flash is 50x cheaper than DRAM, this configuration reduces the memory cost by 20x compared to a 1TB DRAM system.
Claim paging 오버헤드 해부: core-side(~5µs) + memory-side(>10µs)
AstriFlash 동기의 핵심 프레임 — paging 비용을 두 축으로 나눈다.

core-side (task 관리·문맥 전환): OoO가 50µs flash를 못 숨겨 OS가 page fault마다 context switch로 asynchronous 접근 제공. 각 switch ~5µs(복잡한 OS scheduling).

memory-side (flash-access 스케줄·용량 관리): page fault마다 NVMe 등 storage stack ~10µs, page 이동 후 page table 갱신, TLB 일관성 위한 global TLB shootdown — broadcast라 코어 수에 안 스케일, >10µs.

각 코어가 ~10µs마다 DRAM miss → paging 오버헤드가 throughput을 심각히 깎는다. 기존 제안은 대개 한 축만 최적화 → AstriFlash는 둘을 동시에 없앤다.
Original §II.C, p.3
modern datacenter workloads have a DRAM miss every ∼10 μs per thread accompanied by 10 μs of page fault and context switch overhead. Moreover, TLB shootdowns and OS mechanisms result in global synchronization and thus do not scale with the number of cores.

Method §III insight① user-level switch-on-miss (core-side 제거)
core-side 핵심: DRAM-cache miss 시 flash를 동기 대기하지 않고, 100ns user-level thread switch로 다른 job을 실행해 flash 접근을 overlap한다(context switch 대비 50×, 최근 제안 대비 5× 빠름).

queuing 논리: 경량 switch가 있으면 단일 물리 서버가 논리적 multi-server(M/M/k)처럼 동작 — pending 요청이 서버를 비워 head-of-line blocking 제거 → DRAM-only와 유사한 전체 응답 지연. 고부하일수록 outstanding 요청이 많아 효과 큼.

microarchitecture: miss 낸 명령(예: SB의 committed store)을 abort하고 마지막 완료 명령 상태로 core를 되돌린 뒤 scheduler 호출. 기존 switch-on-miss는 ns급 memory stall·batch(SPEC)만 다뤘으나 AstriFlash는 µs급 stall·latency-sensitive workload를 흡수. 분석: ~10µs마다 flash 접근 앱이 DRAM-only의 20% 이내에 들려면 평균 서비스 시간 40× SLO 필요.
Original §III.B, p.4
AstriFlash provides a novel μs-scale switch-on-miss architecture that allows switching user-level threads on a DRAM miss to hide flash accesses efficiently and achieve DRAM-like throughput. While switch-on-miss architectures have been studied only in the context of ns-scale memory stalls and batch workloads like SPEC, AstriFlash needs to absorb μs-scale stalls and support latency-sensitive workloads.
Method §III insight② hardware-managed DRAM cache (memory-side 제거)
memory-side 핵심: memory 관리를 OS에서 빼 hardware-managed DRAM cache에 캡슐화 → page table 수정·TLB shootdown 제거, OS page replacement를 cache eviction으로, I/O 스케줄을 HW-triggered flash 접근으로 대체.

page size 4KB: DRAM cache는 마지막 계층이라 spatial locality 지향(temporal은 희소). 64B block이면 32GB cache에 tag ~4GB로 비현실적, 4KB여도 64MB tag → SRAM 불가라 tag를 DRAM에 보관(serialized tag+data lookup).

주소변환 & DRAM 분할: PCIe BAR로 flash를 PA에 노출(PA ≡ SSD Logical Page Number). TB급 변환은 Midgard로. cold data는 page table도 flash에서 와 SLO 위반 위험 → DRAM을 flat+cached로 분할(Knights Landing식)해 page table을 항상 DRAM-resident로 유지(→ noDP 구성은 이걸 뺀 것, tail 70%↓).
Original §III.B, p.5
AstriFlash employs a hardware-managed DRAM cache to provide efficient near-DRAM capacity management and orchestration of data movement, thus eliminating the traditional OS paging overheads. Removing the explicit DRAM-capacity management in the OS also eliminates OS synchronization due to page-table modifications and TLB shootdowns.
Method §IV DRAM-cache 구조: Frontside/Backside controller + Miss Status Row
4KB page 단위 set-associative(각 DRAM row = 한 set, tag+data). 두 controller로 분리.

Frontside Controller (FC): 전통 DRAM controller 확장. 요청마다 set index(row) 계산 → RAS로 row fetch → CAS로 tag 비교(각 tag 8B, 64B tag column = 8-way). hit면 data 반환·LLC로, miss면 backside queue로(queue full이면 stall).

Backside Controller (BC): programmable(microcode/SW)라 유연한 정책. flash에 4KB read 발행(PCIe controller 경유), victim eviction(dirty면 off-critical-path write-back), 도착 시 set/way에 data+tag 설치.

Miss Status Row (MSR): on-chip SRAM MSHR은 CAM 기반이라 수십 개뿐이나, flash 지연이 길어 100s concurrent miss 필요 → 전용 in-DRAM set-associative row(각 entry 8B, CAS 검색)로 저비용 추적 + 중복 flash 요청 방지. 기존 DRAM cache 제안은 미지원.
Method §IV switch-on-miss HW/SW interface: SB speculation + forward-progress
miss signaling: FC가 miss signal을 core로(DRAM ECC error interface에 piggyback해 각 계층 MSHR 해제). ROB flush 후 PC를 handler로.

register 상태: Handler Address Register(user-level handler VA, privileged로만 write=보안) + Resume Register(user mode R/W, miss 낸 명령 PC 저장 → 나중 재개).

speculative store 되돌리기: store가 이미 retire되어 Store Buffer(SB)에 있으면 기존 speculation으로 못 abort → SC 강제될 위험. ASO[77]를 SB까지 확장해 committed store를 OS 없이 abort(store당 PRF 4개, 32-SB에 128 reg = 1KB SRAM). post-retirement speculation으로 relaxed consistency 성능 회복.

forward-progress bit: 재스케줄된 thread가 또 miss/재축출로 굶지 않게, set 시 FC에서 동기 완료 강제(deadlock/starvation 방지). core당 총 2KB = 0.001mm²(A76의 0.1%).
Original §IV.C, p.8
Based on ASO [77], we expand the speculation mechanisms already present in the ROB to cover the SB so that we can abort the "speculative" stores in case of a DRAM-cache miss.
Method §IV user-level thread lib + priority scheduling with aging
core당 32-64 user thread, 단일 global job queue, cooperative run-to-completion(단 DRAM miss 시 halt해 pending queue로). scheduler는 preempt 불가(job이 OS time quantum보다 작음).

priority scheduling: new job 우선순위 2(flash 접근을 useful work와 overlap), pending job 1. 그러나 skewed 분포에서 miss 안 나는 new job이 연속되면 pending queue starvation 가능.

aging: 각 pending job이 queue 진입 시각 기록. new job 고를 때 pending head의 나이가 평균 flash 응답시간 초과면 그것을 우선 실행 → starvation 방지. pending queue가 가득 차면 새 miss는 가장 오래된 job의 flash 응답 대기(tail 보호). 결과적으로 Flash-Sync의 이상적 latency 분포에 근접.

★ 즉 AstriFlash는 FlatFlash(27%)를 switch-on-miss로 95%까지 끌어올린다.

Gap / Idea 내 연구방향: switch-on-miss는 single-host — multi-host coherence가 빈칸
AstriFlash의 은닉 기법 — switch-on-miss, SB speculation, in-DRAM MSR, forward-progress bit — 은 전부 한 core/한 host의 microarchitecture 안에 닫혀 있다. SSD를 black box로 두는 것도 single-host라 가능하다.

내 방향(multi-node CXL coherence)에서는 stall이 cross-host로 발생한다. 여러 host가 같은 CXL/flash memory를 공유하면:
- cross-host stall: host A가 접근한 cacheline이 host B의 DRAM cache에 dirty로 있어 지연될 때, "다른 thread로 전환"만으로는 정합성이 안 잡힘 → 누가 최신본을 갖고 언제 back-invalidate하나(HDM-DB/BI) 정의 필요.
- MSR/forward-progress의 확장: single-host 구조를 어떻게 multi-host directory로?
- granularity 선택: AstriFlash의 black-box page vs SkyByte의 cacheline — 공유 시 coherence 단위와 직결.

즉 AstriFlash의 '은닉 기법'은 재사용하되 문제 정의를 single→multi host로 다시 세우는 게 gap. $\rightarrow$ [[SkyByte]], [[CXL Multi-node Coherence]], [[CXL Overview]]
