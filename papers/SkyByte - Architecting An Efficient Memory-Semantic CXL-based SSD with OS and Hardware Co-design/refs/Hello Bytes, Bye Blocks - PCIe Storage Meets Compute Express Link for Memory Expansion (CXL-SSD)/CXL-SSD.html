Main topic Killer Application
이 논문은 'CXL-SSD'라는 개념을 정립한 비전/포지션 논문이다. 값싸고 대용량인 PCIe block storage를, CXL로 host CPU에 붙여 byte-addressable working memory로 바꾸자고 논증한다.

Killer application 1 — block을 byte로, non-cacheable을 cacheable로: PCIe로 SSD 내부 DRAM을 BAR로 노출해도 x86이 그 접근을 non-cacheable로 강제해 성능이 무너진다. CXL은 cache-coherent라 이 접근을 cacheable로 만들어 storage를 메모리 계층에 편입시킨다.

Killer application 2 — 왜 Type-3인가의 논거: 세 device type 중 Type-3가 storage-integrated memory expander에 최적임을 3가지 이유(확장성·CXL.cache 오버헤드·host 허가)로 논증 → SkyByte류 CXL-SSD가 Type-3인 근거.

Killer application 3 — storage 물성을 위한 프로토콜 힌트: GC 지연·persistence를 다루도록 CXL.mem 예약 필드에 determinism/bufferability 힌트를 달자고 제안.

FPGA 투영: 고locality에서 CXL가 PCIe 대비 129.5×, 평균 3× 빠르고 DRAM에 근접.
Original §2, p.2
we advocate that CXL can open a new door that changes PCIe storage's block interface to a memory-like, byte interface.
Main topic 필요한 이유 (Why It's Needed)
PCIe storage가 byte-addressable memory가 되는 건 오랜 꿈이다(2B-SSD·NVMe가 SSD 내부 DRAM을 BAR로 노출; 내부 DRAM을 backend flash의 write-back cache로 써 긴 지연 은닉).

그런데 결정적 벽: PCIe 대역폭은 far memory로 충분(Gen5/6 16× = 63~121 GB/s)한데도, PCIe는 storage를 peripheral로 취급해 CPU가 BAR로의 `load`/`store`를 non-cacheable로 해야 한다. x86(Intel/AMD)은 PCIe 메모리 요청을 캐시하면 시스템 실패·storage 단절 위험이 있어 아예 금지한다.

결과: non-cacheable 접근이 성능을 크게 떨어뜨리고, storage-integrated memory expander가 메모리 계층에서 배제되며 CPU cache를 못 쓴다. 이게 CXL이 필요한 이유 — cache-coherent라 이 접근을 cacheable로 만든다.
Original §2, p.2
this non-cacheable characteristic severely degrades the performance of all memory accesses targeting the BARs ... enforces the storage-integrated memory expanders be excluded from the conventional memory hierarchy.
Main topic 해결책 (Solution)
PCIe storage를 CXL로 host 메모리에 편입시키되, Type-3로 하고 storage 물성을 힌트로 다룬다.

1. 세 protocol / 세 type: CXL.io(기본, PCIe·FlexBus), CXL.cache(device가 host mem 캐시), CXL.mem(host가 HDM 접근) → Type-1/2/3 정의.

2. ★ Type-3 옹호: Type-2 대비 (i) RP당 device 1개 제한 없이 확장 가능, (ii) CXL.cache 풀피처의 매 I/O cache-state 확인 오버헤드 없음, (iii) storage-side 연산의 host 허가 불필요.

3. storage-side 최소 수정: 기존 PCIe endpoint 로직 재활용 + NVMe controller를 CXL.mem read/write로 단순화 → 대부분 SSD가 minor 수정으로 Type-3 지원.

4. 시스템 통합: 부팅 시 BAR/HDM을 cacheable 시스템 메모리에 매핑, RP가 remap offset 동기화. load/store → CXL flit → controller가 firmware와 협력 서비스.

5. disaggregation & storage 힌트: switch/multi-switch/VH + MLD(16)로 multi-host 분해, determinism/bufferability로 GC·persistence 제어.
Original §3, p.3
we advocate Type 3 for a storage-integrated memory expander in CXL. There are three reasons why we believe that Type 3 devices are better than Type 2 devices for the storage-integrated memory expander.

Main topic 결론 (Conclusion)
CXL을 memory expander 관점에서 보고, block semantic을 byte semantic으로 옮기는 여러 구성을 탐색한 논문. 결론: CXL은 PCIe storage를 값싼 대용량 working memory로 편입시키는 실용적 길이며, Type-3 + storage-aware 힌트(determinism/bufferability)가 그 핵심.

의의: 'CXL-SSD' 개념의 정립 — [[SkyByte]](Type-3 memory-semantic CXL-SSD)가 이 비전을 실제 co-design으로 구현한다. determinism/bufferability(storage 물성을 host에 힌트로 노출)는 SkyByte의 coordinated context switch(긴 flash 지연을 host에 알림)와 같은 transparent co-design 사고.

한계: (1) 성능 투영이 Apex-Map 합성 + FPGA emul(실 워크로드·실 CXL 실리콘 부재). (2) determinism/bufferability는 제안일 뿐 표준·구현 미완. (3) ★ MLD는 storage를 분할해 각 host에 줄 뿐, 여러 host가 같은 영역을 coherent하게 공유하는 것은 다루지 않음(pooling≠sharing). (4) MLD 분할이 backend/internal DRAM 병렬성을 깎아 per-MLD 대역폭 저하.
Original §8, p.6
This paper examines CXL from a memory expander viewpoint and explores different configurations to transfer PCIe's block semantic to memory-compatible byte semantic.
Claim non-cacheable BAR의 벽 → CXL로 cacheable
PCIe로도 SSD 내부 DRAM을 BAR로 노출하면 byte `load`/`store`는 된다. 그러나 x86(Intel/AMD)은 PCIe 주소공간으로의 메모리 요청을 캐시하면 시스템 실패·storage 단절 위험이 있어 non-cacheable로 강제한다(BAR는 host가 storage에 '무엇을 요청/제어'하는지 알리는 인터페이스라, 캐시되면 storage가 요청 도착을 못 잡음).

결과: BAR 접근 성능이 크게 무너지고 storage-integrated expander가 메모리 계층에서 배제된다. CXL은 cache-coherent interconnect라 PCIe 주소공간으로의 load/store를 cacheable로 만들어 이 벽을 정확히 없앤다 — 이게 'CXL이 storage에 필요한' 단 하나의 핵심 이유.
Original §2, p.2
If CPU can cache/buffer the memory requests targeting the PCIe address space, there is no way for the PCIe storage to catch their arrivals. This can introduce an unexpected situation such as a system failure or storage disconnection.
Claim 초록의 coherence는 Type-1 coherence와 다른가? — 방향·주체가 다름
초록: *'CXL manages data coherency mainly between CPU memory spaces and memory on attached devices'* — 이 coherence는 Type-1의 coherence와 방향·주체가 다르다.

초록 문장은 먼저 CXL의 일반적 coherence 우산(CXL.io+.cache+.mem이 한 coherent domain)을 가리킨다. 하지만 이 논문이 CXL-SSD를 Type-3로 만들 때 실제로 쓰는 coherence는 그 우산 중 한쪽이다.

'sharing 없이도 coherence가 있나?'에서 헷갈리는 이유 — coherence는 복사본이 있으면 필요한데, 그 복사본이 한 host 안이냐 host들 사이냐로 scope가 갈린다.

Hello Bytes 초록 case(Type-3, single-host) = 왼쪽. host 캐시 ↔ device HDM 복사본은 있지만 host가 하나라 inter-host는 없음 $\rightarrow$ HDM-H(host-managed)로 자동 처리. 그래서 'sharing 없이도 coherence가 있다'가 성립(단 그건 intra-host scope).

여러 host가 같은 HDM을 공유(sharing) = 오른쪽. host A·B에 같은 라인 복사본이 생겨 inter-host coherence가 새로 켜진다 $\rightarrow$ device가 directory+back-invalidate로. pooling(독립·분할)엔 없고 sharing에만 있는 층 = 내 연구(「내 연구방향」 노드).

정밀 표현: '독립(unshared) 접근이면 coherence 불필요'는 정확히는 'inter-host(cross-host) coherence 불필요'다. intra-host coherence는 sharing 여부와 무관하게 하드웨어가 늘 본다(공짜라 안 보일 뿐). 즉 네 모델('shared되는 순간 host간 coherence를 봐야 한다')은 오른쪽 열에서 정확히 맞다.
Original Abstract, p.1
CXL manages data coherency mainly between CPU memory spaces and memory on attached devices.
Memo intra-host / inter-host란? — 'host' = 하나의 coherency domain
host = 하나의 CPU 시스템 = 하나의 coherency domain(자기 코어들 + 캐시들을 home agent가 일관되게 관리하는 단위). CXL에서 'host 하나'는 보통 하나의 CXL root port를 가진 하나의 서버/소켓 복합체다.

- intra-host(호스트 내부): 그 한 host의 경계 안 — 코어들·캐시들·그 host가 매핑한 메모리(local DRAM이든 device HDM이든). 여기 coherence는 host home agent가 자동(MESI).
- inter-host(호스트 간): 서로 다른 host들 사이 — 각자 별개 coherency domain. 이들을 잇는 선/프로토콜이 원래 없어서, 여러 host가 같은 메모리를 캐시하면 그 사이 coherence는 누군가 새로 놓아야 한다(CXL 3.0 device back-invalidate).

핵심 경계: coherence domain은 host 경계에서 끊긴다. 그래서 'intra'는 하드웨어가 늘 공짜로 처리하고, 'inter'는 CXL이 새로 풀어야 하는 문제.

일반 패턴: '한 단위 안(intra) vs 단위들 사이(inter)'라는 구분은 CXL만의 것이 아니다 — parallelism에서도 intra-node/inter-node(NVLink vs network), intra-layer/inter-layer(TP vs PP)로 똑같이 나타난다. 의미는 동일(within vs between), 표현만 다름. $\rightarrow$ Parallelism 노트 참조.
Claim byte-addressability는 오랜 꿈 + 내부 DRAM = write-back cache
PCIe storage에 byte-addressability를 주는 건 오랜 목표다 — 2B-SSD·NVMe 표준이 SSD 내부 DRAM/buffer를 BAR로 노출해 host가 local memory처럼 load/store하게 한다. 그리고 그 내부 DRAM을 backend block media(Z-NAND/Flash/Optane)의 write-back inclusive cache로 써서 긴 backend 지연을 숨긴다.

즉 하드웨어적 재료(byte 인터페이스 + 내부 DRAM cache)는 이미 있다. 빠진 것은 그 접근을 CPU cache에 태우는 것인데, 그게 바로 non-cacheable 벽(왼쪽 노드) 때문에 막혀 있었다.
Original §2, p.2
It is a long-standing dream for PCIe storage to have byte-addressability and be a part of working memory devices ... they can use the internal memory/buffer as a write-back inclusive cache of the backend.

CXL provides three different sub-protocols, i) CXL.io, ii) CXL.mem, and iii) CXL.cache, which can also define three different types of CXL devices (Type 1 ~ Type 3).
Claim ★ 왜 Type-3인가 — 3가지 이유 (vs Type-2)
저자가 storage-integrated memory expander로 Type-3를 옹호하는 3가지 근거:

(1) 확장성: Type-2는 연산집약 가속용이라 CXL RP당 device 1개만 연결 가능 → Type-3만큼 scalable하지 않다.

(2) CXL.cache 오버헤드: Type-2의 풀피처(CXL.cache+.mem)는 매 `load`/`store`가 PCIe storage 연산복합체의 cache 상태를 확인해야 해서, I/O마다 여러 CXL transaction 발생 → 성능 저하.

(3) host 허가 비용: Type-2의 CXL.cache는 host local memory와 HDM을 모두 coherent 관리하므로, storage-side 연산이 자기 메모리를 접근할 때마다 host 허가가 필요 → device I/O 성능이 오히려 악화.

→ 이게 SkyByte를 비롯한 CXL-SSD가 Type-3인 1차 논거. (우리가 대화로 정리한 'Type-2는 왜 안 되나'의 원출처.)
Original §3, p.3
only one device (per CXL RP) can be connected to a host system, which makes Type 2 devices not scalable as Type 3 devices can do.
Method Storage-side 최소 수정으로 Type-3 지원
PCIe storage는 이미 PCIe endpoint + NVMe controller로 요청을 파싱하고 데이터를 옮긴다. 따라서 Type-3 지원의 HW 변경은 작다: (a) 기존 PCIe endpoint 로직을 재활용해 CXL transaction packet formatting·CXL.io 제어, (b) 기존 NVMe controller의 command parsing·page copy 기능을 단순화해 CXL.mem read/write 인터페이스 구현, (c) firmware가 내부 DRAM + backend block media 관리. NVMe 스펙은 controller를 firmware/hardware 어느 쪽으로도 구현 가능케 하므로, CXL.mem read/write는 hardware로 자동화하고 내부 DRAM 관리는 firmware로 두는 게 낫다.
Original §3, p.3
a hardware change at the storage side can be simple, which in turn makes most storage devices easily support Type 3 with a minor modification.
Method 시스템 통합 흐름 (BAR/HDM 매핑 → flit)
부팅 시 host가 RP에 연결된 CXL device를 enumerate하고, CXL BAR + HDM 크기를 받아 cacheable 시스템 메모리에 매핑한다. HDM이 device가 원래 관리하던 주소와 다른 곳에 매핑되므로, CXL RP가 CXL controller에 remap offset을 동기화한다(target storage의 CXL capability/config 영역에 기록).

app이 HDM(=시스템 메모리)에 load/store → CXL RP가 CXL flit 생성 → CXL.mem으로 storage controller에 전달 → endpoint+CXL controller가 flit 파싱해 command·target address 추출 → firmware와 협력해 데이터 서비스.
Original §4, p.4
When an application loads or stores data on the system memory (mapped to HDM), CXL RP generates a message, called CXL flit, and sends it to the target's CXL storage controller via CXL.mem.
Method Disaggregation 3토폴로지 + MLD(16) + multi-host
storage를 컴퓨팅에서 분해하는 세 구성(Fig.3): (a) Switch(DSP→각 storage, USP→host RP; switch 레인 64~128 → 16-lane storage 4~8개), (b) Multi-switch(top switch가 host RP+하위 브리지, leaf switch가 다수 storage; network 최대 4PB), (c) Virtual Hierarchy(VH)(FM crossbar가 host↔storage 경로 기억 → 완전 분해).

Multi-host + storage 가상화: 각 storage를 MLD(multiple logical device, 최대 16)로 논리 분할, 각 MLD가 자기 HDM을 서로 다른 host에 매핑(물리 storage처럼). 단점: 대역폭 공유·트래픽 혼잡, backend/internal DRAM 분할로 병렬성·per-MLD 대역폭 저하. (우리가 정리한 MLD 논의의 원출처.)
Original §6, p.5
CXL allows a system to logically split each endpoint into multiple Type 3 devices (up to 16), called multiple logical device (MLD). Thus, we can make each MLD define its own HDM, which can be mapped to a different place of any host of system memory.
Method Storage 힌트: determinism / bufferability (+ GPF)
Type-3는 memory pooling용이라 storage 특유의 (i) latency fluctuation(GC 등 internal task), (ii) data persistence 문제가 남는다. 저자는 CXL.mem 예약 필드에 두 힌트를 달자고 제안:

- Determinism: `DT`(internal task 개입 없이 즉시 서비스) / `ND`(fire-and-forget → storage가 GC 등 스케줄 가능).
- Bufferability: `BF`(SSD 내부 DRAM에 캐시/버퍼 허용) / `NB`(persistence first-class → block media 기록).

조합(BF+DT/BF+ND/NB+DT/NB+ND) + GPF(global persistent flush)로 DB 로깅·트랜잭션·lock 시나리오 최적화(예: 로그는 BF+ND로 버퍼링, commit 시 GPF+NB+DT). loads는 대개 DT, prefetch엔 BF. storage 물성을 host가 힌트로 조종하는 co-design 사고 — SkyByte의 방향과 통한다.
Original §7, p.6
we suggest two simple features, i) determinism and ii) bufferability, which can be annotated to CXL messages and hint the host semantic to the underlying CXL controllers.
Result Apex-Map 투영: PCIe 대비 129.5×(best)/3×(avg), DRAM 근접
Apex-Map(locality $\alpha$)으로 DRAM/PCIe/CXL 비교(Fig.2):

- Best($\alpha=0.001$): 대부분 CPU cache hit → PCIe는 cache를 못 써 CXL 대비 129.5× 긴 지연. CXL ≈ DRAM.
- Average: CXL가 PCIe 대비 3× 빠름. DRAM 대비 9.3× 나쁘지만 block storage 감안 시 합리적.
- Worst($\alpha=1$, 완전 랜덤): CXL가 Z-NAND 지연을 못 숨겨 DRAM 대비 84.1× 나쁨. 그래도 PCIe 대비 1.6×(PCIe는 BAR 요청을 동기 처리).

결론: non-cacheable을 극복한 CXL은 고locality에서 DRAM급, 랜덤에서만 flash 지연 노출. §7의 힌트로 이 긴 지연을 완화할 수 있다고 주장.
Original §5, p.4
CXL is also better than PCIe by 3x for the average case. Note that, even though the performance of CXL is 9.3x worse than that of DRAM, we believe it is still in a reasonable range by considering the fact that CXL leverages the block storage.
Memo 계보/발표축: 'CXL-SSD' 개념의 정립 → SkyByte 구현
이 논문은 'CXL-SSD'라는 개념과 그 설계 좌표(Type-3, storage 힌트)를 처음 세운 글이고, [[SkyByte]]는 그 비전을 실제 co-design으로 구현한 관계다.

- 개념(여기): Type-3가 옳다 + determinism/bufferability로 storage 물성을 host에 힌트.
- 구현(SkyByte): Type-3 CXL-SSD + coordinated context switch(긴 flash 지연을 host에 알림) + cacheline write log.

determinism/bufferability와 SkyByte의 context switch는 같은 transparent co-design 사고(storage 내부 상태를 host에 노출해 함께 최적화). 내 'SSD 이중역할 × transparent co-design' 발표축의 개념적 원점 — 그리고 우리가 대화로 정리한 Type 1/2/3·MLD·pooling 논의가 전부 여기서 출발한다([[CXL Overview]]에 정리).
Gap / Idea 내 연구방향: MLD 분할(pooling) → 공유(sharing) coherence
이 논문의 multi-host는 MLD로 storage를 분할해 각 조각을 다른 host에 주는 것 — 즉 pooling(분할)이지 sharing(공유)이 아니다. 여러 host가 같은 HDM 영역을 동시에 coherent하게 쓰는 시나리오는 다루지 않는다(각 MLD는 한 host 전용).

내 방향(multi-node coherence)은 정확히 그 다음 — MLD 분할을 넘어 공유된 CXL-SSD 영역에서 host 간 캐시 일관성을 어떻게 보장할지(directory + back-invalidate, HDM-DB, CXL 3.0). determinism/bufferability 같은 storage 힌트도 공유 상황에서 누가 어떤 힌트를 세우나로 재정의된다. 즉 이 논문의 개념 프레임(Type-3·힌트·MLD)을 multi-host coherent 공유로 확장하는 게 gap. → [[CXL Multi-node Coherence]], [[CXL Overview]]
Memo 🏛️ 학회: HotStorage 2022 — 도발적 vision/position 보상, 평가 부재 관대
HotStorage는 도발적 vision/position paper를 위한 workshop이다. 완성된 평가·실측보다 새 문제 프레이밍·통찰을 보상하고 평가 부재엔 관대하되, 통찰·문제 프레이밍이 약하면 탈락한다.

이 글은 single-author 7-page position paper로, 상용 CXL 실리콘도 없던 2022년에 'PCIe block storage를 CXL로 byte-addressable memory expander로' 재정의하며 'CXL-SSD'라는 개념 좌표(Type-3 + storage 힌트)를 처음 세웠다. §1은 이 논문 전체를 4개 질문(why/how/which-type/what-to-improve)으로 프레이밍한다.

판단 축 세팅: 그래서 아래 ✅는 '개념 정립·문제 프레이밍의 날카로움' 축에서, ⚠️는 '제안일 뿐 구현·표준·실측 부재' 축에서 읽어야 한다. HotStorage taste에선 후자가 치명적 감점이 아니라 예상된 것 — position paper의 정상 범위다. 반대로 통찰이 평범했다면 여기서 떨어졌을 것.
Original Abstract, p.45
Even though CXL manages data coherency mainly between CPU memory spaces and memory on attached devices, we argue that it can also be useful to reform existing block storage as cost-efficient, large-scale working memory.
Claim ✅ 잘한 점: non-cacheable BAR의 벽을 정확히 짚고 CXL=cacheable로 압축
reviewer가 산 지점 = 문제 프레이밍의 정확성. '왜 지금껏 PCIe SSD를 memory로 못 썼나'를 대역폭 부족이 아니라 x86이 PCIe 접근을 non-cacheable로 강제하는 것으로 지목한다. 대역폭 가설은 수치로 먼저 배제(PCIe Gen5/6 = 63~121 GB/s로 far memory에 충분)하고, 그 위에서 CXL의 단 하나의 본질적 기여를 '그 접근을 cacheable로'로 압축.

이 한 통찰이 논문 전체 argument의 축이다 — §5의 129.5× 실험도 결국 'PCIe는 CPU cache를 못 쓴다'는 이 명제의 정량 증거일 뿐. HotStorage가 보상하는 '기존 문제를 새 각도로 재정의'에 정확히 부합해, 단순 CXL hype가 아니라 한 문장으로 반증 가능한 명제로 vision을 세운 게 강점.
Original §2, p.46
This non-cacheable characteristic severely degrades the performance of all memory accesses targeting the BARs ... this nature enforces the storage-integrated memory expanders be excluded from the conventional memory hierarchy and disables them from taking advantage of CPU caches.
Claim ✅ 잘한 점: Type-3 선택을 3개 구조적 논거로 정당화 (position인데 반증 가능하게)
position paper의 설득력은 '왜 이 설계점인가'를 얼마나 촘촘히 논증하느냐다. 저자는 Type-3를 선언하지 않고 Type-2와의 대비로 3개 구조적 논거를 든다: (1) 확장성(RP당 device 1개 제한), (2) CXL.cache 풀피처의 매 I/O cache-state 확인 오버헤드, (3) storage 연산의 host 허가 비용.

(논거의 *내용*은 기존 「왜 Type-3인가」 노드 소관 — 여기선 reviewer 관점만.) vision paper인데도 device type 선택을 확장성·오버헤드·허가의 세 축으로 나눠 각각 반박 가능한 형태로 못박은 점이 이 논문을 hype에서 구분한 accept 근거. 그리고 이 논증이 SkyByte 등 후속이 'CXL-SSD=Type-3'를 채택할 때 인용하는 1차 근거가 됐다(개념적 파급력).
Original §3, p.47
There are three reasons why we believe that Type 3 devices are better than Type 2 devices for the storage-integrated memory expander.
Claim ✅ 잘한 점: determinism/bufferability — vision을 실행 가능한 프로토콜 어젠다로 내림
'SSD를 memory로 쓰자'에 그치지 않고, memory pooling용 Type-3가 storage로선 못 다루는 두 물성(GC latency fluctuation, persistence)을 짚고, CXL.mem 예약 필드에 DT/ND·BF/NB 힌트를 얹자는 구체 메커니즘까지 제안한다. reviewer가 좋게 볼 지점 = vision을 '그래서 프로토콜을 이렇게 바꾸면'까지 내려 후속 연구 어젠다로 만든 것.

이 transparent co-design 씨앗(storage 내부 상태를 host에 힌트로 노출)이 곧 SkyByte의 coordinated context switch(긴 flash 지연을 host에 알림)로 이어진다 — 즉 이 노드는 논문의 '두 번째 기여 축'이자, 개념이 실제 구현으로 번지는 접점.
Original §7, p.50
we suggest two simple features, i) determinism and ii) bufferability, which can be annotated to CXL messages and hint the host semantic to the underlying CXL controllers.

reviewer 질문: §6의 'virtualize each storage device to be shared by different hosts'는 실은 각 MLD를 한 host에 전용 매핑하는 분할(pooling)이지, 여러 host가 같은 HDM 영역을 동시에 coherent하게 쓰는 sharing이 아니다. 저자 자신이 MLD 분할이 backend/internal DRAM 병렬성을 깎아 per-MLD 대역폭을 떨어뜨린다고 인정. 그렇다면 진짜 disaggregation의 핵심(공유 데이터의 host 간 일관성)이 빠져 있다 — 'shared'라는 단어가 오해를 부른다.

저자 방어: 2022년 CXL 2.0 시점엔 device-side back-invalidate(HDM-DB, CXL 3.0)가 아직 없어 host 간 sharing coherence 자체가 프로토콜 밖 — 그래서 pooling까지가 정당한 scope. → 이 누락 지점이 정확히 내 연구 gap(아래 🧭)이자 SkyByte도 single-host로 남긴 자리.

Question 🔀 왜 Type-3인가 — Type-2도 갈 수 있었는데 (역설계)
설계자라면 storage-integrated expander에 세 갈래가 있다: (A) Type-3(.io+.mem, HDM만), (B) Type-2(.io+.cache+.mem, HDM+연산), (C) Type-1.

(B) Type-2는 실제로 매력적 갈래였다 — 저자 스스로 'Type 2 can probably be a good option for utilizing HDM and/or integrating data processing capabilities into the storage'라 인정한다. computational storage(연산을 SSD로) 흐름과도 정합.

그런데 버린다: (1) RP당 device 1개→비확장, (2) 매 I/O cache-state 확인, (3) storage 연산의 host 허가. 즉 저자는 'storage side가 host CPU cache까지 coherent하게 관리할 필요는 없다'(내부 DRAM 관리 ≠ host cache coherence)는 관찰로 Type-2의 CXL.cache를 통째로 잘라낸다.

저자가 안 판 갈래(gap 후보): '연산형 CXL-SSD(Type-2)에서 확장성·허가 오버헤드를 완화하는' 방향 = computational CXL-SSD의 열린 설계공간. 좁힌 기준: 결론은 어디까지나 '순수 memory expansion 목적' 하에서만 Type-3가 dominant — 목적이 in-storage compute면 저울이 달라진다.
Original §4/§3, p.47
Type 2 can probably be a good option for utilizing HDM and/or integrating data processing capabilities into the storage by being aware of the semantics of host CPUs. In this paper, we however advocate Type 3 for a storage-integrated memory expander in CXL.
Reference 📐 P/L: 기존 PCIe BAR 접근 = non-cacheable 강제 (관점 P → 구조적 한계 L → CXL의 P″)
해법관점 (문제를 본 렌즈)결과로 남는 것
PCIe BAR expander (2B-SSD, NVMe)P: SSD를 host의 *peripheral / I/O device*로 봄 → BAR로의 memory 요청을 storage가 반드시 가로채야 함L(구조적): x86이 PCIe 접근을 non-cacheable로 강제 → CPU cache 원천 봉쇄, storage가 메모리 계층에서 배제
CXL-SSD (이 논문)P″: SSD를 host와 같은 coherent domain의 memory로 봄접근이 cacheable → CPU cache 계층에 편입, non-cacheable L 소멸

L의 핵심(성능이 아니라 관점의 귀결): 느려서가 아니다. storage를 *peripheral*로 보는 관점이면 CPU가 요청을 캐시하는 순간 storage가 요청 도착을 못 잡아 system failure / storage disconnection 위험 → 그래서 x86이 구조적으로 non-cacheable일 수밖에 없다. 관점 P를 'peripheral'→'coherent memory'(P″)로 바꾸는 것만으로 L 전체가 사라진다 — 이 논문의 novelty가 P vs P″ 대비에서 나온다는 증거.
Original §2, p.46
x86 instruction set architectures of both Intel and AMD do not allow PCIe-related memory requests to be cached at the CPU side. Unfortunately, this nature enforces the storage-integrated memory expanders be excluded from the conventional memory hierarchy and disables them from taking advantage of CPU caches.

Gap / Idea 🧭 내 연구: MLD 분할(pooling) → 공유(sharing) coherence P′
