Main topic Killer Application
SkyByte가 푸는 문제는 CXL 기반 SSD(CXL-SSD, memory-semantic SSD)를 진짜 메모리처럼 쓰려 할 때 터지는 두 가지 근본 병목을, host OS와 SSD controller의 co-design만으로 동시에 없애는 것이다. CXL-SSD는 `load`/`store`로 byte 단위 접근이 되지만, 그냥 host memory 확장으로 취급하면 (1) 긴 flash 지연이 CPU pipeline을 통째로 stall시키고, (2) byte-granular CXL과 page-granular flash 사이의 granularity mismatch(입출력 단위 불일치)가 심한 I/O amplification을 낳는다.

Killer application 1 — 사라진 context switch 기회를 되살리기: DRAM에서는 thread가 막히면 OS가 context switch로 CPU를 다른 일에 쓴다. 그런데 CXL-SSD의 `load`/`store`는 CPU에서 SSD로 직접 나가 OS가 가로챌 수 없어 이 기회가 사라진다. SkyByte는 SSD가 긴 지연을 감지해 host에 알리는 coordinated context switch(협력형 문맥 전환)로 이 기회를 복원한다.

Killer application 2 — cacheline 단위로 SSD DRAM 재설계: 대부분 워크로드가 한 page의 40% 미만 cacheline만 건드린다는 관찰에서 출발해, SSD DRAM을 cacheline 단위 write log + page 단위 read-write cache로 쪼개 flash write traffic을 극적으로 줄인다.

Killer application 3 — hot page를 host로 끌어올리는 adaptive migration: 자주 쓰는 page를 host DRAM으로 승격(promote)해 작은 SSD DRAM을 사실상 확장한다.

결과적으로 SOTA CXL-SSD 대비 평균 6.11배 성능 향상, flash write traffic 23.08배 감소, 무한 host DRAM을 가정한 ideal 대비 75% 성능에 도달한다.
Original Abstract, p.1
Our experiments show that SkyByte outperforms current CXL-based SSD by 6.11×, and reduces the I/O traffic to flash chips by 23.08× on average. SkyByte also reaches 75% of the performance of the ideal case that assumes unlimited DRAM capacity in the host.
Main topic 필요한 이유 (Why It's Needed)
CXL-SSD를 그냥 host memory의 확장으로 취급하면 극심한 성능 저하와 CPU stall이 발생한다. 저자들이 짚는 원인은 세 가지다.

(1) 긴 tail latency: flash 접근 지연이 host DRAM보다 수 자릿수 크고, SSD 내부 DRAM cache는 수 GB로 작아 miss가 나면 그 긴 지연을 그대로 맞는다.

(2) pipeline stall: out-of-place update와 garbage collection(GC, 가비지 컬렉션)이 read/write를 지연시켜 긴 CPU pipeline stall을 유발한다.

(3) granularity mismatch(입출력 단위 불일치): CXL은 byte 단위 접근을 열어주지만 flash는 page 단위만 지원해 심한 I/O amplification이 생긴다.

측정으로 뒷받침된다 — 워크로드가 DRAM 대비 CXL-SSD에서 1.5~31.4배 느려지고(Fig.2), memory-bounded cycle 비율이 DRAM의 62.9~98.7%에서 CXL-SSD에서는 77~99.8%로 치솟는다(Fig.4). 즉 CPU가 대부분의 시간을 메모리 대기에 쓴다.
Original §I, p.1
simply treating SSDs as an extension of host memory via CXL causes dramatic performance degradation and excessive CPU stalls.
Main topic 해결책 (Solution)
SkyByte는 세 컴포넌트를 host OS와 SSD controller의 co-design(공동 설계)으로 묶는다. 핵심 통찰은 CPU도 SSD도 단독으로는 어떤 명령이 긴 지연에 막혔는지 알 수 없다는 것 — 그래서 양쪽 coordination이 필수다.

1. Coordinated context switch: SSD가 DRAM cache miss로 긴 지연을 예측하면 CXL.mem NDR(No Data Response) 메시지에 새 opcode `SkyByte-Delay`를 실어 host에 알린다. host CXL controller가 MSHR·상위 cache를 뒤져 해당 명령을 찾고, 그 명령이 retire될 때 *SkyByte Long Delay Exception*을 띄워 CXL-aware scheduler로 문맥을 전환한다.

2. CXL-aware SSD DRAM 재설계: SSD DRAM을 cacheline(64B) 단위 double-buffered write log와 page(4KB) 단위 read-write data cache로 나눈다. 모든 write는 원본 page fetch 없이 log tail에 append되어 critical path에서 flash 접근을 없앤다. log가 차면 background compaction(압축)이 같은 page의 write를 coalesce해 flash write traffic을 줄인다.

3. Adaptive page migration: SSD가 page별 access count를 추적해 hot page를 PCIe MSI-X interrupt로 host DRAM에 promote하고, PLB(Promotion Look-aside Buffer)로 진행 중 migration의 일관성을 보장한다.
Original §III, p.4
Neither CPU nor SSD can by itself decide whether to trigger a context switch. Therefore, to enable context switch on long CXL-SSD memory stalls, we coordinate between host OS and SSD controller.

Main topic 결론 (Conclusion)
SkyByte는 CXL-SSD의 두 근본 문제(긴 flash 지연으로 인한 pipeline stall + byte/page granularity mismatch)를 OS-하드웨어 co-design으로 정면 돌파해, 새 메모리 매체 없이 정책·구조 개선만으로 DRAM-only ideal의 75%에 도달하면서 15.9배 저렴하다. 값싼 대용량 flash를 byte-addressable memory로 실용화하는 길을 보인 셈이다.

의의: SSD를 black box·page 단위로만 다루던 기존 접근(AstriFlash 등)과 달리, CXL.mem 프로토콜 계층까지 내려가 SSD 내부 상태(cache hit/miss, flash queue)를 host 스케줄링과 엮은 transparent co-design(투명한 공동 설계)의 모범 사례다.

한계 / 열린 질문: (1) 평가가 trace replay 기반 시뮬레이션 중심이라 full-system OS 상호작용은 부분 검증에 그친다. (2) `SkyByte-Delay` opcode와 Long Delay Exception은 CPU·CXL controller의 ISA/하드웨어 변경을 요구해 실배포 장벽이 있다. (3) data persistence를 기본 가정하지 않으며 `clwb`+page pin으로만 보장한다(pin된 page는 promote 불가 → trade-off). (4) 전 과정이 single-host 전제 — 여러 host가 한 CXL-SSD를 공유하는 multi-node coherence는 다루지 않는다.
Original §VI, p.10
SkyByte-Full costs 15.9× less than the DRAM-only setup and improves cost-effectiveness by 11.8×.
Claim OS가 CXL load/store를 가로챌 수 없다 → co-design이 유일한 길
이 논문 전체를 관통하는 통찰. 현대 OS는 host DRAM에서 thread가 막히면 context switch로 다른 thread를 돌려 CPU를 활용한다. 그런데 CXL-SSD에서는 `load`/`store` 명령이 host CPU에서 CXL 프로토콜을 통해 SSD로 직접 발행되므로, OS가 이를 intercept(가로채기)할 수 없다. 따라서 OS는 어느 명령이 긴 SSD 지연에 막혔는지조차 모른다.

CPU는 flash cache hit/miss 여부를 모르고, SSD는 그 명령이 speculative인지(나중에 squash될지) 모른다. 어느 쪽도 혼자서는 context switch를 결정할 수 없다 — 그래서 host OS와 SSD controller의 co-design이 선택이 아니라 필수가 된다.
Original §I, p.1
this context switch opportunity is missing for CXL-SSDs, because the OS cannot intercept the load/store memory instructions issued directly from the host CPU to the SSD device via the CXL protocol.
Claim 측정 근거: CXL-SSD가 DRAM 대비 1.5~31.4배 느림, memory-bounded cycle 77~99.8%
세 문제(long tail latency / pipeline stall / granularity mismatch)를 저자들은 측정으로 입증한다. 동일 워크로드가 host DRAM 대비 CXL-SSD에서 1.5~31.4배 느려진다(Fig.2). 원인을 cycle 분해로 보면, memory-bounded cycle 비율이 DRAM에서 62.9~98.7%였다가 CXL-SSD에서 77~99.8%로 올라간다(Fig.4) — CPU가 거의 항상 메모리 대기 상태다.

flash page read 지연은 약 $3\,\mu s$로, 일반적인 context switch overhead($\approx 2\,\mu s$)보다 길다. 이 부등식이 성립하기 때문에 '막힌 thread를 재우고 다른 thread를 돌리는' 전략이 순이득을 낸다 — SkyByte의 switch threshold를 $2\,\mu s$로 잡는 근거다.
Original §II, p.3
The tail latency of CXL-SSD causes severe processor pipeline stalls, leading to both performance degradation and underutilization of CPU and SSD bandwidth.
Claim granularity mismatch 근거: page의 75% 이상에서 cacheline 40% 미만만 접근
SSD DRAM을 왜 cacheline 단위로 재설계해야 하는지의 실측 근거. 대부분 워크로드가 page의 75% 이상에서 그 page 안 cacheline의 40% 미만만 접근한다(Fig.5/Fig.6). 즉 4KB page를 통째로 SSD DRAM에 caching하면 대부분의 공간이 안 쓰이는 cacheline으로 낭비되고, 그 page를 flush할 때 건드리지도 않은 부분까지 flash로 나가 write amplification(쓰기 증폭)을 키운다.

이 관찰이 곧 write log를 cacheline(64B) 단위로 두는 설계 결정으로 직결된다 — finer granularity로 (1) SSD DRAM 공간을 아끼고 (2) 더 큰 write coalescing window를 확보해 flash write를 줄인다.
Original §II, p.2
our study in §II finds that most workloads access less than 40% of cachelines in more than 75% of pages. Caching the entire page in the SSD DRAM significantly wastes precious SSD DRAM space.

Method Coordinated context switch 흐름 (C1~C4)
SSD DRAM cache miss로 긴 지연이 예상되면 SSD가 host OS에 문맥 전환을 요청한다. 4단계로 흐른다.

(C1) host CPU가 tracking 정보와 함께 CXL.mem `MemRd` 요청을 보낸다. shared LLC의 MSHR(Miss Status Holding Register)이 어느 `load`/`store`가 응답을 기다리는지 추적하고 memory access coalescing도 한다.

(C2) SSD가 cache miss를 감지하면 estimated latency로 switch 여부를 판단하고, NDR(No Data Response) 메시지의 새 opcode `SkyByte-Delay`로 '이 요청은 오래 걸린다'고 표시해 회신한다.

(C3) host CXL controller가 NDR을 받아 LLC MSHR과 L1/L2를 탐색, 이 응답을 기다리는 uncommitted 명령을 찾고 그 명령이 retire stage에 진입할 때 *SkyByte Long Delay Exception*을 트리거한다(Page Fault와 유사).

(C4) exception handler가 x86 IDT(Interrupt Descriptor Table)에 설치된 CXL-aware 스케줄링 정책을 호출해 다음 thread를 고르고 전환한다. 원래 thread가 다시 스케줄되면 막혔던 명령부터 재개한다.
Original §III-A, p.5
When the SSD detects a cache miss that will incur a long delay, it notifies the host via the NDR message so that the host OS can switch to another thread.
Method SkyByte-Delay opcode + Long Delay Exception (retire-time로 false-positive 제거)
두 개의 새 프리미티브가 핵심이다.

`SkyByte-Delay` opcode: CXL.mem의 NDR(No Data Response, slave→master) 메시지 사양을 확장해 reserved opcode를 하나 활용한다(Fig.8). 해당 `MemRd`가 긴 지연(예: SSD DRAM cache miss)을 겪을 것임을 host에 알리는 신호다. 표준 프로토콜의 여유 공간을 재활용하므로 wire format 변경이 최소다.

SkyByte Long Delay Exception: NDR 수신 후 곧바로 전환하지 않고, 대응 명령이 retire될 때만 exception을 띄운다. 이유는 speculative `load`/`store`나 하드웨어 prefetch가 결국 squash(무효화)될 수 있기 때문 — retire 시점까지 미루면 '전환했는데 알고 보니 취소될 명령이었던' false-positive context switch를 추가 하드웨어 비용 없이 제거한다. 이 깔끔함이 이 설계의 백미다.
Original §III-A, p.5
SkyByte extends the NDR message specification by introducing a new opcode called SkyByte-Delay. This opcode indicates that the corresponding MemRd request will suffer from a long access delay (e.g., an SSD DRAM cache miss).
Method 언제 전환할까: threshold-based policy (Algorithm 1)
SSD는 FTL mapping table로 PPA(Physical Page Address)를 구해 해당 flash channel queue 상태(대기 요청 수)를 조회하고, 예상 지연을 계산한다.

$$L_{est} = t_{read}\,(n_{read}+1) + t_{write}\,n_{write} + t_{erase}\,n_{erase}$$

이 $L_{est}$가 threshold보다 크면 문맥을 전환한다. 기본 threshold는 $2\,\mu s$ — flash page read 지연($\approx 3\,\mu s$)이 일반 context switch overhead($\approx 2\,\mu s$)보다 길다는 관찰에서 나온 값이다. GC로 막힌 요청은 보통 milliseconds 지속되므로 계산 없이 즉시 전환한다.

다음 thread 선택 정책은 Round-Robin / Random / CFS(Completely Fair Scheduler) 중 Linux 표준인 CFS를 기본으로 쓴다(Fig.10).
Original §III-A, p.6
The estimated latency is computed based on the number of pending requests in the flash channel queue, and a context switch is triggered if it exceeds a threshold.
Method CXL-aware SSD DRAM: cacheline write log + page data cache
SSD DRAM을 두 구조로 재구성한다(Fig.11) — cacheline(64B) 단위 double-buffered write log와 page(4KB) 단위 read-write data cache.

Write path: 모든 cacheline write는 원본 page를 먼저 fetch하지 않고 write log의 tail에 append된다(W1) → critical path에서 flash 접근이 사라진다. data cache에 그 page가 있으면 병렬로 갱신하고(W2), log index도 갱신한다(W3). 실제 flash flush는 나중에 몰아서 한다.

Read path: data cache와 write log를 병렬 lookup한다. 둘 다 miss면 flash에서 page를 읽어온 뒤 write log의 최신 cacheline을 그 위에 merge한다(R1~R3). 즉 log가 항상 최신 진실을 갖고, cache는 spatial locality를 위한 read 가속용이다.
Original §III-B, p.6
All cacheline writes are directly appended to the log without flash access along the critical path. They are flushed to the flash memory later.
Method Write log를 빠르게 뒤지기: two-level hash table
write log lookup은 hash table로 amortized $O(1)$을 노린다. 다만 평범한 단일 hash table은 '같은 page의 모든 cacheline'을 찾으려면 여러 번 lookup해야 한다 — compaction에 불리하다.

SkyByte는 인덱스를 2단으로 쪼갠다(Fig.12). 1단은 LPA(Logical Page Address)로 색인하고, 각 valid entry가 2단 hash table을 가리킨다. 2단은 그 logical flash page 안의 로그된 cacheline을 page 내 offset별로 추적한다. 덕분에 같은 page의 모든 cacheline을 한 번에 모아 compaction에서 통째로 merge할 수 있다. log index의 memory footprint는 평균 5.6MB로 가볍다.
Original §III-B, p.7
SkyByte breaks the indexing structure into two levels. At the first level, we employ a hash table indexed by the logical page address (LPA). Each valid entry points to a second level hash table that tracks all logged cache lines in this logical flash page with their offset within the page.
Method Write log compaction: double-buffered, 평균 146μs
log가 가득 차면 background compaction(압축)이 같은 page로의 write를 coalesce해 flash write traffic을 크게 줄인다(Fig.13). indexing table은 최신 갱신만 추적하므로 오래된 갱신은 자동으로 drop된다. dirty cacheline을 가진 page가 이미 cache에 있으면 바로 flush하고, 없으면 coalescing buffer로 load해 merge한 뒤 flash로 batch write한다.

double-buffered log가 핵심 — compaction이 도는 동안 들어오는 새 write는 두 번째 log가 받아내므로 incoming write가 blocking되지 않는다. 한 번 compaction은 평균 $146\,\mu s$가 걸리며, 이 비용을 background로 숨겨 critical path 밖에 둔다.
Original §III-B, p.7-8
The double-buffered design allows incoming writes to be served by the new log while the old log is being compacted, avoiding blocking.
Method Adaptive page migration + PLB로 일관성 보장
SSD가 flash page별 access count를 추적해 threshold를 넘는 hot page를 host DRAM으로 promote한다(SSD DRAM cache에 올라와 있는 page만 대상). 알림은 PCIe MSI-X interrupt로 host에 올린다.

일관성이 관건이다 — migration 도중 그 page에 접근이 오면 어디가 최신인지 모호해진다. 이를 위해 root complex에 PLB(Promotion Look-aside Buffer, 64 entry)를 두어 진행 중인 migration을 추적하고, 완료 후 OS가 PTE와 TLB를 갱신한다. host 공간이 부족하면 Linux page reclamation으로 cold page를 SSD로 evict한다. NUMA와 huge page(2MB)도 지원한다.
Original §III-C, p.8
To ensure data consistency during migration, we introduce a Promotion Look-aside Buffer (PLB) in the root complex that tracks in-flight page migrations.
Claim 왜 'DRAM 복사'를 필수로 안 하나 — 필수 paging vs 선택적 promotion
'SSD가 느리니 접근할 때 DRAM에 복사'가 자연스러워 보이는데, SkyByte는 이 복사를 없앤 게 아니라 '필수'에서 '조건부'로 바꾼다.

'복사(=paging/swap)'의 정체: 접근하려면 (1) 반드시 page를 DRAM에 복사(필수), (2) 복사 끝까지 접근이 stall(동기·critical path), (3) 64B만 필요해도 4KB 통째(page 단위).

왜 필수 복사를 버리나 — 복사는 '재사용될 때만' 이득이다
- I/O amplification: 대부분 워크로드가 page의 40% 미만 cacheline만 접근 → 4KB 옮겨 절반 이상 버림.
- thrashing: working set > DRAM이면 재사용 전에 축출 → 복사·축출 무한반복.
- 복사 비용: page promote $\approx 12.1\,\mu\text{s}$(FlatFlash 실측) vs cacheline 직접 read $\approx 4.8\,\mu\text{s}$. 한 번 쓸 데이터면 직접 접근이 압도적 이득.

→ 그래서 cold/sparse는 SSD를 직접 load/store(딱 필요한 64B만), hot page에만 복사를 건다.

Claim Thrashing은 왜 생기나 — 직접 접근이 정말 없애나?
Thrashing(스래싱)의 원리: fast memory(DRAM) 용량보다 working set(활발히 쓰는 page 집합)이 커서, page를 하나 올리면 곧 다시 쓸 page를 쫓아내는 악순환.

사이클:
1. page A 접근(DRAM에 없음) → fault → A 복사, B 축출(LRU)
2. 곧 B 접근 → fault → B 다시 복사, A(또는 C) 축출
3. WS가 안 들어가니 올린 page가 재사용 전에 축출 → fault율 거의 100%
4. 시스템이 copy-in/out 트래픽에 잡아먹혀 CPU 대기, throughput 절벽처럼 붕괴

세 조건이 겹칠 때 터진다: (a) footprint > DRAM, (b) 낮은 locality(접근이 재사용보다 빨리 흩어짐), (c) 강제·page 단위 복사. HPCC-GUPS류 대용량 random access가 전형.

swap 안 쓰면 해결되나 — 반은 맞다
- 용량 부족(footprint > DRAM) 자체는 그대로. 데이터는 여전히 느린 SSD에 있음.
- 그러나 thrashing은 '용량 부족'이 아니라 '강제 복사·축출 churn'이라는 메커니즘이다. 직접 byte 접근(복사 없이 64B read)은 올릴 page도 쫓아낼 page도 없어 악순환 자체가 성립 안 함 → thrashing 소멸.
- 성격이 바뀐다: catastrophic churn → bounded per-access SSD latency. cold/sparse는 한 cacheline 지연만 내면 됨(4KB 복사+되돌려지는 축출보다 압도적 이득).

단, promotion을 naive하게 하면 재발: hot/cold 안 가리고 접근 page를 다 promote = paging과 동일(DRAM 오염+축출 storm). FlatFlash도 *'naive ... promotes every accessed page ... can pollute the DRAM as many of these pages have low reuse'*라 명시. 그래서 adaptive threshold(재사용 빈도로 promote 결정)가 곧 anti-thrashing 장치.

한 줄: thrashing = 강제·전체page·용량초과 복사의 병리. 강제 복사를 없애면 병리의 *메커니즘*이 사라져 소멸(용량 부족은 남되 SSD 접근 지연으로 완만히 드러남). promotion은 threshold로 재발을 막는다.
Question ISA/하드웨어 변경(opcode+exception)이 실배포를 막지 않나?
SkyByte의 우아함은 곧 배포 장벽이기도 하다. `SkyByte-Delay` opcode는 CXL.mem NDR 사양 확장을, SkyByte Long Delay Exception은 CPU retire logic + x86 IDT handler 설치를, PLB는 root complex 하드웨어 추가를 요구한다. 즉 CPU 벤더·CXL 표준·SSD 컨트롤러 세 주체의 동시 협조가 필요하다.

논문은 reserved opcode 재활용으로 wire 변경을 최소화했다고 하지만, retire-time exception과 MSHR 탐색은 마이크로아키텍처 수정이라 FPGA/시뮬레이터를 넘어 상용 실리콘에 언제 실릴지는 불투명하다. '표준에 얹을 수 있는 최소 변경'과 '벤더가 실제로 넣어줄 변경'의 간극이 이 설계가 답하지 않은 지점이다.

특히 coordinated context switch는 OS 스케줄러 내부(CFS runqueue, IDT handler)와 깊게 엮이는데, 이 부분이 실제 커널에서 얼마나 매끄럽게·안전하게 도는지(예: switch storm, priority inversion, TLB shootdown 비용)는 시뮬레이션이 완전히 대변하지 못한다. adaptive migration의 access-count threshold와 PLB 용량(64 entry)이 워크로드별로 얼마나 robust한지도 추가 분석 여지가 있다.
Memo 발표 축과의 정합: SSD 이중역할 × transparent co-design
이 논문은 내 세미나 축 — SSD의 이중역할(byte-addressable memory $\leftrightarrow$ block storage) $\times$ transparent co-design — 의 거의 교과서적 사례다.

- 이중역할: 같은 flash를 CXL.mem으로 노출하면 memory, 내부적으로는 여전히 page/GC를 가진 storage다. SkyByte의 세 메커니즘은 전부 '메모리처럼 보이되 storage의 물성(page, GC, 긴 지연)을 host와 협력해 흡수'하는 장치다.
- transparent co-design: 애플리케이션은 그냥 `load`/`store`를 쓰고(투명), 그 밑에서 OS와 SSD 컨트롤러가 프로토콜(NDR opcode)·마이크로아키텍처(retire exception)·스케줄러(CFS)까지 함께 뜯어고친다.

2회차 발표로 SkyByte를 고른 이유가 여기 있다 — Smart-Infinity(near-storage compute)와 달리 SkyByte는 SSD를 메모리 계층으로 끌어올리는 쪽이라, 축의 반대편 극을 보여준다. 「결론(Conclusion)」 노드의 co-design 서사와 이어 발표하면 대비가 선명하다.
Memo 내 연구방향과의 연결: SkyByte는 single-host, 나는 multi-node CXL coherence
내 박사 방향은 메모리 시스템 아키텍처, 그중에서도 여러 host가 CXL로 공유하는 메모리의 coherence/consistency 원리다. 그 렌즈로 보면 SkyByte는 강력하지만 철저히 single-host 설계다 — CXL-SSD를 하나의 host physical memory에 통째로 매핑한 Type-3 HDM device로 노출하고, context switch도 migration도 그 한 host 안에서만 조율된다.

즉 SkyByte의 '기법'(coordinated notification, cacheline write log, hot-page promotion)은 재사용 가능하지만, '문제 정의'(single-host state/일관성)는 multi-node 공유 상황에서 다시 세워야 한다. 오른쪽 노드들에서 이 gap을 구체화한다 — write log의 최신성, promotion 일관성, NDR coordination이 여러 host가 한 CXL-SSD를 공유할 때 어떻게 깨지고 무엇을 새로 풀어야 하는지가 정확히 내 연구가 채울 자리다.
Gap / Idea 전제 노출: 전 과정이 Type-3 HDM single-host를 가정
SkyByte의 모든 메커니즘은 CXL-SSD를 한 host의 physical memory에 통째로 매핑하는 Type-3 HDM(Host-managed Device Memory) 위에 서 있다. 그래서:

- context switch는 그 host의 OS 스케줄러(CFS/IDT) 안에서만 조율된다 — 다른 host의 thread는 시야 밖이다.
- page migration은 그 host의 PTE/TLB를 갱신하며, PLB도 단일 root complex에 붙는다.
- write log의 '최신 cacheline'은 한 writer 세계를 전제한다.

여러 host가 같은 CXL-SSD를 공유 메모리 풀로 나눠 쓰는 순간, 이 전제들이 전부 재검토 대상이 된다. 논문은 이 축을 아예 열지 않는다(§Discussion의 persistence·NUMA·huge page는 전부 single-host 내부 이야기).
Gap / Idea 깨지는 지점: 공유 시 write log 최신성 · promotion 일관성
multi-host 공유에서 SkyByte의 두 핵심 구조가 직접 흔들린다.

(1) Write log의 최신성: 지금은 read가 flash page 위에 log의 최신 cacheline을 merge해 '항상 최신'을 보장한다. 그런데 host A와 host B가 같은 LPA에 각자 write를 append하면, log는 더 이상 단일 total order가 아니다 — 어느 write가 최신인지 정하려면 host 간 write serialization / coherence protocol이 필요하다. two-level hash index도 host-oblivious라 충돌을 구분하지 못한다.

(2) Promotion 일관성: hot page를 host A의 DRAM으로 promote하면, 그 순간 그 page의 '진짜 위치'는 SSD가 아니라 A의 로컬 DRAM이다. host B가 CXL.mem으로 같은 page를 읽으면 stale copy를 볼 수 있다. PLB는 in-flight migration만 추적할 뿐, promote된 뒤의 cross-host 무효화(invalidation)는 설계에 없다.
Question NDR coordination을 multi-node로 일반화할 수 있나?
SkyByte의 가장 이식성 높은 아이디어는 SSD→host 알림(informing)이다 — SSD가 내부 상태(cache miss, flash queue)를 host 스케줄링에 노출한다. 이걸 multi-node로 밀면 자연스러운 질문이 생긴다.

한 host의 `MemRd`가 긴 지연에 막혔을 때, 그 지연의 원인이 다른 host가 같은 page를 promote/lock했기 때문이라면, `SkyByte-Delay` 같은 신호에 coherence 상태(누가 소유 중인지)를 실어야 하지 않을까? 즉 NDR opcode를 'delay 있음'을 넘어 'shared/exclusive/owned' 같은 directory 상태 힌트로 확장하는 것이다.

이는 CXL 3.x의 back-invalidation / hardware coherence 방향과 맞닿는다. SkyByte가 single-host에서 보인 'retire-time에 정확히 트리거' 트릭이 multi-host directory update에서도 false-positive를 줄이는 데 쓰일 수 있는지가 파볼 지점이다.

Question 구별 실험(discriminating experiment): 무엇을 보이면 gap이 실재하나?
이 gap이 '말뿐'이 아님을 보이려면, SkyByte를 그대로 두 host가 공유하는 구성으로 확장한 뒤 cross-host 공유 페이지 비율을 축으로 스윕하는 실험이 필요하다.

측정 대상: (a) 두 host가 같은 page 집합을 read/write 공유할 때, promotion 후 발생하는 stale-read 빈도와 이를 막기 위한 invalidation traffic; (b) write log를 host별로 분리할지 공유할지에 따른 write serialization 오버헤드; (c) NDR에 coherence 상태를 실었을 때 절감되는 불필요한 stall.

baseline은 'SkyByte 그대로(coherence 무지)' vs '제안(coherence-aware NDR + cross-host PLB)'. 이득이 커지는 조건은 공유도(sharing degree)가 높고 write 충돌이 잦을수록. 남는 위험: coherence 힌트가 부정확하면 back-invalidation storm이 나므로, confidence/hysteresis 안전장치가 novelty를 얼마나 깎는지가 다음 확인 포인트다.

핵심 아이러니: swap은 page fault라는 동기 trap 덕분에 '막히면 다른 thread로 전환하는 무료 점심(context switch)'을 공짜로 누렸다. 그런데 CXL.mem은 `load`/`store`가 OS를 우회해 SSD로 직접 나가므로 그 trap 경계가 사라지고, CPU는 그냥 조용히 stall한다. SkyByte의 coordinated context switch는 결국 swap이 공짜로 갖던 이 이점을, cacheline 단위·프로토콜/하드웨어 수준에서 재구성하는 셈이다 — NDR opcode로 miss를 알리고, precise한 trap이 없으니 retire-time exception을 새로 만들어 그 경계를 복원한다.

마찬가지로 adaptive page migration $\approx$ 선택적 swap-in이다. 단, swap-in은 fault 시점에 강제로 일어나고 항상 4KB를 옮기지만, SkyByte의 promotion은 hot page만 골라 하드웨어가 트리거하고, precise fault 경계가 없어 PLB로 일관성을 따로 지켜야 한다. 정리하면 — swap은 'storage를 느린 memory로 빌려쓰되 OS가 전부 중재', CXL-SSD는 'storage가 진짜 memory 주소공간에 들어오되 그 대가로 OS의 중재 지점(그리고 context switch)을 잃음'이다.
Reference 기반: CXL Type-3 device + CXL.mem 프로토콜 (버전 명시 없음)
SkyByte가 서 있는 CXL 기반(substrate) 정리 — 논문 §II·§V·Fig.8 근거.

Device type: Type-3. SSD 전체를 HDM(Host-managed Device Memory)으로 host physical address space에 매핑해 normal physical memory처럼 노출한다. 즉 memory-expander 형태의 Type-3 device다.

사용 프로토콜: CXL.io + CXL.mem (CXL은 세 sub-protocol로 정의됨). Type별 프로토콜 조합:
TypeCXL.ioCXL.cacheCXL.mem예
Type-1OOaccelerator(NIC 등)
Type-2OOOmemory 달린 GPU/가속기
Type-3OOmemory expander (SkyByte SSD)

- CXL.io: 전통 PCIe 등가 — device discovery/config/DMA.
- CXL.mem: host가 device memory를 `load`/`store`로 직접 접근. `MemRd`(master$\rightarrow$slave, M2S)와 `NDR`(slave$\rightarrow$master, S2M)이 여기 속하며 SkyByte 메커니즘 전체가 도는 무대다.
- CXL.cache: device가 host memory를 caching(Type-1/2)하는 용도 — SkyByte는 사용 안 함.

프로토콜 확장: SkyByte는 CXL.mem NDR(No Data Response, S2M) 메시지에 reserved opcode로 `SkyByte-Delay`를 추가한 것뿐(Fig.8), 새 wire protocol을 만들지 않는다.

버전: 논문은 특정 CXL spec 버전(2.0/3.0)을 명시하지 않는다. Type-3 HDM + CXL.mem은 CXL 1.1/2.0부터 존재하는 기능이다. 여러 host가 한 device를 공유하는 것은 CXL 3.x 영역인데, SkyByte는 single-host 전제라 그쪽으로 가지 않는다 — 내 multi-node coherence 관심사와 갈리는 지점.

Claim SSD 전체가 HDM 하나로 매핑 — block/mem 경계 없음 (vs FlatFlash)
자주 나오는 오해 정리: SkyByte는 '일부는 원래 SSD(block storage), 일부는 memory'로 쪼개는 게 아니라 연결된 SSD 전체를 통째로 memory로 노출한다.

호스트 관점 — 경계 없음: 부팅 시 SSD 전 용량이 한 덩어리 flat byte-addressable 영역으로 host physical address space에 매핑된다(Fig.1a). `load`/`store`로만 접근하고, 별도 block 인터페이스로 남겨두는 부분이 없다. 즉 '전부 memory'.

flash가 전체 메모리 용량이고 SSD DRAM은 그 위 캐시일 뿐 — 호스트가 따로 주소로 보지 않는다. hot page를 host DRAM으로 올리는 것도 같은 주소의 물리 위치만 옮기는 최적화(PTE remap)지 storage/memory 구분이 아니다.

vs FlatFlash [7]: '일부 block + 일부 byte'로 두 인터페이스를 동시에 노출하는 unified memory-storage 모델은 FlatFlash 쪽이다. SkyByte는 그게 아니라 순수 memory-semantic(전체를 memory로만) — flash의 page/GC 물성은 write log·context switch로 host와 협력해 숨긴다.

persistence 뉘앙스: 기본은 persistence 미가정. 필요 시 `clwb`+page pin을 주는데, pin된 page도 여전히 memory(promote만 안 됨) — storage 영역으로 떼는 게 아니라 migration 정책의 예외.
