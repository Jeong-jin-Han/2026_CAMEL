Main topic Killer Application
이 논문은 두 개의 독립적으로 remarkable한 기여를 갖는다.

1. CXL.cache로 PCIe의 NIC I/O를 실제로 대체하는 FPGA 하드웨어 구현 — CXL 연구의 대부분이 `CXL.mem`(Type-3, 메모리 확장)에 쏠려 있는 동안 상대적으로 덜 탐구됐던 `CXL.cache`(Type-1/2)를, 소형·고빈도 패킷 통신이라는 PCIe가 가장 취약한 워크로드에 정면으로 적용한다.

2. Networking과 Application을 CXL coherence로 관통하는 co-acceleration — 단순히 NIC-호스트 통신만 빠르게 하는 게 아니라, NIC 메모리에 Key-Value Store(KVS)를 직접 얹어 host-bias/device-bias 모드를 동적으로 전환하며 hot/cold 데이터를 계층화한다. 네트워킹 계층 최적화가 애플리케이션 계층까지 투명하게 이어진다는 것이 핵심.
Original §1, p.1810
We contend that Network Interface Controllers (NICs) represent a particularly compelling, indeed a 'killer application' for harnessing the power of CXL's cache coherence.
Main topic 필요한 이유 (Why It's Needed)
PCIe 기반 NIC의 두 가지 구조적 한계가 출발점이다.

- DMA-only: load/store가 아닌 DMA만 지원 $\rightarrow$ 대량 전송엔 유리하지만 64B 디스크립터 같은 소형·고빈도 전송엔 setup/completion 오버헤드가 상대적으로 커짐
- No coherence: 호스트-디바이스 간 공유 메모리·캐시 일관성 부재 $\rightarrow$ MMIO는 512B 기준 8$\mu$s 이상의 지연, 0.3GB/s 미만의 대역폭. 소프트웨어가 explicit flush·pinning·barrier로 일관성을 직접 관리해야 함

실측 결과, 64B 패킷 기준 e2e 지연의 52%가 PCIe 연산 자체에서 발생한다(1500B에서는 45%). 이건 이미 알려진 문제였지만, 이 논문이 강조하는 진짜 사각지대는 따로 있다: CXL 연구·산업의 초점이 대부분 메모리 확장(`CXL.mem`, Type-3)에 쏠려 있어, 정작 device-to-host coherence의 핵심인 `CXL.cache`(Type-1/2)는 상대적으로 덜 탐구되어 왔다는 점이다.
Original §1, p.1810
This focus on memory expansion inadvertently overshadows the potential residing within the CXL.cache protocol, a key feature of CXL Type-1 and Type-2 devices.
Main topic 해결책 (Solution)
CXL.cache의 4가지 요청 타입(`NC-read/write`, `NC-P`, `CS-read`, `CO-read`)을 Rx/Tx 데이터패스 각 단계의 특성에 맞춰 세밀하게 배분하는 것이 핵심 설계 원리다. Type-1(온디바이스 메모리 없음) 아키텍처로 시작해 CXL.cache 자체의 순수 이점을 격리 측정하고, 그 위에 Type-2(coherent on-device memory 보유)를 얹어 버퍼 배치 자유도를 얻고, 마지막으로 Key-Value Store 애플리케이션을 통합해 networking-application co-acceleration까지 보인다 — 세 단계가 점진적으로 쌓이는 구조.

CXL-NIC leverages CXL protocols to orchestrate low-latency packet transfers between the host CPU and NIC.

Main topic 결론 (Conclusion)
CXL.cache 기반 coherence, coherent NIC memory, application co-acceleration이라는 세 축을 하나의 하드웨어-소프트웨어 co-design(CXL-NIC)으로 통합해 보였다. 저자들이 스스로 명시한 한계는 CXL 1.1의 CAS 부재(MPMC 큐 문제), 세밀하지 않은 HPA 기반 보안 모델, FPGA 클럭 제약(400MHz)에 따른 절대 수치의 하드웨어 세대 종속성이다. CXL.cache가 '메모리 확장에 가려진 저평가 영역'이라는 이 논문의 문제의식은, 단일 host-device 관계를 넘어 여러 노드·여러 디바이스가 참여하는 coherence 도메인으로 자연스럽게 이어질 수 있는 여지를 남긴다.
Original §10, p.1822
We present CXL-NIC, a novel hardware-software co-design for high-performance NIC, leveraging the great potential of the emerging CXL protocols.
Method PCIe의 두 가지 구조적 한계
- DMA-only: device-to-host memory access가 load/store를 지원하지 않고 DMA에만 의존 $\rightarrow$ setup·completion 오버헤드가 소형·고빈도 전송(예: 64B 디스크립터)에서 특히 비효율적
- No coherence: 호스트 CPU-디바이스 간 공유 메모리·캐시 일관성 부재 $\rightarrow$ CPU는 MMIO로만 디바이스 메모리 접근 가능(512B 기준 8$\mu$s 초과 지연, 0.3GB/s 미만 대역폭). 소프트웨어가 explicit cache flush, memory pinning, memory barrier로 일관성을 직접 관리해야 해 프로그래밍이 복잡해지고 지연이 추가됨

Gap / Idea CXL 연구의 사각지대: CXL.cache vs CXL.mem
CXL은 `CXL.io`/`CXL.cache`/`CXL.mem` 세 프로토콜을 제공하지만, 지금까지의 CXL 연구·산업 관심은 거의 전부 `CXL.mem` 기반 Type-3 디바이스(메모리 확장·용량/대역폭 스케일링)에 쏠려 있었다. 이 논문은 그 흐름에서 벗어나 Type-1/2 디바이스의 `CXL.cache`(device가 host의 coherence 도메인에 직접 참여하는 능력)로 연구 렌즈를 명시적으로 옮긴다는 점에서, 이 논문 자체가 하나의 gap-filling 시도다.
Original §1, p.1810
Therefore, this work shifts the research lens towards CXL Type-1 and Type-2 devices, conducting a focused exploration of the performance advantages unlocked by their inherent cache coherence support.
Method Type-1 CXL-NIC 아키텍처: DMU + PFU
Type-1 CXL-NIC(온디바이스 메모리 없음)은 네 컴포넌트로 구성된다.

- Network interface: NIC ↔ 이더넷 간 양방향 패킷 통신
- Descriptor Management Unit (DMU): RxD/TxD 검색, 패킷 버퍼 주소 추출, 전송 완료 상태 갱신
- Packet Forwarding Unit (PFU): NIC ↔ 패킷 버퍼 간 실제 패킷 이동. 버스트 트래픽 대응용 1MB SRAM 내장
- CSR/MMIO space: `CXL.io`를 통해 매핑, 초기화·런타임 설정(레거시 호환용, 드물게만 사용)

DMU와 PFU는 DCOH(Device COherence engine)에 서로 다른 포트로 접속해 디스크립터 관리와 데이터 전송 간의 경합(contention)을 원천적으로 막는다.

Method NC-P와 두 가지 완화 기법
`NC-P`(push-write)는 device가 데이터를 host LLC로 먼저 밀어넣어, 이후 host의 `ld`가 로컬 캐시 hit이 되게 하는 최적화다. Intel DDIO와 비슷한 목적이지만, 무분별하게 쓰면 LLC를 오염시켜 오히려 성능을 해친다. 두 가지 완화 기법:

- (1) Adaptive push-write gating: 런타임 설정 가능한 플래그 레지스터로, LLC 이용률이 임계치에 다가가면 host CPU가 `NC-P`를 끄고 `NC-write`로 되돌림. DDIO의 정적(static) LLC 리다이렉션과 달리 세밀한 제어 가능
- (2) Post-push write-back: `NC-P` 후 $N$ 사이클 뒤 지연된 `NC-write`를 같은 주소에 발행해 host LLC의 캐시 라인을 무효화하고 device memory로 다시 씀. $N$ 사이클 안에 host가 데이터를 접근하지 않으면 `NC-P`의 지연 이점이 사라지는 시간 트레이드오프가 있어, $N$ 값을 디바이스 레지스터로 조정 가능하게 함
Method KVS Networking-Application Co-acceleration
Key-Value Store를 Type-2 CXL-NIC 위에 직접 얹는다. NIC 메모리는 host CPU가 미리 올려둔 '핫(hot)' key-value 쌍의 부분집합을 캐싱하고, host memory는 '콜드(cold)' 데이터의 확장 가능한 백엔드 역할을 한다.

요청 처리 흐름: 키를 해싱 $\rightarrow$ hit이면 NIC 메모리의 해시 테이블을 `D2D CS-read`로 조회하고 값을 `D2D NC-read`로 읽어 로컬에서 즉시 응답(host 접근 없이, device-bias mode로 coherence 체크 자체를 생략). miss면 host-bias mode로 전환해 `D2H CO-read`로 host 데이터베이스에서 값을 가져와 응답하고, 비동기로 `D2D NC-write`를 통해 NIC 메모리에 저장하며 LRU 항목을 background swap으로 host에 되돌린다.

Memo 왜 Type-1과 Type-2를 나눠 설계했나
Type-1(메모리 없음)을 먼저 설계해 CXL.cache 자체의 순수 이점(host memory만 쓸 때도 PCIe보다 빠른가?)을 격리해서 측정하고, 그 위에 Type-2(coherent NIC memory 추가)를 얹어 '메모리를 NIC에 두면 항상 좋은가?'라는 별개 질문을 분리해서 답한다. 이 점진적 구조 덕분에 §7.2의 반직관적 결과(NIC memory 배치가 오히려 느릴 수 있다)가 명확하게 드러날 수 있었다 — 두 기여를 한 번에 섞었다면 이 결과의 원인 분리가 어려웠을 것.
Result 요청 타입 조합별 Loopback Latency
Rx/TxD/Tx 각 단계에서 쓸 CXL request type 조합 8가지(Comb. 0-7)를 비교한 결과, 전 구간에서 non-coherent `NC`만 사용하는 Comb.0이 최적이다: BF-3 대비 median 46%, p99 49%(64B) / 38%(1500B) 지연 감소.

- `NC-read`$\rightarrow$`CS-read`로 바꾸면(Tx 전송) 캐시 라인이 Shared 상태로 들어가며 coherence 트래픽이 늘어 median 17%(64B)/13%(1500B) 지연 증가
- `CO-write`는 exclusive ownership 획득 오버헤드로 15%(64B)/19%(1500B) 지연 증가
- `CO-read` 기반 TxD 폴링은 대역폭은 아끼지만 exclusiveness 획득 트래픽으로 19%(64B)/13%(1500B) 지연 페널티

결론: 데이터 이동(data movement)은 캐시-투-캐시 전송을 피하는 `NC` 요청을, 동기화(synchronization)는 대역폭을 아끼기 위한 캐시 가능(`CO-read`) 요청을 쓰는 decoupled coherence 전략이 유효하다.
Result 처리량과 배칭 효과
이론적 처리량 상한(400MHz, 64B/cycle $\rightarrow$ 204Gbps) 대비: Rx `NC-write`/`NC-P`는 90%, Tx `NC-read`는 62%만 달성 — Tx가 D2H 접근을 인터커넥트로 2회 왕복해야 하는 반면 Rx는 D2H write가 단방향(single-trip)이라는 구조적 비대칭 때문.

배칭(batch size $N$)으로 동기화 오버헤드를 패킷 여러 개에 분산시키면 격차가 크게 줄어든다: 1500B 패킷 기준 Rx는 batch=8에서 최대 처리량의 95%, Tx는 batch=32에서 88%(배칭 없이는 31%)까지 개선.
Claim 반직관적 결과: NIC memory 배치가 항상 빠르지 않다
패킷 버퍼·디스크립터를 NIC memory에 두면(L2-L4) 오히려 host memory에만 두는 L1보다 느리다: 64B/1500B 패킷 기준 L2는 23%/38%, L3는 54%/35%, L4는 71%/74% 더 높은 median/p99 지연.

원인 두 가지: (1) NIC memory 접근은 CXL 인터커넥트를 추가로 거쳐야 함, (2) host-bias 모드의 coherence 체크(host CPU와의 검증)가 D2D 접근의 공간 지역성 이점을 상쇄함. 즉 '디바이스 로컬 메모리 = 항상 빠름'이라는 직관이 coherence 오버헤드 앞에서 무너진다 — uninformed data placement가 오히려 성능을 해칠 수 있다는 저자들의 §1 경고가 실측으로 확인된 지점.
Result CC-NIC 대비 우위와 KVS 애플리케이션 성능
버퍼 배치와 request type을 함께 최적화한 latency-optimal 설계(Rx는 NIC memory, Tx는 host memory)가 CC-NIC[48] 대비 64B-1500B 구간 평균 median 37% 낮은 지연을 보인다. CC-NIC은 Intel UPI의 symmetric NUMA coherence를 가정한 설계라, 이 논문이 지적하는 hardware heterogeneity(호스트-디바이스 간 클럭·대역폭 비대칭)를 반영하지 못한다는 것이 우위의 근거.

KVS 애플리케이션 평가(SmartNIC 기반 RAMBDA[61] 방법론 사용): Zipfian 분포 read-only 워크로드에서 median 18%, p99 39% 지연 감소. 균일(uniform) 분포에서는 median이 오히려 20% 증가(p99는 변화 없음) — locality 이점이 사라지면 host memory 접근이 잦아지기 때문.
Gap / Idea CXL 1.1의 한계: CAS 부재로 인한 MPMC 문제
CXL 1.1은 Compare-and-Swap(CAS) 같은 원자적 연산을 지원하지 않는다. Tx 경로에서 여러 CXL-NIC 엔진이 동시에 shared tail index(디스크립터 링 버퍼의 head/tail)를 갱신해야 하는 Multiple-Producer-Multiple-Consumer(MPMC) 상황에서, CAS 없이는 디스크립터 중복 처리나 유실이 발생할 수 있다. 저자들은 이를 CXL 2.0+에서의 원자 연산 지원을 기다려야 하는 미해결 과제로 명시적으로 남겨둔다.

Without CAS, this coordination is unsafe, leading to potential descriptor duplication or loss.
Gap / Idea 보안·가상화의 열린 문제
CXL 디바이스는 IOMMU 없이도 Host Physical Address(HPA)를 통해 임의 host memory 영역에 DMA(H2D)나 D2H coherent access가 가능해, out-of-bound access로 인한 보안 위험이 있다. CXL 2.0의 HPA 범위 사전 지정 보호는 디바이스당 제한된 수의 영역만 지원해 세밀하지 않다. 가상화(SR-IOV)에서도 CXL 디바이스 자체가 MMU급 보호를 갖추지 못하면 hypervisor가 각 VF에 할당된 HPA 범위 필터링을 직접 에뮬레이션해야 하는 부담이 생긴다 — 두 문제 모두 실제 구현·평가 없이 'open challenge'로만 논의됨.
Reference 관련 연구 계보: CC-NIC / Dagger / Enzian
- CC-NIC[48] (ASPLOS'24): Intel UPI 기반 cache-coherent NIC 인터페이스. 이 논문의 직접 비교 baseline — symmetric NUMA coherence를 가정해 hardware heterogeneity를 반영하지 못한다는 점이 이 논문과의 핵심 차이
- Dagger[26], Enzian[7]: proprietary coherence 프로토콜 기반 host-device coherent 시스템의 선행 사례. 범용성이 떨어진다는 것이 이 논문이 CXL(open standard)을 택한 이유
- STYX[21] (ATC'23), Demystifying a CXL Type-2 Device[22] (MICRO'24): 같은 저자 그룹(Nam Sung Kim 랩)의 선행 CXL 하드웨어 실측 연구 계보 — 이 논문의 방법론적 뿌리
Memo 내 연구방향과의 연결: single-device를 넘어 multi-node coherence로
이 논문은 host 1개 ↔ CXL 디바이스 1개라는 단일 host-device coherence 관계에 철저히 국한된다 — CAS 부재로 인한 MPMC 문제조차 '단일 디바이스 내 여러 엔진 간' 문제로 스코프가 좁다. 내가 보려는 multi-node coherence는 이 스코프를 '여러 host·여러 디바이스가 하나의 coherence 도메인을 공유'하는 상황으로 넓히는 문제다. 이 논문이 증명한 'CXL.cache가 메모리 확장에 가려진 저평가 영역'이라는 프레이밍이, 노드가 여러 개로 늘어날 때도 여전히 유효한 통찰인지(혹은 완전히 새로운 원자성·프로토콜 설계가 필요한지)가 내 연구의 출발 질문이 될 수 있다.
Memo 왜 CXL+NIC은 자연스럽고 'SSD+NIC(coherence)'는 안 나오는가
CXL.cache가 어떤 워크로드와 잘 맞는지는 트랜잭션의 단위 크기와 지연 예산으로 결정된다.

- CXL.cache가 노리는 프로파일: 작고(64B 캐시라인 단위) 빈번하며, 지연 예산이 마이크로초 이하로 빡빡한 트랜잭션. NIC이 정확히 이 프로파일이다 — 패킷·디스크립터가 64B 단위이고, PCIe 연산이 e2e 지연의 45~52%를 차지할 만큼 오버헤드가 payload 크기 대비 상대적으로 크다(§3.1 실측).
- CXL.mem이 노리는 프로파일: 크고(4KB+ 페이지/블록 단위) 대용량이며, 지연보다 용량·대역폭이 병목인 트랜잭션.

SSD/flash 워크로드는 후자에 훨씬 가깝다: I/O 단위가 4KB 이상 블록이고, end-to-end 지연은 이미 flash media 자체의 접근 지연(수십~수백 $\\mu$s)이 지배적이라, PCIe DMA의 setup/completion 오버헤드(수 $\\mu$s)가 상대적으로 무시할만하다 — NIC의 64B 패킷과는 정반대 상황이다. 그래서 SSD가 CXL과 결합할 때 자연스럽게 맞아떨어지는 지점은 `CXL.cache`(세밀한 coherence)가 아니라 `CXL.mem`(Type-3, 용량 확장·메모리 시맨틱)이다 — 실제로 상용/연구용 CXL-SSD(메모리 확장형 CMM-H류, 이 vault의 Smart-Infinity·SkyByte가 다루는 CXL-연결 flash 계열)는 전부 이 경로를 택한다.

결론: 'SSD-NIC'(CXL.cache에 참여하는 coherent SSD)가 자연스럽게 나오지 않는 이유는, SSD의 자연스러운 CXL 결합처가 이미 다른 프로토콜(`CXL.mem`)로 정해져 있고, 그 결합 방식 자체가 CXL.cache가 요구하는 트랜잭션 프로파일(작고 빈번함)과 맞지 않기 때문이다. 이 논문 §1이 스스로 짚는 구도 — 'CXL.mem에 쏠린 연구(=SSD류 디바이스에 자연스러운 영역) 때문에 CXL.cache(=NIC류 디바이스에 자연스러운 영역)가 저평가됐다' — 는 사실 두 프로토콜이 애초에 서로 다른 디바이스 클래스를 겨냥하도록 설계돼 있다는 것의 다른 표현이다.
Memo NIC이란 무엇인가
NIC(Network Interface Controller/Card)는 컴퓨터(host)를 외부 네트워크(이더넷 등)에 연결해주는 하드웨어 부품이다 — 서버 메인보드의 PCIe 슬롯에 꽂히는 카드(또는 온보드 칩) 형태로, 흔히 '랜카드'라고도 부른다.

하는 일: 호스트 내부(CPU/메모리)와 외부 네트워크는 서로 다른 '언어'를 쓴다 — 호스트는 메모리 주소·바이트 배열로 데이터를 다루고, 네트워크는 이더넷 프레임(전기/광 신호)으로 데이터를 주고받는다. NIC이 그 사이를 통역한다.

- 송신(Tx): 호스트가 보낼 데이터를 메모리에 준비 $\\rightarrow$ NIC이 그 데이터를 읽어와 이더넷 패킷으로 포장 $\\rightarrow$ 케이블/광섬유로 전기·광 신호를 내보냄
- 수신(Rx): 케이블에서 들어온 신호를 NIC이 이더넷 패킷으로 복원 $\\rightarrow$ 호스트 메모리의 지정된 버퍼에 써 넣고 CPU에 도착을 알림

이 논문에서 왜 중요한가: 호스트가 패킷 하나를 보내거나 받을 때마다 반드시 NIC과 통신해야 하는데, 지금까지 그 통신 수단이 PCIe(DMA + MMIO)였다. 이 논문의 전체 주장은 정확히 이 'host ↔ NIC 통신 수단'을 PCIe에서 CXL.cache로 바꾸자는 것이다 — 즉 NIC 자체(패킷을 만들고 신호로 내보내는 기능)를 재설계하는 게 아니라, NIC이 호스트와 대화하는 방식을 재설계한다.

참고: 이 논문의 비교 대상인 BF-3(NVIDIA BlueField-3)는 'SmartNIC' — 단순히 신호를 주고받는 기본 NIC을 넘어, 자체 ARM 코어·가속기를 내장해 네트워킹 로직(패킷 처리, 가상화 등) 일부를 직접 수행할 수 있는 고급 NIC이다. 이 논문의 CXL-NIC도 FPGA 기반이라는 점에서 넓게 보면 SmartNIC 계열에 속하지만, 강조점은 '지능(compute)'이 아니라 '호스트와의 통신 방식(coherence)'에 있다.
Memo NIC 1개가 여러 원격 host/device를 동시에 상대한다
NIC 하나가 '여러 디바이스를 상대하는가'는 두 가지로 나눠 봐야 한다.

- 물리적으로: host 한 대가 NIC을 여러 장 가질 수 있다(관리망/데이터망 분리, 대역폭 aggregation, 이중화 등). 이때 각 NIC은 host 입장에서 독립된 PCIe/CXL 디바이스다 — 이 논문의 CXL-NIC도 그중 하나일 뿐, 같은 host에 다른 CXL 디바이스(GPU 등)가 동시에 붙을 수 있다.
- 기능적으로: NIC 한 장은 물리적으로 하나의 링크만 갖지만, 그 하나의 링크로 동시에 수많은 원격 host/디바이스와 패킷을 주고받는다 — 패킷 스위칭 네트워크의 본질이 이것이다. NIC은 패킷 헤더의 주소만으로 상대를 구분하지, 상대마다 별도 물리 채널을 쓰지 않는다.

즉 'NIC = host의 유일한 관문이지만, 그 관문 하나로 네트워크상의 여러 상대를 동시에 상대한다'는 게 정확한 그림이다.
Memo CXL.cache 캐싱의 진짜 원리 — device가 자기 캐시를 갖고, coherence는 '기존 복사본'에만 적용된다
(1) 오버헤드를 줄이는 진짜 메커니즘: 'host 캐시를 그때그때 device에 빌려준다'가 아니라, device가 자기 자신의 캐시(이 논문에서 HMC)를 갖고 host 메모리의 코히런트 사본을 그 안에 들고 있는다는 게 정확하다. DMA는 매번 처음부터 재전송하지만, CXL.cache로 한 번 `CS-read`/`CO-read`한 데이터는 device 로컬 캐시에 남아있고, host가 원본을 바꾸지 않는 한 재요청이 필요 없다(HMC 히트가 host 접근보다 3.3배 빠름, §4.3). Host가 원본을 바꾸면 소프트웨어가 아니라 하드웨어가 자동으로 device의 캐시를 무효화시킨다 — PCIe였다면 이 무효화 타이밍 판단을 소프트웨어가 직접(explicit flush) 했어야 한다.

(2) Coherence는 '이미 존재하는 복사본'에만 적용된다: coherence가 필요한 조건은 '같은 데이터의 복사본이 host와 device(들)에 동시에 존재하는 것'이다 — device 하나만 있어도 이미 host 사본 + device 사본 2개가 있으니 coherence가 필요하다(CPU 코어 여러 개의 L1/L2 캐시끼리 coherence가 필요한 것과 같은 원리를, CXL.cache가 device 캐시까지 확장한 것). 반대로 device가 방금 스스로 생성한 데이터(예: 네트워크에서 막 도착한 패킷)는 애초에 '지킬 기존 복사본'이 없다 — host에 원본이 있던 게 아니라 device가 처음 만든 것이므로, 이건 coherence 문제가 아니라 그냥 일회성 데이터 이동(one-shot transfer)이다.

결론: '반복 참조되는, host가 원본을 가진 데이터'(RxD 디스크립터)는 `CS-read`/`CO-read`(캐싱)로, '한 번 쓰고 끝나는, device가 새로 만든 데이터'(패킷 payload)는 `NC-write`(비캐싱)로 — 이 논문의 Rx/Tx request-type 배분 전략이 정확히 이 원리를 따른다.
Gap / Idea SSD가 CXL.cache의 device cache 역할을 못하는 물리적 이유
'캐시를 SSD에 저장한다'는 리프레이밍 자체는 개념적으로 성립하지만, 그 순간 SSD에게 CXL.cache의 device cache가 요구하는 세 조건을 동시에 만족하라고 요구하게 되는데, 셋 다 NAND flash의 물리적 본질과 정반대다.

- 속도(latency): CXL.cache의 device cache는 coherence probe/invalidation에 서브-마이크로초로 반응해야 한다(HMC 히트가 host 접근보다 3.3배 빠른 이유이기도 함). NAND flash는 read 수십~백$\\mu$s, write 수백$\\mu$s~ms, erase는 ms 단위 — coherence가 요구하는 반응속도를 원천적으로 못 맞춘다.
- 단위 크기(granularity): coherence는 64B 캐시라인 단위로 상태를 추적하는데, NAND flash의 물리적 read/write 단위는 4~16KB 페이지, erase 단위는 그보다 훨씬 큰 블록(MB급)이다. 64B짜리 트랜잭션 하나가 SSD 쪽에서는 그보다 몇백 배 큰 단위를 건드리는 극단적 write amplification을 유발한다.
- 내구성(endurance): 캐시는 원래 초당 수백만 번 덮어써져도 되는 게 정상 동작이다(SRAM/DRAM은 마모 없음). NAND flash는 셀당 P/E 사이클 수명 한계가 있어, 캐시처럼 쓰면 순식간에 마모된다.

결론: 이건 '뭐라고 부르냐(캐시 vs 저장소)'의 개념 문제가 아니라, coherence 프로토콜이 요구하는 물리적 성질(빠름·작은 단위·무한 덮어쓰기)과 NAND flash의 물리적 성질(느림·큰 단위·마모 한계)이 근본적으로 어긋난다는 하드웨어 문제다.
Memo CXL Type-1/2/3 구분 — 누가 누구를 캐싱/메모리로 쓰는가
세 타입의 차이는 프로토콜 조합보다 방향으로 이해하는 게 정확하다.
Type프로토콜핵심 동작방향
Type-1`CXL.io` + `CXL.cache`device가 자기 자신의 캐시에 host 메모리의 코히런트 사본을 들고 있음(host의 캐시를 빌리는 게 아니라 device 자체 캐시가 host 메모리를 미러링)Device가 Host를 캐싱 (D2H)
Type-3`CXL.io` + `CXL.mem`device 메모리를 host가 자기 메모리처럼(원격 NUMA 노드처럼) 접근Host가 Device를 메모리로 사용 (H2D)
Type-2`CXL.io` + `CXL.cache` + `CXL.mem`Type-1(D2H 캐싱) + Type-3(H2D 메모리) 둘 다 + device가 자기 메모리에 직접 접근(D2D)까지양방향

이 논문의 Type-1 CXL-NIC이 §4.1에서 스스로 '온디바이스 메모리 없음'이라 명시하는 것도 이 표와 정확히 일치한다 — Type-3의 핵심 요소(device memory)가 Type-1에는 애초에 없다는 뜻이다. Type-2는 이 둘의 단순 합집합이 아니라, 두 방향(D2H 캐싱 + H2D 메모리)이 동시에 성립하면서 서로 다른 데이터 배치 자유도(레이아웃 L1-L4)를 만들어낸다는 점이 실제 설계의 재미있는 지점이다.
