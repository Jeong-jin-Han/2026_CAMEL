Main topic Killer Application
GNN 서비스의 진짜 병목은 모델 연산이 아니라 전처리(graph preprocessing)다.

이 논문이 remarkable한 이유는 세 겹이다.

① 문제의 재정의 (re-framing): 대형 그래프에서 graph preprocessing이 end-to-end GNN 서비스 시간의 90.8%를 차지한다. 지금까지의 GNN 가속 연구는 aggregation/transformation(추론 연산)만 겨냥했고, 그 앞단의 데이터 준비(data preparation) 는 사각지대였다.

② 전처리 전 과정을 하드웨어로 end-to-end 자동화: graph conversion(COO $\rightarrow$ CSC 변환)과 graph sampling(이웃 표집)의 네 태스크 전부를 7nm FPGA 위에서 처음부터 끝까지 수행하고, GPU나 다른 GNN accelerator가 바로 소비할 수 있는 subgraph를 내놓는다. sampling만 가속하는 기존 FPGA 가속기와 갈리는 지점이 바로 이 전 구간(from start to finish) 이다.

③ 그래프 특성이 하드웨어를 결정한다 (hardware-driven): 전처리 병목은 그래프 크기와 시간에 따라 이동하므로, 입력 그래프를 프로파일링해 cost model로 UPE/SCR 구성을 고르고 런타임 partial reconfiguration으로 FPGA를 바꿔 낀다.

결과: conventional(CPU) 전처리 대비 최대 $9.0\times$, GPU-가속 전처리 대비 $2.1\times$ (Abstract, p.1).

Main topic 필요한 이유 (Why)
왜 GPU로는 안 되는가 — 세 가지 실측 근거.

① GPU를 써도 전처리가 남는다. DGL(Deep Graph Library)이 이미 GPU로 전처리를 최적화했는데도, 전처리는 전체 inference 시간의 평균 70%를 차지한다. 게다가 그래프가 커질수록 이 비중은 더 커진다 — 전처리 부하는 그래프 크기에 비례해 늘지만, sampling 덕분에 inference 지연은 상대적으로 일정하기 때문이다 (§III-A, p.4).

② 원인은 atomic/lock에 의한 직렬화(serialization)다. 전처리에는 counter 갱신과 map 갱신이 끼는데, 이것들은 mutual exclusion(atomic transaction, lock)을 요구한다. 논문이 재설계한 알고리즘을 CUDA 커널로 GPU에서 돌려도 평균 실행 시간의 64.1%가 직렬 구간으로 남고, GPU memory bandwidth는 평균 30.3%밖에 쓰이지 않는다 (§III-B, p.5).

③ 병목이 고정되어 있지 않다. 500K edge 미만의 작은 그래프에서는 sampling(Selecting 33.8% + Reindexing 22.1%)이 지배하지만, 수천만~수십억 edge의 큰 그래프에서는 conversion, 특히 Reshaping이 86.1%(Ordering 1.8%)로 뒤집힌다. 심지어 같은 워크로드 안에서도 그래프가 성장하면 시간에 따라 병목이 이동한다 (§III-A, p.4).

$\Rightarrow$ 고정 구성(fixed configuration)의 가속기 하나로는 전 구간을 다 잡을 수 없다는 것이 재구성형(reconfigurable) 하드웨어의 논거가 된다.

Main topic 해결책 (Solution)
알고리즘 환원 $\rightarrow$ 두 개의 재구성형 블록 $\rightarrow$ 런타임 적응. 세 층으로 쌓인 해법이다.

① 알고리즘 재설계 (§IV-A): 이질적인 네 전처리 태스크를 단 두 개의 공통 연산으로 환원한다.
- set-partitioning: 조건을 만족하는 원소를 뽑아 새 집합으로 재배치 $\rightarrow$ edge ordering(radix sort)과 unique random selection이 여기에 속한다. prefix-sum이 각 원소의 배타적 write index를 주므로 한 번의 pass로 scatter가 끝난다.
- set-counting: 조건을 만족하는 원소의 개수를 셈 $\rightarrow$ data reshaping(pointer array 생성)과 subgraph reindexing이 여기에 속한다. atomic counter와 hash map을 없앤다.

② 두 하드웨어 블록 (§IV-C):
- UPE (Unified Processing Element) = prefix-sum logic + relocation logic. set-partitioning 담당. 하나의 로직으로 edge ordering과 selection을 공유하기 때문에 UPE를 놀리지 않고 자원을 최대로 쓴다.
- SCR (Single-Cycle Reducer) = 수천 개의 comparator + adder tree(reshaper) 혹은 filter tree(reindexer). set-counting을 한 사이클에 끝내 GPU가 못 풀던 atomic 병목을 제거한다.

③ HW-shell / HW-kernel 분리와 런타임 재구성 (§IV-B, §V-B): 재구성 영역(HW-kernel: UPE 커널 + SCR 커널)과 고정 영역(HW-shell: PCIe controller, DMA, 내부 DRAM, FPP/ICAP controller)을 나누고, 미리 컴파일된 bitstream 중에서 cost model이 고른 것만 부분 재프로그램한다.



위 그림(Fig. 11)의 왼쪽이 (a) 전체 구조 — bitstream이 내부 DRAM에서 FPP controller를 거쳐 HW-kernel만 갈아끼운다는 점, 오른쪽이 (b) 호스트/GPU 인터페이스 — 대용량 COO를 scatter-gather descriptor로 끌어오는 DMA-main과, 작은 결과 subgraph를 GPU 메모리에 바로 꽂는 DMA-bypass(PCIe BAR MMIO)의 이원화다. 이 이원화가 있어야 "전처리를 통째로 가속기 안에서 끝낸다"는 Killer Application이 데이터 이동 비용에 잡아먹히지 않는다.

Main topic 결론 (Conclusion)
이 논문이 열어준 것: GNN 가속의 전선을 "모델 연산"에서 "데이터 준비"로 옮겼다. preprocessing을 critical path에서 통째로 들어내면, GPU는 자기가 잘하는 dense 연산만 하면 된다. 성능($9.0\times$ / $2.1\times$), 전력(전처리 구간 $19.7\times$ 낮은 소비전력), 비용 효율(저가 FPGA에서 $21.8\times$)이 동시에 개선된다.

방법론적 기여: "이질적인 태스크들을 공통 연산으로 환원한 뒤, 그 연산에 맞는 최소 하드웨어를 만든다"는 규칙 세우기(rule-making). set-partitioning $\rightarrow$ prefix-sum + relocation logic, set-counting $\rightarrow$ comparator + adder/filter tree. 4개의 서로 다른 태스크가 2개의 재구성형 블록으로 접힌다.

남는 것 (paper가 스스로 인정하거나 드러내는 지점):
- 전처리 결과 subgraph는 결국 명시적 transfer로 GPU 메모리에 복사된다(약 2.8 ms, end-to-end의 1% 미만). 가속기 안에서 완결되지 않는다.
- 재구성 지연 230 ms가 존재하며, 그래프가 자주 바뀌지 않으면 회수되지 않는다.
- 모델이 무거워질수록(GAT) 전처리 비중이 줄어 상대 이득이 $1.67\times$까지 좁혀진다.
- FPGA의 재구성 가능성에 의존하는 설계라, ASIC화하면 이 논문의 세 번째 기여(적응성)가 사라진다.

Method GNN preprocessing의 4-태스크 분해 (task decomposition)
이 논문의 첫 번째 기여는 "전처리"라는 뭉뚱그려진 덩어리를 네 개의 태스크로 쪼갠 것이다 (§II-B, p.3).
태스크 (task)소속환원되는 공통 연산담당 HW
Edge orderinggraph conversionset-partitioningUPE
Data reshapinggraph conversionset-countingSCR
Unique random selectiongraph samplingset-partitioningUPE
Subgraph reindexinggraph samplingset-countingSCR

각 태스크가 하는 일
- Edge ordering: edge를 destination VID 기준 1차 정렬, source VID 기준 2차 정렬. 같은 destination을 가진 edge들이 연속으로 모인다.
- Data reshaping: 정렬된 COO를 index array로 재해석하고, 새 destination VID가 나타날 때마다 시작 offset을 기록해 pointer array를 만든다. "computationally intensive하고 최적화 여지가 적다"고 논문이 명시한 부분.
- Unique random selection: 각 hop에서 $k$개 이웃을 중복 없이(uniqueness) 무작위(randomness)로 뽑는다. 보통 동기화된 dictionary(map) 조회가 낀다.
- Subgraph reindexing: 표집된 vertex들의 원본 VID를 새 VID로 재번호 매김. mutual exclusion 관리 때문에 지연이 붙는다.

분류의 의미: §II-B는 요소 수 기준으로 "대량 처리(ordering, reshaping) vs 소량이지만 빈번한 갱신(selection, reindexing)"으로 나누고, §IV는 GPU 실측으로 비병렬 구간 기여도를 selection 27.9% / reshaping 41% / reindexing 31.1%로 정량화한다. 이 분류가 있어야 "어디에 무슨 하드웨어를 붙일지"가 정해진다 — Killer Application의 ③(hardware-driven)이 여기서 출발한다.
Original §I, p.2
Our in-depth analysis classifies these tasks into parallelizable and non-parallelizable categories, enabling targeted acceleration strategies within a single preprocessing hardware architecture.
Method end-to-end 하드웨어 워크플로 (dataflow)


왼쪽(Fig. 14) — 전 구간 자동화된 dataflow: 호스트에서 받은 COO graph가 ① UPE의 edge ordering $\rightarrow$ ② SCR의 reshaping을 거쳐 CSC graph가 되고, ③ UPE의 uni-random selection $\rightarrow$ ④ SCR의 subgraph reindexing으로 COO subgraph가 나온 뒤, ⑤ 다시 한 번 edge ordering + reshaping을 통과해 최종 CSC subgraph가 된다. 여기서 결정적인 관찰: graph conversion이 두 번 돈다. 원본 그래프용 한 번, 표집된 subgraph용 한 번 — 큰 그래프에서 Reshaping이 86.1%를 먹는 이유가 바로 이 이중 변환이다.

Claim COO vs CSC — 표현 불일치(representation mismatch)가 전처리를 강제한다
COO (coordinate format, edge array): 각 edge를 (source VID, destination VID) 쌍으로 정렬 없이 저장. 갱신이 잦은 그래프에 적합하고, 저장 효율과 갱신 유연성 때문에 원본/애플리케이션 그래프는 대개 이 형태로 보관된다.

CSC (compressed sparse column): pointer array + index array의 vertex-centric 구조. pointer array의 index는 adjacency matrix의 column(= destination VID)에 대응하고, 그 값은 index array에서의 시작 offset이다. destination VID 하나를 주면 연결된 source VID들을 offset부터 다음 pointer까지 한 번에 긁어올 수 있어 graph traversal에 효율적이다.

불일치가 곧 비용: GNN 서비스의 그래프 순회는 source에서 destination을 찾아가는 형태라 CSC를 선호하는데, 저장은 COO로 되어 있다. 그래서 COO $\rightarrow$ CSC 변환이 추론 전 필수 전처리가 되고, 이것이 GNN preprocessing에서 가장 시간이 많이 걸리는 작업 중 하나가 된다.

이건 알고리즘의 결함이 아니라 두 표현의 목적이 다르기 때문에 생기는 구조적 세금이다 — 그래서 소프트웨어 최적화로 사라지지 않고, 하드웨어로 흡수하는 것이 이 논문의 선택이다.
Original §II-A, p.2
While COO is suitable for frequently updated graphs, CSC provides efficient graph traversal.
Memo 왜 GPU도 ASIC도 아니고 FPGA인가 (design rationale)
논문이 §I에서 밝히는 FPGA 선택의 논거는 정확히 두 개다.

① 전처리 연산량이 입력 그래프 특성에 따라 크게 변한다. 관계(edge)가 많은 그래프는 graph conversion에 연산이 몰리고, 규모가 작은 데이터는 graph sampling이 지배한다. 고정 하드웨어는 한쪽에 맞추면 다른 쪽에서 손해를 본다 $\rightarrow$ 재구성 가능성(reconfigurability) 이 필요하다.

② 전처리에는 복잡한 동기화가 낀 result reduction이 대량으로 있다. lock과 atomic transaction이 실행을 직렬화한다 $\rightarrow$ FPGA의 adder tree logic이면 reduction을 $O(1)$ 시간에 끝낼 수 있다.

ASIC이 아닌 이유(논문의 인정): "While FPGAs are generally slower than ASICs, AutoGNN's hardware design achieves high performance ... by fully exploiting FPGA resources" (§IV-B, p.5). 즉 절대 속도를 포기하는 대신 적응성을 산 것이다. 그래프가 정적이라면 이 트레이드오프는 성립하지 않는다 — 논문이 §III-A에서 동적 그래프 데이터를 그렇게 공들여 보여준 이유가 여기에 있다.
Original §I, p.1
FPGAs are well-suited to handle these computational dynamics by adapting to varied graph inputs and efficiently executing reduction operations. Its specialized components, such as adder tree logic, enable result reduction in O(1) time

Question atomic이 왜 "근본" 한계인가 — 알고리즘을 고쳐도 안 되는 지점
질문: set-partitioning / set-counting으로 알고리즘을 다시 짰다면, 그 자체가 이미 atomic을 줄인 것 아닌가? 그런데도 왜 GPU로는 부족한가?

논문의 답 (§IV-A, p.5): 재설계된 알고리즘도 GPU에서 가속은 되지만, 전처리를 critical path에서 완전히 들어내지는 못한다. 이유는 counter 변수와 map 구조 같은 공유 자원(shared resources) 을 여러 thread에 걸쳐 동기화해야 하고, 그것이 전 thread의 동시 실행을 제약하기 때문이다.

구조적으로 보면: GPU는 thread 수를 늘려 병렬성을 얻는 구조인데, reduction의 마지막 합류점은 결국 하나의 메모리 위치다. 반면 adder tree는 $n$개 입력을 $O(\log n)$ 깊이의 고정 배선 회로로 합치므로 합류점 경합 자체가 존재하지 않는다:

$$\text{GPU: } T \propto \frac{n}{p} + T_{\text{atomic}}(p) \qquad \text{vs} \qquad \text{adder tree: } T = O(1)\ \text{cycle (깊이 } O(\log n)\text{ 파이프라인)}$$

남는 질문: 그렇다면 GPU의 warp-level primitive(예: shuffle 기반 reduction)나 cooperative group을 극한까지 쓴 구현은 얼마나 좁힐 수 있었을까? 논문은 CUDA 커널 구현의 세부 최적화 수준을 명시하지 않는다 — 64.1%라는 숫자가 "GPU의 이론적 하한"인지 "이 구현의 값"인지는 PDF만으로는 판별되지 않는다.
Original §IV-A, p.5
These limitations arise from the need to synchronize shared resources, such as the counter variables and map structures, across multiple GPU threads, which restricts the simultaneous execution of all threads.
Method set-partitioning — prefix-sum이 write index를 준다
정의: 주어진 VID 배열을 각 원소를 평가해 두 개의 서로소 부분집합(disjoint subsets)으로 나누고, 원소를 그에 맞게 옮기는 연산 (§IV-A, p.5).

핵심 트릭: 모든 원소를 훑는 대신 prefix-sum 결과로 재배치한다. prefix-sum은 조건을 만족하는 원소를 누적 카운트해 새 배열을 만드는데, 그 값이 곧 각 원소가 출력에서 가질 배타적 write index(exclusive write index) 다. 그러므로 충돌 검사 없이 한 번의 pass로 scatter가 끝난다.

$$\text{pos}(i) \;=\; \sum_{j<i} \mathbb{1}[\,\text{cond}(j)\,] \quad\Longrightarrow\quad \text{out}[\text{pos}(i)] \leftarrow \text{in}[i]$$

두 태스크에 동시에 적용된다
- Edge ordering: prefix-sum 값이 radix bucket offset이 된다. 그래프의 VID는 수는 많아도 작고 연속된 정수 범위라는 성질 때문에 radix sort가 적합하고, radix sort의 digit-wise pass가 바로 set-partitioning이다.
- Uni-random selection: 정점을 sampled / unsampled 두 bucket으로 가른 뒤 unsampled bucket에서만 무작위로 뽑는다. 그러면 전체 공간을 훑지 않고도 uniqueness가 보장된다 (재선택 자체가 불가능해진다).

왜 이 환원이 중요한가: 성격이 전혀 다른 두 태스크(정렬 / 표집)가 같은 회로로 처리 가능해진다 $\rightarrow$ UPE 하나를 두 단계가 시분할로 나눠 쓸 수 있고, 그것이 StatPre가 LUT 활용률을 47%에서 82.2%로 올린 근거다.
Original §III-B, p.4
both edge ordering and uni-random selection can be implemented using a common operation: extracting elements that satisfy specific conditions and organizing them into a new set [8], [46], called set-partitioning in this work.
Method set-counting — atomic counter와 hash map을 지운다
정의: 집합의 모든 원소를 주어진 조건과 대조해 만족하는 개수를 세는 연산 (§IV-A, p.5).

Data reshaping에의 적용 — 관찰이 전부다: pointer array의 index는 destination VID에 직접 대응하고, 그 index의 값은 destination VID가 그 index보다 작은 원소의 수다. 그러므로 pointer array의 각 항목을 서로 독립적으로 셀 수 있다.

$$\text{ptr}[v] \;=\; \bigl|\{\,e \in E \;:\; \text{dst}(e) < v \,\}\bigr|$$

기존 방식은 정렬된 edge 배열을 훑으며 counter를 올리고 직전 edge의 destination VID를 갱신하는 것인데, 각 단계가 이전 단계에 의존하므로 순차 실행이 강제된다. set-counting으로 보면 각 pointer 항목이 동시에 계산된다.

Subgraph reindexing에의 적용: 보통 hash map으로 매핑 존재 여부를 확인하는데, hash map은 resize에 $O(n)$ 시간이 든다. 대신 (원본 VID / 재번호 VID) 두 배열을 두고, uni-random selection이 뽑은 VID를 조건으로 set-counting을 돌리면 hash map 없이 이미 재번호되었는지 판정할 수 있다.

핵심: 여기서 없어지는 것은 연산량이 아니라 의존성이다. 순차 의존을 독립 카운팅으로 바꿔놓았기 때문에 비로소 수천 개 comparator를 동시에 때릴 수 있고, 그 하드웨어가 SCR이다.
Original §III-B, p.5

Method UPE 커널 마이크로아키텍처 (Unified Processing Element)


(a) UPE 커널: UPE controller(입력/중간 결과를 scratchpad memory에 넣고 뺌) + 다수의 UPE + UPE scheduler(scoreboard로 각 UPE의 busy/idle을 추적해 데이터를 배분) 가 crossbar switch로 연결되고 scratchpad를 공유한다. UPE의 개수와 크기(width)가 모두 재구성 대상이다.

입력은 두 배열: node array(VID)와 condition array(boolean).

(b) Prefix-sum logic: condition array를 계층적 adder network에 넣어 displacement array를 만든다. 첫 layer가 배열 전·후반의 지역 합을 구하고 이후 layer들이 전파·결합한다. 깊이는 $O(\log n)$ adder layer이고, 입력이 boolean이라 각 adder의 폭은 $\log n$ bit면 충분하다. 논문은 이 하드웨어가 한 사이클에 수백 개 원소를 처리할 수 있음을 관찰했다.

(c) Relocation logic: node array는 condition array와 AND되어 조건 불만족 원소가 0으로 지워진 filtered node array가 되고, 이것이 displacement array에 따라 이동한다. 이동 거리를 2의 거듭제곱으로 분해해 $O(\log n)$ routing layer에서 단계적으로 왼쪽으로 민다. 각 multiplexer는 1-bit select만 필요하고, 데이터 폭은 정렬 대상 원소 폭과 같다 — AutoGNN에서는 VID 두 개를 담는 64 bit.

구현 규모: VPK180 기준 UPE는 최대 240 instance, 각 width 64 elements까지 구성 가능하며, FPGA가 커지면 더 늘어난다.

Killer Application과의 연결: 이 한 벌의 회로가 edge ordering의 radix pass와 sampling의 bucket 분할을 둘 다 수행한다. 하드웨어를 태스크별로 나눠 갖지 않기 때문에 FPGA 자원이 놀지 않는다.
Original §IV-C, p.6
We observed that this hardware can process hundreds of elements in a single cycle.
Method SCR 커널 마이크로아키텍처 (Single-Cycle Reducer)


(a) SCR 커널: 두 controller — reshaper(reshaping controller, COO와 중간 결과용 register 보유)와 reindexer(reindexing controller, 매핑 정보를 담는 SRAM bank 보유) — 가 AXI crossbar로 묶여 HW-shell에 단일 포트를 노출한다. 그 뒤로 개수 재구성 가능한 SCR들이 배치된다.

(b) SCR 구조: comparator logic + reducer logic.
- reshaper 모드: comparator가 입력 배열의 각 원소에서 target을 빼서 0 이상이면 양수를 출력한다(비교기 폭은 VID와 같은 32 bit). reducer는 adder tree로 그 1-bit 결과들을 합산해 CSC pointer array 값을 만든다. 동시 처리 원소 수가 $n$이면 adder 폭은 $\log n$까지 필요하다.
- reindexer 모드: reducer가 adder tree 대신 filter tree(OR gate) 다. 실제 값(재번호된 VID)과 검색 hit 여부를 함께 반환해야 하므로 폭이 $32+1$ bit다.

(c) Reindexer 동작: SRAM bank에 (원본 VID / 재번호 VID) 두 배열을 두고, SCR이 원본 VID 존재 여부를 확인한다. hit이면 재번호 VID를 반환하고, miss면 counter를 증가시켜 그 값을 새 VID로 할당하고 매핑 쌍을 SRAM에 저장한다. hash map이 사라진 자리다.

reshaper의 스트리밍 규칙: target VID 진행용 counter와 소비된 COO 원소 수 counter 두 개를 유지한다. target VID보다 엄격히 큰 COO 원소를 만나면 그 target은 완료 처리하고 다음 VID로 넘어가며, target보다 작은 COO 원소는 더 기여할 수 없으므로 소비 처리한다. 소비가 일어나면 다음 COO segment를 버퍼로 당겨온다.

왜 결정적인가: GPU가 64.1%를 직렬로 흘려보낸 그 구간(reshaping 41% + reindexing 31.1%)을 정확히 겨냥한 회로다. 수천 개 comparator가 한 사이클에 답을 내므로 atomic이 존재할 자리 자체가 없다.
Original §III-B, p.5
The SCR overcomes these challenges by utilizing thousands of comparators and an adder/filter tree to aggregate the comparator outputs in a single cycle.
Method edge ordering workflow와 merge sort (Algorithm 1)
왜 chunk로 쪼개는가: UPE는 동시에 처리하는 원소 수에 상한이 없지만, 원소 수를 늘리면 prefix-sum과 relocation logic의 깊이가 깊어져 성능이 나빠진다. 그래서 UPE controller가 COO를 UPE의 처리 용량(UPE width) 단위 chunk로 쪼갠 뒤 각 chunk에 radix sort를 돌린다.

4단계: ① Concatenation(destination VID와 source VID를 한 원소로 결합) $\rightarrow$ ② Splitting(UPE width 단위로 분할, 각 UPE가 독립 radix sort) $\rightarrow$ ③ Merging(지역 정렬된 chunk들을 UPE로 병합) $\rightarrow$ ④ Deconcatenation(다시 VID 쌍으로 분리).

Algorithm 1 (merge sorting using UPE): width $w$일 때
1. 두 정렬 배열 A, B에서 각각 가장 작은 $w/2$ 원소를 읽어 버퍼에 담고 정렬한다.
2. 버퍼 앞쪽 $w/2$개는 양쪽 배열을 통틀어 최소이므로 그대로 출력에 확정한다.
3. 버퍼에 $w/2$개가 남으므로, A와 B의 첫 원소를 비교해 더 작은 쪽에서만 새로 $w/2$개를 읽어온다.

$$\text{throughput} \;=\; \frac{w}{2}\ \text{elements per cycle}$$

전체 비용과의 연결: 이 $w/2$ 처리율이 cost function의 $\text{cycle}_{Ordering}$ 분모에 그대로 들어간다. 병합 라운드 수 $m=\log_2(e/w_{upe})-1$과 곱해져 전체 정렬 사이클이 결정된다.

Method cost function (Table I) — 어떤 bitstream을 고를지 계산한다
런타임에 호스트가 가벼운 그래프 메타데이터(node 수 $n$, edge 수 $e$)와 GNN 하이퍼파라미터(layer 수 $l$, 최대 표집 수 $k$, batch size $b$)를 모으고, 하드웨어 파라미터($n_{upe}, w_{upe}, n_{scr}, w_{scr}$)와 함께 세 개의 해석 모델(analytic model)에 넣어 미리 컴파일된 bitstream 각각의 end-to-end 지연을 추정한다 (§V-B, p.8).

Edge ordering — 병합 라운드 수 $m$, 총 작업량 $m \cdot e$를 UPE 총 처리율($n_{upe} \cdot w_{upe}/2$)로 나눈 값:

$$m=\log_2\!\left(\frac{e}{w_{upe}}\right)-1, \qquad \text{cycle}_{Ordering}=\frac{2 \times m \times e}{n_{upe} \times w_{upe}}$$

Unique random selection — UPE 하나가 step당 node 하나를 고르므로 step당 $n_{upe}$개:

$$s = b \times k^{\,l+1} - 1, \qquad \text{cycle}_{Selecting}=\frac{s}{n_{upe}}$$

Data reshaping — SCR들이 COO 배열을 병렬로 훑어 pointer array를 만들며, COO 쪽 항과 CSC 쪽 항 중 큰 쪽에 묶인다:

$$\text{cycle}_{Reshaping}=\max\!\left(\frac{n}{n_{scr}},\ \frac{e}{w_{scr}}\right)$$

두 단계 평가: ① cost 관련 그래프 파라미터 산출은 AutoGNN이 graph conversion 중에 처리하고, ② 가용 bitstream 전부에 대한 점수 매기기는 호스트 라이브러리가 한다. 비용 계산 자체는 0.1 ms 미만으로 end-to-end의 0.1%도 되지 않는다.

해석: $\max(\cdot)$ 형태가 말해주는 것 — reshaping은 SCR 개수(CSC 쪽, node 수에 비례)와 SCR 폭(COO 쪽, edge 수에 비례) 중 어느 쪽이 부족한지가 성능을 정한다. degree가 낮은 그래프(AX)는 slot 수를, degree가 높은 그래프는 slot 폭을 늘리는 것이 유리하다는 §VI-B의 실측과 정확히 일치한다.

Method graph sampling 제어 경로 (node-wise / layer-wise 모두 지원)
UPE controller가 source node들에서 $k$개를 uniqueness와 randomness를 지키며 고르는 절차다 (§V-A, p.7).

절차 (Fig. 16)
1. source node 수와 같은 길이의 index array를 만든다(각 원소가 source node의 index).
2. $k$번 반복: unsampled 집합에서 새 random index를 뽑아 그 index에 대한 one-hot condition을 만들고, UPE의 set-partitioning으로 해당 원소를 한 사이클에 추출한다.
3. controller는 bitmap을 유지해 추출된 index를 sampled로 표시한다 $\rightarrow$ 재선택이 원천 차단되어 uniqueness가 보장된다.
4. $k$개가 모이면 bitmap으로 condition array를 만들어 원본 source node 배열에 set-partitioning을 한 번 더 적용해 $k$-표집 이웃을 뽑아낸다.

두 표집 방식 모두 커버한다
- node-wise sampling: 이웃 배열마다 controller를 호출한다. 정확도가 높아 선호되는 방식.
- layer-wise sampling: 한 layer의 모든 이웃 node 배열을 하나로 합친 뒤 controller를 한 번 호출해 layer당 $k$개를 고른다. 단계 수가 적어 빠르다.

자원 재사용의 묘: 이 selection에 쓰이는 UPE는 edge ordering에 썼던 바로 그 UPE다. 두 단계가 데이터 의존 때문에 어차피 순차로 실행되므로, 같은 하드웨어를 시분할하면 놀고 있는 UPE가 없어진다 — StatPre가 AutoPre보다 빠른 이유가 이 한 문장이다.

To support layer-wise sampling methods [15], [39], [88], [102], all neighbor node arrays of a layer are first aggregated together as a single array; the UPE controller is then called for the aggregated array, selecting k nodes per layer.

Method 소프트웨어 스택 — DGL 개조, AGNN-lib / AGNN-drv, DMA 경로
DGL(Deep Graph Library)을 수정해 AutoGNN을 상용 GPU 기반 GNN inference 서비스에 끼워 넣었다. 인터페이스는 DGL과 동일하게 유지하고, `updategraph()`와 유사한 `uploadgraph()` 같은 그래프 관리 함수만 추가했다 (§V-B, p.8).

두 컴포넌트
- AGNN-lib (user-level library): ① 그래프 I/O 관리, ② 하드웨어 재구성 여부 판단(cost function 평가 후 지연이 임계치를 넘으면 최적 UPE/SCR 프로파일 쌍의 key를 AutoGNN에 전달), ③ 전처리 태스크를 위한 AutoGNN과의 상호작용.
- AGNN-drv (kernel driver): `pci_ioremap_bar()`로 DMA-main 인터페이스를 잡고, 그래프 데이터에 대한 scatter-gather list용 PCIe descriptor를 만들어 그 주소를 DMA-main에 쓴다. AutoGNN이 descriptor를 참조해 그래프를 직접 끌어온다.

GPU와의 결정적 차이: GPU는 모델 추론 중에 그래프 데이터셋을 해제해야 하므로 매 전처리 pass마다 호스트에서 전체 그래프를 다시 가져와야 한다. AutoGNN은 이전 그래프를 디바이스 메모리에 유지할 수 있어서 갱신된 부분만 읽어오면 된다. 대신 전처리된 subgraph를 GPU로 옮기는 추가 이동이 생기는데, 이미 표집된 subgraph라 원본보다 훨씬 작아(평균 $1230\times$) 약 2.8 ms, end-to-end의 1% 미만이다.

해석: 하드웨어 이득이 소프트웨어 통합에서 새는 것을 막는 장치들이다 — 인터페이스 호환성(DGL), 데이터 이동 최소화(증분 갱신), 그리고 재구성 판단의 자동화(cost function). Killer Application의 "end-to-end"는 회로만이 아니라 이 스택까지 포함해야 성립한다.

§VII의 위치 선언: GNN 가속기는 GPU 프레임워크, FPGA 구현, ASIC 설계로 많이 나왔지만 전부 추론에 집중하고 전처리 오버헤드를 무시했다. sorting, format processing, sampling을 겨냥한 가속기들도 있지만 자원 대부분을 단일 기능에 쏟아 end-to-end 전처리에는 부적합하다는 것이 AutoGNN의 차별점 주장이다.

Gap / Idea 마지막 2.8 ms — 전처리는 가속기 안에서 끝나지 않는다
AutoGNN은 전처리를 한 장치 안에서 끝내지만, 그 결과물인 sampled subgraph는 결국 GPU 메모리로 명시적으로 복사되어야 한다. 논문이 제시하는 수치: 전송 지연 약 2.8 ms, end-to-end의 1% 미만(Fig. 20 기준으로는 잔여 전송 오버헤드 0.6%), subgraph가 원본보다 평균 $1230\times$ 작기 때문에 무시할 수준이라는 논리다.

그런데 이 논리가 성립하는 조건은 (a) 표집률이 충분히 낮아 subgraph가 작고, (b) 추론이 별도 장치(GPU)에서 일어난다는 것이다. layer 수나 $k$가 커져 subgraph가 커지면 이 항은 다시 자란다 — 실제로 §VI-B는 layer를 1에서 6으로 늘리면 sampling 지연이 $51.1\times$ 커진다고 보고한다.

열린 아이디어(논문 밖 · 검증되지 않음): 이 전송이 PCIe DMA 복사이기 때문에 남는 비용이라면, 가속기와 GPU가 주소 공간을 공유하는 인터커넥트 위에서는 복사 대신 참조로 바뀔 수 있는가? 이 논문은 PCIe(DMA-main / DMA-bypass) 기반이고 coherent interconnect를 다루지 않으므로, 이는 논문의 주장이 아니라 독자의 질문이다. 판단하려면 (i) subgraph 크기 대비 전송 대역폭, (ii) GPU 커널이 subgraph를 소비하는 접근 패턴(순차 스트리밍인지 무작위인지)을 먼저 봐야 한다.
