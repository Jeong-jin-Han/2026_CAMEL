# 2.1 Prefetcher Ensemble — 실험 기록

## 논문 원문

> A prefetcher ensemble is typically composed of multiple time-proven hardware prefetchers as *sub-prefetchers* as well as an *orchestration layer*. The orchestration layer manages the sub-prefetchers and make the whole ensemble expose the same interface like only one single prefetcher.

> A prefetcher's interface includes the demand requests as inputs (for training the prefetcher) and an output port where the prefetch requests are been issued from.

> When multiple, distinct prefetchers are combined into an ensemble, a dedicated orchestration layer is required to manage their **interactions and resource contention**.

> this orchestration layer is responsible for making two fundamental decisions: 1) When a demand request arrives, which one or more sub-prefetchers should this demand request be routed to as shown in Figure 2(a)? 2) When one or more sub-prefetchers issue prefetch requests, which request or requests should be selected to issue to the next level of the memory hierarchy as shown in Figure 2(b)?

> an ill-suited selection degrades performance by **evicting useful cache data** and **wasting memory bandwidth**.

## 읽어낸 구조

### "training"은 ML이 아니다
마이크로아키텍처 어휘. prefetcher가 demand 스트림을 지켜보며 내부 상태를 갱신하는 것. branch predictor를 training한다고 말할 때와 같은 뜻. 논문은 이 단어를 두 의미로 쓴다 (§2.1 = 마이크로아키텍처, §4.2/§5.3 = ML). Pythia[6]만 두 의미가 겹침(진짜 RL).

세 번째 힌트(demand request filtering)의 존재 이유가 이 단어다 — §4.4: *"protecting its internal state from irrelevant training information."*

### interface ≠ orchestration layer
- **interface** = prefetcher **하나**의 계약. 포트 2개 (입력=demand, 출력=prefetch request). 함수 시그니처.
- **orchestration layer** = prefetcher가 **여럿**일 때 그 포트들을 조율하는 기계. Router(Fig 2a) + Mux(Fig 2b). 호출자.

**포트가 둘이라서 결정이 둘이다.** interface 정의가 "two fundamental decisions"의 근거.

### 두 포트 ↔ 세 힌트 (§4.4, Fig 3c)
| 힌트 | §4.4 원문 | 통제 지점 |
|---|---|---|
| Selection (4bit) | *"permitted to **issue** prefetch requests"* | 출력 = Mux (Fig 2b) |
| Demand Filtering (2bit) | *"prevents the demand request from being **sent to**"* | 입력 = Router (Fig 2a) |
| Degree (2bit) | *"passed directly to the selected sub-prefetcher to control its aggressiveness"* | 상자 내부 |

세 힌트는 임의 선택이 아니라 **통제 표면 전체**. interface에 포트가 둘뿐이니 그 이상 통제할 게 없음.

### 자원 경합의 실체 (Table 3)
| 자원 | 값 | 다투는 주체 |
|---|---|---|
| **MSHR** | L1D **16개** | 모든 prefetcher + demand miss |
| 캐시 용량 | 64KB 4-way | prefetcher끼리 + demand 라인 |
| 발행 경로 | L1D→L2 (Mux) | 동시 발행하는 prefetcher들 |
| 메모리 대역폭 | DRAM single channel, 1 rank | 전부 |

**핵심 숫자**: §5.1 — DSPatch aggressive = `round(0.75 × 64) = 48`. **prefetcher 하나가 트리거 한 번에 48개를 당기는데 MSHR은 16칸.** 혼자서 3배 초과 구독.

**경합에서 지는 쪽이 정해져 있음**: MSHR이 차면 demand miss는 stall(버릴 수 없음), prefetch는 **드롭**(비구속 힌트). prefetch가 항상 진다.

**Mux/Router의 존재 자체가 경합의 물증** — 다 보낼 수 있으면 "selected"할 이유가 없다.

## 실험: orchestration 없는 다중 prefetcher는 실물로 존재하는가

**Intel CPU에 이미 박혀 있다.** MSR `0x1A4` (`MSR_MISC_FEATURE_CONTROL`), disable 비트:

| bit | prefetcher |
|---|---|
| 0 | L2 streamer |
| 1 | L2 adjacent cache line |
| 2 | DCU (L1 next-line) |
| 3 | DCU IP (L1 IP-based stride) |

**넷이 독립 토글로 동시에 돈다.**

> 주의 — **"이들 사이에 orchestration이 없다"는 문서화된 사실이 아니라 추론.** Intel은 prefetcher 내부를 공개하지 않음. 근거는 (a) 독립 토글 4개, (b) 조율 메커니즘이 문서에 없음, (c) 서로 간섭한다는 게 업계 상식 — 이 셋뿐. 반증 불가.
> 또한 Alder Lake는 저 넷보다 prefetcher가 더 많음(Golden Cove 추가분, 별도 MSR). 저 넷은 클래식 4종이지 전부가 아님.

**확인할 원전**: Intel SDM Vol. 4 (Model-Specific Registers) → `1A4H` / `MSR_MISC_FEATURE_CONTROL`, family 6 model 151(0x97) 항목. 동작은 Intel Optimization Reference Manual의 "Data Prefetching" 챕터.

## 실행 방법

### 안전성 — 먼저 읽을 것

**망가뜨릴 수 없습니다.**

- **MSR은 휘발성입니다.** 재부팅하면 무조건 초기값(전부 ON)으로 돌아옵니다. 영구 변경이 불가능합니다.
- `0x1A4`는 Intel이 **문서화한 정식 손잡이**입니다. 최악의 결과는 "컴퓨터가 느려짐"이고, `wrmsr -a 0x1a4 0x0` 한 줄이면 즉시 복구됩니다.
- 단 하나 주의: **손으로 끄고 복구를 잊으면 기계가 느린 채로 남습니다.** 재부팅하거나 복구 명령을 치면 끝입니다. `run_pf.sh`는 Ctrl+C를 눌러도 자동 복구(trap)합니다.

### 0. 폴더로 이동

```bash
cd "/media/hanjeongjin/T7/Workspace/Obsidian/2026_CAMEL/papers/PF-LLM - Large Language Model Hinted Hardware Prefetching/PPT/Notes/exp/background"
```

### 1. 지금 prefetcher 상태 보기 (읽기만, 완전 안전)

```bash
sudo modprobe msr          # 이미 로드돼 있으면 아무 일 없음
sudo rdmsr -a 0x1a4
```

12줄(코어 0~11)이 나옵니다. **전부 `0`이면 prefetcher 4종이 다 켜져 있다**는 뜻입니다 (disable 비트니까 0 = 안 껐음).

### 2. 아무것도 안 건드리고 한 번 돌려보기 (sudo 불필요)

```bash
taskset -c 2 ./pf_bench line 2
taskset -c 2 ./pf_bench chase 1
```

`taskset -c 2` = 코어 2번에 고정. 스케줄러가 코어를 옮겨다니면 숫자가 흔들리니까.

감 잡는 단계입니다. `line`은 몇 ns, `chase`는 몇 ns 나오는지 눈으로 보면 됨.

### 3. 손으로 껐다 켜보기 — 여기가 실험의 본질

```bash
# 끄기
sudo wrmsr -a 0x1a4 0xf
sudo rdmsr -p 2 0x1a4              # 확인: f 나와야 함

taskset -c 2 ./pf_bench line 2     # 껐을 때

# 반드시 복구
sudo wrmsr -a 0x1a4 0x0
sudo rdmsr -p 2 0x1a4              # 확인: 0 나와야 함

taskset -c 2 ./pf_bench line 2     # 켰을 때
```

**이 두 줄의 차이가 전부입니다.** prefetcher 하나 껐다 켠 것 말고 아무것도 안 바뀌었으니, 시간 차이는 순수하게 prefetcher가 한 일입니다.

`0xf` = `0b1111` = bit 0~3 전부 1 = 네 개 다 disable.

### 4. 네 패턴 자동 대조

```bash
sudo ./run_pf.sh
```

ON/OFF × 네 패턴을 다 돌고 `perf` 카운터까지 찍습니다. **`page`가 500패스라 몇 분 걸립니다.**

빨리 보려면 패턴을 골라서:
```bash
sudo PATTERNS="line chase" ./run_pf.sh
```

코어를 바꾸려면:
```bash
sudo CORE=4 ./run_pf.sh
```

### 출력 읽는 법

```
line    passes=10   accesses=335544320   loop=   0.853 s      2.54 ns/acc
      cycles                   3123456789
      instructions             2012345678
```

- **`ns/acc`** ← 1차 지표. ON/OFF 비교는 이걸로.
- **`L1-dcache-load-misses`** ← 메커니즘. **시간도 안 변하고 miss도 안 변하면 → prefetcher가 애초에 그 패턴에서 아무 일도 안 하고 있었다는 뜻.**

### 문제가 생기면

| 증상 | 원인 / 해결 |
|---|---|
| `rdmsr: CPU 0 cannot read MSR` | `sudo modprobe msr` |
| `perf: Permission denied` | `perf_event_paranoid=4`. `sudo`로 실행 |
| 숫자가 매번 크게 흔들림 | 주파수 스케일링. `sudo cpupower frequency-set -g performance` 후 재시도 |
| prefetcher를 끈 채로 잊음 | `sudo wrmsr -a 0x1a4 0x0` 또는 그냥 재부팅 |

### 실험 위생

- **여러 번 돌릴 것.** 한 번은 데이터가 아님.
- 코어 2의 **HT 형제(보통 CPU 8)**가 놀고 있어야 깨끗함.
- 무거운 프로그램(브라우저 등) 꺼두면 L3 경합이 줄어듦.
- 시간의 **절대값**이 아니라 **ON/OFF 비**를 볼 것. 비를 보면 주파수 변동이 상쇄됨.

### 측정 범위의 한계 (중요)
**`0xf`는 prefetcher를 전부 끈 게 아니다.** MSR `0x1A4`가 통제하는 **4종만** 끔. Alder Lake(Golden Cove)에는 그 외 prefetcher가 더 있고 별도 MSR로 제어됨.

따라서 정확한 진술:
- ~~"prefetcher를 끄면 20% 느려진다"~~
- **"MSR 0x1A4의 4종을 끄면 20% 느려진다" → 1.20×는 하한선.**

인용 시 이 단서 필수.
