---------------------
이 절에서 우리는 PF-LLM의 핵심 설계 선택들의 근거를 깊이 파고들고, prefetching 기법들의 더 넓은 지형 안에서 
그 위치를 분석한다. 먼저 입력 매체로 어셈블리 코드를 택한 우리의 전랴적 선택을 정당화하며, 소스 코드에 비해 그것이 갖는 보편성과 
런타임 동작과의 긴밀한 정합성을 부각한다. 다음으로, PF-LLM을 Profile-Guided Optmization (PGO) 및 전통적 소프트웨어 prefetching과 
대조하여, 우리의 하이브리드 접근법이 어떻게 입력 변이(input variation)에 대한 견고성(robustness)을 달성하면서 명령어 주입
(instruction injection)의 오버헤드를 피하는지 강조한다.
그런 다음 서로 다른 명령어 집합 아키텍쳐 (ISA)와 머신 구성에 걸친 우리 프레임워크의 일반화 가능성(generalizability)을 평가한다.
마지막으로, JIT 컴파일과 ASLR에 관한 현재의 한계를 다루고, 미래의 HW-SW co-design을 위한 LLM guided 마이크로아키텍쳐의 더 넓은 
함의를 탐구하여 마무리한다.

# 7.1 입력에 대해서 어셈블리 코드와 소스 코드의 비교 (PF-LLM)
우리 PF-LLM은 binary 실행 파일에서 직접 추출(strip)한 어셈블리 코드를 입력으로 받는다. 우리가 PF-LLM의 입력으로 
어셈블리 수준을 택한 것은 그 보편성 (university)와 컨텍스트의 복잡도를 관리하는 능력 때문이다. 
첫째, 소스 코드나 중간 표현(IR)은, 특히 폐쇄 소스 binary의 경우, 항상 이용 가능한 것은 아닌다. 
둘때, 바이너리 실행 파일에서 코드를 직접 추출하는 것이 절차 간 (inter-procedural) 호출 관계를 깨뜨리는 것처럼 보일 수 있으나, 
컴파일러는 호출 친화도가 높은 함수들을 명령 캐시 성능 향상을 위해 인접한 메모리 영역에 배치하는 경우가 많다. 이 덕분에 함수 경계를 고려하지 않고
직접 추출한 우리 컨텍스트도 함수 간 정보를 포착할 수 있다. 반대로 함수 인라이닝(inlining)이나 루프 언롤링(unrolling)은 컨텍스트 길이를 지수적으로 증가시켜, 
우리 LLM이 고정된 컨텍스트 길이 안에서 의미 있는 semantic 패턴을 포착하기 어렵게 만든다. 마지막으로, 우리는 어셈블리 코드가 런타임 컨텍스트와 가장 가깝게 
합한다고 믿는다. 추가적인 간접 (indirection) 충돌은 LLM이 입력 추상화와, 런타임 컨텍스트에 직접 관련된 출력 힌트 사이의 매핑을 학습하기 더 어렵게 만든다. 
그럼에도, 우리 실험은 어셈블리 코드가 LLM이 효과적인 힌트를 생성하기에 충분히 표현력이 있음을 확인한다.

# 7.2 SW prefetching vs Profile-Guided Optimization prefetching vs HW prefetching -> 용어가 맞는지 확인해보기
PGO(Profile-Guided Optimization) 대비 PF-LLM의 핵심 이점은 입력 데이터 변이에 대한 견고성이다.
PGO는 특정 입력으로 하는 프로파일링 실행에 의존하는데, 그 입력이 배포 binary에 대해 정적이긴 하지만, 우리의 전체 접근법은 런타임 환경에 
적응력이다. 선행 연구[4]와 일관되게, 우리는 메모리 접근 패턴이 주로 프로그램 코드에 의해 결정됨을 발견했으며,
이는 주어진 load 명령의 패턴이 여러 실행에 걸쳐 코드의 semantic을 대체로 반영함을 의미한다. 우리의 
충분히 큰 컨텍스트 윈도우 덕분에, PF-LLM은 서로 다른 입력 의존적-분기 의존적 경우들을 포착하고 구분할 수 있다. 선택된 prefetcher는 남은 데이터 입력 
의존적 변이를 처리하기 위해 런타임 데이터로부터 계속 학습할 수 있다. 우리 작업의 핵심 기여는 offline 힌트 생성과 online prefetcher 선택 사이의 인지 
(semantic-aware, context aware) 힌트로 하여금 동적 런타임 적응적 하드웨어를 안내하게 된다.

더 나아가, Figure 6과 7에서 보이듯, 소프트웨어 prefetch[1]는 하드웨어 prefetchcing 기법에 비해 저조한 성능을 보인다. 이는 명령 스트림에 
prefetch 명령을 직접 주입하는 순수 소프트웨어 기반 접근법의 한계를 부각한다. 그러한 접근법은 런타임 메모리 접근 패턴에 대한 가시성이 제한될 뿐 아니라, 명령
수를 증가시켜 코어의 front-end에 추가 오버헤드를 유발한다.
(cf. -> 코어의 front end가 정확히 무엇을 의미하는 거지? 어떤 오버헤드를 유발한다는 것이지?)

# 7.3 Generalizability and Robustness
ISA 의존성: 우리 평가는 x86-64에 집중하지만, PF-LLM의 방법론은 ISA-agnostic이다.
서로 다른 ISA에 대해, 우리 모델은 특정 대상 ISA에 적응하도록 재학습되거나 fine-tuning될 수 있다.

머신 구성 의존성: 최적 prefetching 정책은 cache 크기나 대역폭 같은 마이크로아키텍처가 파라미터에 따라 달라질 수 있다. 
우리의 현재 모델은 특정 구성에 대해 학습되었으나, 프레임워크는 확장 가능하다. 다양한 하드웨어를 지원하기 위해, 모델은 
서로 다른 구성의 데이터로 재학습되거나, 하드웨어 파라미터를 LLM에 추가 프롬프트로 포함시켜 구성 인지 (configuration-aware) 힌트를 생성하게 할 수 있다.
우리는 CPU 벤더가 PF-LLM 모델을 공급할 것으로 전망하는데, 그들은 자사 플랫폼에 맞는 PF-LLM 모델 학습용 데이터를 생성할 상세 지식과 정확한 
시뮬레이터를 보유하기 때문이다. 향후 연구는 또한 prefetch hinting을 위해 다양한 머신 구성에 적용 가능한 단일의 일반화 모델을 학습하는데 집중할 수 있습니다.
(cf. CPU 벤더가 PF-LLM 모델을 공급하더라도 사용할 수 있는 이유? : 파라미터 수가 적어서, inference매우 빠르고 가벼울 듯)

# 7.4 한계점 
우리는 현재 PF-LLM 구현의 두 가지 주요 한계를 인정한다.
첫째, PF-LLM은 정적 binary 분석에 의존하기 대문에, JIT 컴파일 요구하는 프로그램이나 어떤 중간 바이트코드 위에서 실행되는 프로그램을 네이티브로 지원하지 못한다. 
그러나 이는, 런타임 전에 이용 가능한 정적 중간표현 (IR)을 분석하도록 우리 접근법을 확장하여, IR로부터 힌트를 생성하는 별도의 LLM 모델을 학습시킴으로써 해결될 수 있다.
둘째, 우리의 현재 프로토타입은 주소 공간 배치 무작위화 (ASLR)를 고려하지 않는다. PF-LLM은 정적 Program Counter (PC)로 인덱싱된 힌트를 생성하므로, 런타임 무작위화가 
힌트와 명령 사이의 매핑을 깨뜨릴 수 있다. 이는 hinting 메커니즘을 OS 로더와 통합함으로써 해결될 수 있다. 코드 세그먼트에 적용되는 것과 동일한 무작위화 오프셋을 hint 테이블에도 
적용하면, hint와 런타임 PC 사이의 대응이 보존될 수 있다.

(cf. 만약에 IR을 사용하게 된다면 compiler마다 IR이 다를텐데 오히려 어셈블리 언어는 clossed된 binary에 대해서도 가능했는데 범용성이 더 떨어지는 것 아닌가?JIT만을 위한 것을 의미하는 것일까?
ASLR에서 OS로더와 통합함을써?, OS로더는 무엇이며 hint와 런타임 PC 사이의 대응이 보존될 수 있다는 말이 무슨 말이지?)

# 7.5 Implication (영향과 가치)
PF-LLM의 성공은 LLM-guided 마이크로아키텍처라는 더 넓은 패러다임을 시사한다. 우리는 LLM을 사용해 정적 코드 컨텍스트를 offline에서 이해하는 이 근본적 접근법이, 다른 동적 하드웨어
메커니즘에도 가치있는 안내를 제공할 수 있다고 믿는다. 향후 연구는 이 co-design 방법론을 다른 고전적 난제들에 적용하는 predictor에 힌트를 제공하거나, 데이터 재사용 (data reuse) 특성을 추론하여
더 지능적인 cache 교체 (replacement) 및 삽입 (insertion) 정책에 정보를 줄 수 있다. 이 방향은, LLM의 깊은 분석 능력을 활용하여 런타임 하드웨어의 효율을 높이는 새로운 부류의 
hybrid 하드웨어-소프트웨어 co-optimization을 약속한다.

            Q. segment가 무엇을 의미하는가? 

                A.
                segment = 프로그램 메모리를 성질별로 나눈 큰 구획

                왜 나누는가? 성질이 다르면 권한도 다르기 때문에
                    .text       기계어         RX     
                    .rodata     상수           R     
                    .data/.bss  전역변수        RW    
                    stack/heap  지역변수/동적할당 RW      

                    Q. 왜 code는 쓰기 금지이고 data는 실행 금지인가?

                        A. 
                        데이터 segment에 공격 코드를 심어도 실행 권한이 없어서 못 돌립니다. (stack에 저장된 return address는 쓰기가능해서 buffer overflow공격이 가능함)
                        segment 분리가 모안 경계

                        JIT가 특별한 이유는 
                        쓰기 + 실행 권한을 동시에 얻는 특수 메모리를 만든다.

                        A.
