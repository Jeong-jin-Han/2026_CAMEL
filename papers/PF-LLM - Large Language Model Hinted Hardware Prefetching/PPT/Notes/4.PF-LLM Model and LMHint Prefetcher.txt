# 4.1 PF-LLM 모델 아키텍처
PF-LLM 모델은 정적 코드 context를 분석하기 위해 디자인되었고 
런타임 prefetcher를 위한 힌트를 제공한다. 
이 아키텍쳐에 대해 설명하고 input과 output의 서식을 묘사한다.

------------
모델 아키텍처 
기존의 파운데이션 모델의 내재된 광범위한 지식을 이용하기 위해서 
본 연구는 사전 훈련된 코딩에 특화된 LLM을 fine-tune했다. 

prefetching이라는 작업이 고도로 특화된 작업이기에
작은 모델은 충분한 용량을 제공하면서도 더 빠른 훈련을 가능하게 하고
더 작은 GPU 메모리 공간을 요구한다. 

이용가능한 모델의 리뷰를 한 후, Qwen-2.5-Coder-0.5B-Instruct [16]를 선택했다.
사이즈와 우리의 요구 사항에 잘맞고
SOTA 코딩 역량을 가지고 있는 ->  Qwen-2.5-Coder-0.5B-Instruct

우리의 실험은 이 모델에 대해서 
기본 모델 아키텍처를 변경하지 않고
prefetching 데이터셋에 대해서 fine tune하고 

------------
입력
PF-LLM은 문자열을 입력으로 받는다,
우리의 경우 타켓 load 명령어에 둘러싼 어셈블리 코드 컨텍스트를 입력으로 한다.

소스 코드 또는 IR (LLVM IR)을 사용될 수 있는 반면  <- 왜 어셈블리 언어야 하는가?
우리는 정적 binary 실행 파일을 가진 어떤 프로그램에도 우리의 접근법이 적용가능하도록 보장하기 위해서 
어셈블리 코드를 선택했다.

정적 binary는 어셈블리 코드로 쉽게 disasseble할 수 있는 반면
binary에서 소스 코드로 복구하는 것은 종종 어려운 일이다.

주어진 load 명령어의 코드 컨텍스트를 
그 앞에 있는 128개의 어셈블리 라인과 그 뒤에 있는 128개의 라인 
(총 257개의 어셈블리 코드 라인)으로 구성하도록 설정한다.


------------
출력
모델은 online prefetcher를 위한 힌트 집합을 생성한다.
3가지 힌트 유형

prefetcher selection hint
주어진 load 명령어에 대해서 prefech 요청을 발행하기 위해 
ensemble 내에서 어떤 sub prefetcher를 사용해야 하는지 지정하는 정수 인덱스이다.

prefetcher degree hint 
선택된 prefetcher의 적극성을 조절하기 위한 정수
degree에 대한 해석은 sub prefetcher에 특정된다. 하지만
높은 값은 항상 더 적극적인 정책을 나타낸다.
만약에 선택된 prefetcher가 prefetch degree 조절을 지원하지 않는다면 해당 힌트는 사용되지 않음 
(cf. 여기서 각주, 더 자세한 것은 Table 2에 나와있다.)

demand request filtering hint 
load 명령어에서 비롯된 demand 요청을 받지 않아야 할 서브 prefetcher 를 지정해준다.
관련없는 demand 요청을 필터링하는 것은 특정 sub prefetcher의 내부 상태 업데이트 바뀌는 것의 노이즈를 줄일 수 있다.
이 방식은 선행연구[22]에서도 사용되어왔다.
이 힌트는 optional로 모든 load instruction에서 제공하는 것은 아닌다.

# 4.2 PF-LLM Prompt Formatting and training
PF-LLM 모델을 fine-tuning학는 것은 어셈블리 코드 context와 그것에 대응되는 정답 prefetching policy로 구성된 대규모 데이터를 필요로 한다.
우리는 이 데이터셋을 ChampSim 아키텍처 시뮬레이터[15]를 사용해 생성하는데, 이것은 널리 쓰이고 시뮬레이션 속도가 빨라서 선택했다.

우리의 데이터셋 생성은 벤치마크 프로그램 모음으로 시작된다.
각각의 벤치마크마다 sub prefetcher와 prefetcher degree의 모든 unique 조합에 대해에 대해 별도의 ChampSim 시뮬레이션을 실행했다.
ChampSim 시뮬레이터를 수정하여 unique PC로 식별된 모든 load 명령어에 대해 AMAT를 cycle로 측정했다.

-------------
우리는 이 표로부터 정답 정책을 도출하기 위해, 간단한 결정론적 휴리스틱을 사용한다.

-------------
1. unique PC를 가지고 있는 모든 load 명령어 마다 우리는 최소 AMAT를 달성하는 prefetcher 유형과 prefetcher degree의 조합을 선택했다. 
최적의 prefetche 정책이 될 수 있게 load 명령에 대해서

하지만 복잡한 내부 상태를 가진 정교한 prefetcher를 방해하는 것을 막기 위해 이 필터링 힌트는 생략된다.

4.4 LMHint Hardware Prefetcher
offline에서 생성된 힌트를 processor 내부에서 runtime에 사용될 수 있도록 어떻게 전달해야 할까?
LMHint Prefetcher HW prefetcher 
PF-LLM 모델에서 제공된 힌트와 함께 서브 prefetcher를 런타임에서 관리하기 위해서

-----------
offline에 생성된었던 힌트들은, 프로그램 실행 전에, PHT라고 불리는 DRAM의 데이타 구조에 메인 메모리 자료 구조로 load된다.
PHT는 각 load 명령의 virtual PC로 인덱싱된다. 이 힌트들을 낮은 지연에 접근할 수 있도록, 우리는 Prefetch Hint buffer(PHB)라 불리는 작은 
on chip 버퍼를 도입한다.

PHB는 PHT의 힌트 엔트리 중 가장 최근에 사용된 것들을 캐싱하는데, 이는 TLB가 page table 엔트리를 캐싱하는 방식과 유사하다.

우리 설계에서는, 하드웨어 오버헤드를 최소화하면서 single cycle 접근을 보장하기 위해 256 엔트리 PHB를 사용한다.
각 PC에 대한 힌트를 단일 8bit 값으로 제한하여, 4bit는 prefetcher selection에, 2 비트를 prefetch degree에, 2비트를 demand request filtering 정책에 할당한다. sub-prefetcher가 소수인 ensemble에서는 더 적은 비트로도 충분할 수 있지만 8bit보다 작은 row width를 갖는 SRAM blackbox는 흔히 구할 수 없으므로 우리는 8bit 인코딩을 채택한다. 원래 JSON 파일 형태였던 힌트 데이터는, PHT와 PHB 양쪽에 효율적으로 저장하기 위해 이 압축된 binary 형식으로 변환된다. -> 압축 binary 형식이 어디에 나와있지?
-----------
load 명령이 issue될 때, 그 PC로 PHB를 조회한다. hit이면, 해당 힌트 정책이 인출되어 prefetcher ensemble을 제어하도록 dispatch된다. 
LMHint prefetcher는 여러 기존 sub-prefetcher를 조율하는 prefetcher ensemble이다. 인출된 힌트가 그 동작을 3가지 방식으로 좌우한다.

1. prefetcher selection 힌트는, 이 load에 대응하여 생성된 prefetch 요청을 어느 sub-prefetcher가 issue하도록 허용될지를 결정한다.

2. prefetch degree 힌트는, 선택된 sub-prefetcher에 직접 전잘되어 그 적극성을 제어한다. 

3. demand request filtering 힌트는, demand 요청이 지정된 sub-prefetcher로 전송되는 것을 막아, sub-prefetcher의 내부 상태를 무관한 training 정보로부터 보호한다. 

PHB miss가 발생하면, 메인 메모리의 PHT로부터 엔트리를 채우기 위한 요청이 전송된다. 그 사이에는 PHT와 PHB 양쪽의 예약된 zero-addressed 엔트리에 저장된 기본 prefetch 정책을 사용한다.

Q. filter가 2bit면 4가지 조합뿐인데, Listing1의 JSON엔 "Filter":"stream"처럼
   prefetcher 이름이 적혀있다. 어떻게 2bit로 이게 가능한가?
    A.
    [사실 확인] §4.4: 8bit 힌트 = selection 4bit + degree 2bit + filter 2bit. filter는 2bit(4값) 맞음.

    [먼저 filter가 하는 일] "이 load의 demand를 *어느* sub-prefetcher에게 보내지 말지" 지정.
      (§4.4: 지정된 prefetcher가 demand를 못 받게 해 내부상태를 무관한 training으로부터 보호)
      → "Filter":"stream" = "이 load의 demand를 stream prefetcher엔 안 보냄"

    [두 표현이 다른 층위] = 이게 정진 모순의 정체
      JSON "Filter":"stream"  = SW/사람용 이름 (offline 표현)
      2bit                    = HW 인코딩 (런타임 표현)
      §4.4 "originally in JSON, converted into compact binary format"
        = JSON→2bit lowering (컴파일: C소스→기계어와 동형)

    [★2bit(4값)로 충분한 이유 = filter 대상이 소수]
      - selection: 전체 prefetcher(최대 11개) 중 1개 골라야 → 4bit(16값) 필요
      - filter   : "막을 수 있는" prefetcher가 적음 → 2bit로 충분
        · §5.1: 정교한 5개(Pythia/Bingo/DSPatch/Sandbox/SMS)는 절대 filter 안 함 → 제외
        · 최종 설계 SDFR = sub-prefetcher 4개뿐
        → {no-filter + 소수 후보} = 4값(2bit)로 커버
      즉 selection과 filter의 비트 수가 다른 건 "고를 대상 집합 크기"가 달라서.

    [논문 미설명 지점]
      - JSON 이름 → 정확히 어느 2bit 값인지의 매핑은 논문에 없음("compact binary로 변환"까지만)
      - 8bit(4/2/2)도 딱 필요해서가 아니라 "8bit 미만 SRAM 매크로가 흔치 않아서" 채운 것(slack 有)
      - 그래서 "stream"이 2bit 어디에 대응하는지는 하드웨어 구성(어떤 4개를 쓰냐)에 종속, 원문 미기재

    [결론] 2bit로 "stream" 지정이 되는 건 filter 대상이 소수(정교한 것 제외 + 최종 4개)라서.
      JSON 이름=offline 표현 / 2bit=특정 HW 구성용 인코딩. 정확한 매핑은 논문 미기재.
