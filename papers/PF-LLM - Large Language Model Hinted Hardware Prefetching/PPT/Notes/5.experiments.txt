# 5.2 ChampSim 시뮬레이션 환경 세팅
우리의 데이터셋 생성과 성능 평가는 Table 3에 상술된 일관된 시스템 구성을 사용한다. 코어 구성은 Arm Neoverse N2 코어[28]를 모방한다.
시뮬레이션 프레임워크는 ChampSim 시뮬레이터의 DPC-3 버전 위에 구축된다. 짚어둘 점은, Figure 3의 우리 workflow가 공개된 사전생성 trace를 쓰는 대신
SPEC 벤치마크를 소스에서 컴파일할 것을 요구한다는 것이다. 이는 Pin[24]으로 공개 ChampSim trace가 명령 실행 순서, 메모리 접근 이력 같은 동적 정보만 담고,
PF-LLM이 요구하는 정적 어셈블리 코드는 담지 않기 때문이다. 
벤치마크를 직접 컴파일함으로써, 우리는 분석에 필요한 전체 프로그램 binary에 접근할 수 있다. 컴파일 환경의 세부는 Table 3 하단에 있다. 이 커스텀 컴파일된 binary들을
데이터셋 생성, 어셈블리 context 추출, 최종 성능 평가를 포함한 이후 모슨 실험에 사용된다.

-----------
엄밀한 평가를 하기 위해, 우리는 테스트 데이터가 학습셋으로 누출되는 것을 방지한다. SPEC 2006 패키지의 메모리 집약 benchmark를 쓰고, SPEC 2017 오로지 테스트용으로 사용한다.
따라서 PF-LLM 모델은 평가 전에 test set을 보지 않았다.

Q. Data parallelism을 한 예시로 설명을 해야겠다. 0.5B이면 gpu한대여도 충분함에도 여러 대의 gpu를 사용하는 것은 학습을 빨리 하기 위해서임

Q. efective batch size, BF16 정밀도는 무엇인가?
    A.
    [effective batch size = 64]그러
    - gradient 한 번 업데이트에 실제로 모으는 총 샘플 수.
    - effective batch = (GPU당 batch) × (GPU 수) × (gradient accumulation step)
      → 8 GPU에 데이터를 나눠 각자 계산한 gradient를 합쳐 유효 64 달성 (data parallelism)
      → 앞 Q "0.5B인데 왜 8 GPU"의 답과 직결: 8대로 나눠 학습을 빨리.
    - 배치 클수록: gradient 노이즈↓(안정적), 학습 빠름. 너무 크면 일반화↓ 위험.
      → "effective"라는 단어 자체가 여러 GPU로 나눴다는 신호 (full FT data-parallel 정황, 발견 #38)

      => GPU당 batch size는 8개

    [BF16 = bfloat16, 16bit 부동소수점]
    - FP32(32bit) 대신 16bit로 학습 → 메모리 절반, 연산 빠름.
    - 비트 구성이 핵심 (BF16 vs FP16):
        BF16 = 부호1 + 지수8 + 가수7   ← 지수 8bit = FP32와 동일
        FP16 = 부호1 + 지수5 + 가수10
        가수는 Mantissa
    - BF16의 장점 = 표현 "범위(range)"가 FP32와 같음 (지수 8bit).
      → gradient overflow/underflow 적어 학습 안정. loss scaling 불필요.
      → FP16은 정밀도(가수)는 높지만 범위가 좁아 gradient 터지기 쉬움.
    - 그래서 딥러닝 대규모 학습의 사실상 표준. 정밀도(가수 7bit)를 조금 희생하고 안정성·속도를 얻음.
      가중치는 어차피 noisy하게 업데이트되니 가수 7bit로 충분.
