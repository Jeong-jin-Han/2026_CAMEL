Main topic Killer Application
GPU-centric SmartNIC 최초 구현: 기존 SmartNIC은 산업계 전부(Broadcom, Pensando, Netronome, Intel IPU)가 CPU-centric인데, FpgaNIC은 GPU가 SmartNIC을 CPU 개입 없이 직접 제어하는 최초의 100Gbps FPGA 기반 SmartNIC이다.

양방향 CPU-우회 통신: (1) GPU가 FPGA의 doorbell/status 레지스터를 CUDA 커널 내부에서 직접 트리거·폴링(control plane, G1), (2) FPGA가 GPU 가상주소(virtual address)로 GPU 메모리에 직접 PCIe P2P DMA를 수행(data plane, G2). 이 두 방향을 모두 CPU 없이 구현한 것은 이 논문이 최초라고 주장한다.

하드웨어로 완전히 구현된 100Gbps 신뢰성 네트워크 트랜스포트(G3): 소프트웨어 스택이 감당하지 못하는 line-rate 처리를 FPGA 하드웨어 TCP 스택으로 해결.

HLS로 프로그램 가능한 데이터패스 가속기(G4, G5): On-NIC Computing(ONC) 모듈을 C++ 기반 HLS(High Level Synthesis)로 작성 가능하게 하여, direct/on-path/off-path 세 SmartNIC 모델을 단일 아키텍처로 모두 지원.

실증된 성능: 8-GPU 분산 AllReduce에서 NCCL 대비 최대 2.5배 속도 향상을, GPU/CPU 컴퓨팅 사이클을 전혀 소모하지 않으면서 달성.
Original §1, p.967
In this paper, we present the design of a 100Gb GPU-centric SmartNIC to serve distributed applications running on GPUs.
Main topic 필요한 이유 (Why)
멀티코어 SmartNIC의 한계: BlueField-2 같은 임베디드 ARM 코어는 control-plane 관리에는 적합하지만, 100Gbps 데이터 스트림을 line-rate로 처리(data-path accelerator, G4)하기엔 메모리 대역폭이 부족하다(실측 27.3GB/s, §1 p.968).

FPGA-증강 SmartNIC의 한계: Mellanox Innova-2는 FPGA가 NIC ASIC에 PCIe Gen4 x8로 연결되어 있어, 패킷이 FPGA를 거치는 순간 상당한 지연이 추가되고 line-rate 처리가 불가능하다. GPU 가상주소 접근(C1)도 지원하지 않는다.

CPU 기반 네트워크 트랜스포트의 한계: 100Gbps 신뢰성 네트워크 트랜스포트를 CPU 소프트웨어로 구현하면 여러 CPU 코어를 소모하고, GPU가 네트워크 오퍼레이션을 개시할 때마다 CPU를 거쳐야 해 지연이 늘어난다(C2).

GPU 가상주소 문제(C1): GPU 프로그램은 가상주소를 다루는데 DMA 엔진은 물리주소만 인식한다. GPU의 64KB 페이지 크기 때문에 32GB 메모리는 순진하게 구현 시 512K TLB 엔트리가 필요해 FPGA 온칩 메모리로 감당하지 못한다.

프로그래밍 인터페이스 문제(C3): FPGA 전통적 프로그래밍은 HDL(cycle-sensitive)이라 시스템 프로그래머 접근성이 낮다.

SmartNIC 모델 다양성 문제(C4): 스마트 기능의 위치(direct/on-path/off-path)에 따라 적합한 모델이 다른데, 기존 SmartNIC은 특정 모델 하나에 고정되어 있다.
Original §2.1, p.969
how to enable the GPU to efficiently manipulate the reliable hardware transport on the FPGA becomes a new challenge.
Main topic 해결책 (Solution)
3계층 아키텍처: GPU Communication Stack(제어/데이터 평면 오프로드) + 100Gbps Hardware Network Transport(신뢰성 TCP) + On-NIC Computing(ONC, HLS 데이터패스 가속기)을 하나의 FPGA(Xilinx Alveo U50/U280)에 계층적으로 결합(Figure 1).

GTLB (GPU Translation Lookaside Buffer): main TLB(2MB 페이지, 물리적으로 연속인 경우) + complementary TLB(64KB 페이지, 비연속인 경우)로 구성. GPU 커널 함수 nvidia_p2p_put_pages로 얻은 주소 쌍을 순회하며 최대한 2MB 페이지로 병합, 완전 파이프라인된 온라인 주소 변환을 FPGA 온칩 메모리(BRAM)에서 수행.

Decoupled application interface: 원래의 TCP 스택은 handshake(10~30 사이클)와 payload transfer가 직렬화되어 대역폭 손실이 컸는데, FpgaNIC은 둘을 오버랩시켜 최대 4GB 스트림을 자동 chunking.

Direct / On-path / Off-path 세 모델: (1) direct — GPU가 네트워크 트랜스포트를 직접 조작(GCN 예시), (2) on-path — 패킷 흐름 위에서 즉시 처리(HyperLogLog 예시), (3) off-path — 별도 엔진이 데이터 흐름을 오케스트레이션(AllReduce 예시).

Original §2.3, p.970
FpgaNIC enables offloading of control plane onto GPUs (via a slave interface) and offloading of the data plane onto the FPGA (via a master interface), such that the host CPU is bypassed.
Main topic 결과 (Results)
공유 인프라 벤치마크: 제어 평면 지연(GPU에서 FPGA)은 1$\mu$s 미만, PCIe P2P DMA read to A100 GPU는 12.6GB/s(PCIe 이론 대역폭에 근접). 하드웨어 TCP 스택 RTT는 마이크로초 단위(3.1~7$\mu$s), 처리량은 큰 패킷에서 94.4Gbps(100Gbps 채널에 근접).

Direct 모델: 제어 평면 오프로드가 있을 때 작은 chunk/transfer size에서 처리량이 유의미하게 향상(CUDA 커널 invocation 오버헤드 제거).

Off-path 모델(AllReduce): 8-GPU 분산 풀에서 NCCL 대비 최대 2.5배 speedup(소데이터), 8MB 이상에서 이론적 bus bandwidth 도달, GPU/CPU 사이클 소모 없음.

On-path 모델(HyperLogLog): 오프로딩해도 전체 처리량에 영향 없이 최소 8개 A100 GPU SM 절약.

리소스 사용: GPU 통신 스택 + 100G HW 트랜스포트가 U50 FPGA 자원의 약 20%만 사용, 나머지 80% 이상이 ONC(온-NIC 컴퓨팅)에 할당 가능.
Original §3.4, p.976
FpgaNIC leads to up to a 2.5x speedup over NCCL, because the AllReduce engine in FpgaNIC efficiently overlaps the operations of the PCIe DMA, network transport, and FPGA memory.
Main topic 결론 (Conclusion)
FpgaNIC은 GPU 클러스터를 위한 최초의 FPGA 기반 GPU-centric 100Gbps SmartNIC으로, direct/off-path/on-path 세 모델을 하나의 아키텍처로 지원하며 오픈소스로 공개되었다(GitHub: RC4ML/FpgaNIC). 저자들은 이를 발판으로 (1) Deep Learning 분산학습에서 통신(AllReduce) + 컴퓨팅(compressor, Adam optimizer)을 함께 오프로드하는 연구, (2) Intel FPGA 포팅, (3) OpenCL 성능 분석 프레임워크를 통한 완전 자동화된 오프로드 식별을 미래 방향으로 제시한다.

내 연구 방향에서 이 논문의 위치는 명확하다 — 네트워킹(원격 GPU-to-GPU)을 위한 FPGA-GPU P2P 메커니즘의 실증이며, H3(로컬 GPU 제어 평면)이 요구하는 세 가지 필요조건(PCIe endpoint + bus mastering, 같은 PCIe 스위치 아래 P2P, 성숙한 스택인 HLS)이 실제 상용 FPGA 보드 위에서 모두 충족 가능함을 보여주는 구체적 증거다. 다만 FPGA가 GPU의 실행(커널 스케줄링/launch)을 지시하는 사례는 아니며, 그 지점은 여전히 미탐색 공간으로 남아 있다.
Original §6 Conclusion, p.978
Inspired by the fact that there is no SmartNIC designed for GPUs, we present FpgaNIC, a full-stack FPGA-based GPU-centric 100Gbps SmartNIC that allows a large design space exploration around SmartNICs for accelerating applications running on distributed GPUs.

Method C1: 512K -> 18K 엔트리로 압축
32GB GPU 메모리, 64KB 페이지 -> naive하게 저장 시 512K TLB 엔트리 필요. FpgaNIC은 64KB 페이지들이 물리적으로 연속(2MB 정렬)인 경우가 많다는 관찰을 이용해, 연속 64KB 페이지 32개를 2MB 페이지로 병합한다.

$$16K + 2K = 18K \text{ entries} \quad (\text{vs. } 512K \text{ naive})$$

the total number of required entries for 32GB memory becomes 16K+2K=18K, significantly smaller than the previous 512K entries.

Claim C2: GPU는 원래 신뢰성 네트워크용이 아니다
GPU는 대규모 병렬성을 위해 설계되었는데, 신뢰성 네트워크(retransmission 등 복잡한 flow control)는 병렬성을 저해한다(§2.1, p.969, ref[28,43]). CPU 기반 트랜스포트는 여러 코어를 소모하고 GPU발 오퍼레이션마다 CPU 개입이 필요해 지연이 늘어난다.
Original §2.1, p.969
GPUs are not originally designed for reliable network transport since reliable networking reduces the degree of parallelism and requires a complex flow control, e.g., retransmission.
Reference Innova-2의 구조적 한계
Mellanox Innova-2는 FPGA가 ConnectX-5 NIC ASIC에 PCIe Gen4x8 인터페이스로 연결된다. 패킷이 FPGA에서 처리될 때 이미 상당한 지연이 붙어 line-rate가 불가능(G4 부분 지원에 그침). Appendix A.2.2(p.985)에서 저자들은 동일한 AllReduce를 Innova에서 구현하면 처리량이 반토막날 것이라 추정한다.
Original Appendix A.2.2, p.985
In such a design, the FPGA can consume data either from the GPU or from the network but not from both at the same time. We estimate that the overall throughput would be halved.
Gap / Idea off-path 멀티코어 CPU도 여전히 병목이 될 수 있다
off-path 모델에서 멀티코어 CPU(2-channel DDR4)를 staging에 쓸 수 있지만, 멀티코어 CPU의 메모리 대역폭이 100Gb 트래픽 처리 시 쉽게 병목이 된다(§2.1, p.969, ref[40]). 즉 off-path라고 CPU를 쓰면 여전히 병목 — FpgaNIC은 off-path도 FPGA 내부(온보드 메모리)로 구현해 이 문제를 회피한다.
Original §2.1, p.969
multicore CPU's memory bandwidth can easily become a performance bottleneck when processing 100Gb network traffic using the multicore CPU.

Method GTLB 주소 변환 알고리즘
Algorithm 1 (POPULATING GTLB, p.971): (1) gpuMemAlloc으로 GPU 메모리 공간을 미리 할당, (2) nvidia_p2p_put_pages로 모든 64KB 페이지의 VA/PA 쌍을 획득, (3) 물리적으로 연속인 64KB 페이지 32개를 2MB 페이지로 최대한 병합, (4) main TLB(2MB 단위)와 complementary TLB(64KB 단위, 비연속인 경우)를 채운다.

$$\text{index} \leftarrow 0, \quad \text{comp} \leftarrow 0$$

물리적으로 연속인 2MB 페어는 main TLB에 저장(valid=1)하고, 비연속인 경우 complementary TLB에 32개의 64KB 서브페이지를 저장한 뒤 main TLB에는 comp_offset만 기록한다. 조회 시 main TLB를 먼저 확인하고, 비연속이면 comp_offset으로 complementary TLB를 참조 — 완전 파이프라인(fully-pipelined) 조회가 가능하다.
Original §2.3.2, p.971
FpgaNIC can easily achieve fully-pipelined translation lookup on the FPGA.
Method Decoupled Application Interface
원래 인터페이스: control handshake(10~30 사이클) 후 payload(최대 1460B, 10~23 사이클) — handshake 오버헤드가 payload 전송시간과 맞먹어 대역폭 낭비가 컸다. FpgaNIC의 decoupled interface는 handshake를 payload transfer와 오버랩시키고, 최대 4GB 데이터 스트림을 프로그래머 개입 없이 자동으로 올바른 크기 청크로 분할한다(§2.4.1, p.971).
Original §2.4.1, p.971
The proposed decoupled interface gets rid of the handshake, overlapping the control handshakes with the data transfer.
Method GCN (Direct Model) 아키텍처 - Figure 11
Direct 모델의 예시인 GPU-centric Networking(GCN): 3계층(GPU user / GPU kernel / FpgaNIC)으로 구성되며, 송신측은 send buffer(circular buffer)에서 DMA read and forward, 수신측은 100Gb HW Transport에서 receive buffer로 add header and DMA write. Credit-based flow control로 신뢰성을 보장한다.

$$M = \frac{100}{N}\text{MB (연결당 버퍼 크기)}, \quad W = \frac{M}{F}\text{MB (슬롯 크기)}$$

수신자가 누적 수신량 $M_r$이 임계값 $Th$를 넘으면 $Th \times M$ 바이트의 credit을 doorbell로 송신자에 반환한다.

Original Figure 11, §A.1.4, p.983
Reliable communication (goal D1) is achieved through a simple credit-based flow control over each TCP connection.
Method 세 SmartNIC 모델의 응용 매핑
direct — GPU가 네트워크 트랜스포트를 직접 조작(예: GCN, 소켓형 API로 원격 GPU와 통신). on-path — 패킷이 네트워크에서 GPU로 흐르는 도중 op_in/op_out/op_return 포트로 즉시 처리(예: HyperLogLog로 cardinality를 line-rate로 계산). off-path — 별도 엔진이 PCIe DMA/네트워크/온보드 메모리 세 리소스를 오케스트레이션(예: AllReduce 8-step 링 알고리즘). 다른 스마트 기능은 다른 SmartNIC 모델을 선호한다 — 예: 데이터베이스 필터 연산은 on-path, AllReduce는 off-path가 유리.

Memo 스코프 차이를 잊지 말 것: 네트워킹 vs 로컬 제어 평면
이 논문을 인용할 때 반드시 '원격 GPU-to-GPU 네트워킹'이라는 스코프를 명시해야 한다. FpgaNIC의 스마트 기능은 전부 네트워크 데이터 흐름(AllReduce 리덕션, HLL cardinality, GCN 소켓 통신) 위에서 동작하며, GPU 커널의 launch/scheduling을 FPGA가 결정하는 사례는 전혀 없다. 과장해서 'FpgaNIC이 이미 GPU 제어 평면을 구현했다'고 말하면 부정확 — 정확히는 'FpgaNIC이 그 제어 평면을 만들기 위한 배관(PCIe P2P, doorbell, HLS)을 실증했다'가 맞는 표현이다.
