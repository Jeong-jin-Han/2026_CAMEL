Venice: Improving Solid-State Drive Parallelism at Low Cost via Conflict-Free Accesses
Click a node to select
Main topic Killer Application
Venice는 SSD 컨트롤러와 flash chip 사이의 path conflict(경로 충돌) 문제를 flash chip을 전혀 수정하지 않고 해결한다. 상용 SSD는 채널(channel)당 여러 flash chip이 컨트롤러로 가는 단 하나의 경로(path)를 공유하는 multi-channel shared bus 구조라서, 같은 채널을 향하는 I/O 요청들이 몰리면 경로를 두고 직렬화(serialize)되어 병렬성(parallelism)이 크게 제한된다.

각 flash chip이 컨트롤러와 독립 채널을 갖는다고 가정한 이상적인 path-conflict-free SSD는 baseline 대비 평균 $4\times$(최대 $11.74\times$) 빠르다 — 이 격차가 path conflict 하나가 만드는 순수한 성능 손실이다. Venice는 flash chip 옆에 저비용 router chip을 붙여 2D mesh 네트워크를 구성하고, 데이터 전송 전에 경로를 미리 예약(path reservation)하는 방식으로 이 격차의 대부분을 좁힌다 — 그것도 flash chip 설계는 그대로 둔 채로, 낮은 면적·전력 오버헤드로.
Original Abstract, p.1
SSDs use a multi-channel shared bus architecture where multiple memory chips connected to the same channel communicate to the SSD controller with only one path. As a result, path conflicts often occur during the servicing of multiple I/O requests, which significantly limits SSD parallelism.
Main topic 필요한 이유 (Why It's Needed)
채널 수를 늘리는 단순한 해법은 컨트롤러의 I/O pin과 복잡도를 늘려 확장성(scalability)이 없다. 선행 연구들도 근본 해결에는 못 미친다.

pSSD(Kim et al.)는 flash chip의 control/data pin을 모두 써서 채널 대역폭을 2배로 늘리지만, die당 20%라는 큰 면적 오버헤드가 들고 path conflict 자체는 없애지 못한다(baseline 대비 성능 향상 평균 27%에 그침). pnSSD는 chip마다 수평/수직 두 채널을 둬 path diversity를 일부 확보하지만 개선폭은 평균 30%뿐이다.

interconnection network를 쓰는 최선의 선행 연구 NoSSD(Tavakkol et al.)조차 두 가지 근본 약점을 갖는다: (1) router마다 16KB buffer를 flash chip 내부에 통합해야 해서 면적과 I/O pin 수($4\times$)가 크게 늘고, (2) deterministic dimension-order routing이라 여러 자유 경로(path diversity)가 있어도 활용하지 못한다. 그 결과 NoSSD는 baseline 대비 평균 35% 개선에 그쳐, ideal $4\times$ 상한과 큰 격차가 남는다.
Original §1, p.1
prior SSD interconnection network designs have two main weaknesses which prevent them from effectively addressing the path conflict problem. First, prior works impose significant area (i.e., cost) overhead as they integrate a buffered router (e.g., 16KB buffer per router port) inside each flash chip. ... Second, prior works do not resolve path conflicts effectively because they employ a simple deterministic routing algorithm, which cannot utilize the interconnection network's rich path diversity.
Main topic 해결책 (Solution)
Venice의 해결책은 세 가지 핵심 기술로 구성된다.

(1) 저비용 인터커넥트: flash chip 옆에 별도의 router chip을 붙인 flash node(flash chip + router chip)를 새 빌딩 블록으로 도입한다. router는 flash chip이 원래 shared channel에 연결할 때 쓰던 I/O data pin(injection/ejection port)을 그대로 재사용해 통신하므로 flash chip 자체는 전혀 수정하지 않는다. flash node들을 2D mesh topology로 연결해 router끼리 양방향(bidirectional) link로 이웃과 연결한다.

(2) Path Reservation: I/O 요청마다 데이터 전송 전에 scout packet을 먼저 보내 컨트롤러↔목적 flash chip 사이의 충돌 없는 경로를 예약해둔다. 예약된 link는 양방향이라 forward(write)/backward(read) 모두에 쓰인다 — 이 덕분에 NoSSD처럼 충돌 시 데이터를 담아둘 대형 router buffer가 필요 없다.

(3) Non-Minimal Fully-Adaptive Routing: scout packet 라우팅 시 최단 경로(minimal path)가 막혀 있으면 유휴 링크(idle link)를 우회하는 경로를 찾아 path diversity를 실제로 활용한다. deadlock은 backtracking으로, livelock은 같은 router 재방문 횟수 제한으로 회피한다.

Original §4.1, p.5
We introduce a new building block, called flash node, which consists of a flash chip and a separate router chip. ... a flash chip communicates with a router chip using its I/O data pins (i.e., injection/ejection pins) that are otherwise used for connecting the flash chip to the shared channel.

Main topic 결론 (Conclusion)
Venice는 flash chip을 건드리지 않고도 path conflict를 근본적으로 줄여, ideal path-conflict-free SSD의 성능에 상당히 근접하는 저비용 경로를 제시했다. 늘어난 path diversity는 SSD 내부 near-data processing(NDP) 시 여러 flash chip에 흩어진 operand를 효율적으로 모으거나, garbage collection(GC)의 valid page 이동이 host I/O와 겹칠 때 생기는 path conflict를 줄이는 데도 쓰일 수 있다고 저자들은 제안한다.

다만 한계도 있다: 논문은 I/O 요청의 0.02%가 첫 시도에 실패했을 때의 추가 지연을 정량화하지 않았고, scout packet 재전송 최적화는 extended version으로 미뤘다. 또한 평가는 $8\times8$(flash chip 64개) 규모에 한정되어, 훨씬 큰 네트워크로의 확장성은 향후 과제로 남는다. FLIN/PAQ/PIQ 같은 I/O 스케줄링 기법들과는 orthogonal한 방향이라고 저자들은 밝힌다.
Original §7-8, p.13
We believe Venice is orthogonal to these works and I/O scheduling for the Venice architecture is an interesting research direction.

Thus, in this simple example, the path conflict problem increases the average I/O access latency by 57%, which in turn results in lower SSD throughput.
Result Ideal path-conflict-free SSD가 baseline 대비 평균 4배(최대 11.74배)
각 flash chip이 컨트롤러와 direct separate channel을 갖는다고 가정한 이상적 SSD(path-conflict-free SSD)는 19개 real-world 워크로드에서 baseline 대비 평균 $4\times$, 최대 $11.74\times$ 빠르다. 이 수치가 Venice가 좁혀야 할 상한이자, path conflict 문제 하나의 순수 임팩트를 정량화한 값이다.
Original §1, p.1
We observe that the ideal SSD outperforms the baseline SSD by 4$\times$ on average across nineteen data-intensive real-world workloads.
Claim Path conflict는 write보다 read에 더 치명적
read는 data transfer time이 flash read latency와 비슷하거나 더 길어서 path 직렬화의 영향을 고스란히 받는다. 반면 write는 flash write latency(예: performance-optimized 구성에서 100$\mu$s)가 service time 전체를 지배하므로, path가 잠깐 막혀도 상대적 영향이 작다. 그래서 read-intensive 워크로드일수록 Venice의 이득이 크다.
Original §3.1, p.4
The path conflict problem affects the performance of read requests more than that of write requests. This is because data transfer time for a read request is comparable to or longer than the flash read latency, while the flash write latency ... dominates the total service time of a write request.
Result pSSD/pnSSD: 대역폭·path diversity는 늘지만 근본 해결 못함
pSSD는 flash chip의 control/data pin을 모두 써서 channel 대역폭을 2배로 늘리고 packetization용 on-die controller를 추가한다. transfer latency를 줄여 path conflict의 성능 영향은 줄이지만, path conflict 자체를 근본적으로 없애지는 못한다(baseline 대비 평균 27% 개선). 게다가 flash die 내부를 수정해야 해서 die당 20%라는 상당한 면적 오버헤드가 든다. pnSSD는 chip마다 수평/수직 두 channel을 둬 path diversity를 일부 확보하지만 개선폭은 평균 30%에 그친다.
Original §3.2, p.4
While pSSD can reduce the performance overhead of path conflicts by reducing the I/O transfer latency, pSSD imposes significant area overhead (i.e., 20% [15]) in each flash die.
Result NoSSD의 두 약점 → baseline 대비 겨우 35% 개선
NoSSD(최선의 선행 interconnection network)는 (1) router당 16KB buffer 통합 + chip당 $4\times$ I/O pin이라는 큰 면적·비용 오버헤드, (2) deterministic dimension-order routing이라 여러 free path가 있어도 활용 못한다는 두 약점을 가진다. 그 결과 baseline 대비 평균 35% 개선에 그쳐, ideal $4\times$ 상한과 큰 격차가 남는다.
Original §3.3, p.4-5
NoSSD has two main weaknesses that limit its effectiveness at mitigating the path conflict problem. First, NoSSD imposes significant area and cost overhead due to 1) the integration of a buffered router (e.g., with a 16KB buffer per router port) inside each flash chip and 2) 4$\times$ increase in the number of I/O pins compared to a commodity flash chip. Second, NoSSD does not utilize the path diversity effectively as NoSSD employs simple deterministic routing.
Reference 비교 대상: pSSD/pnSSD[15], NoSSD[7,38], MQSim[57,58]
Venice가 직접 정량 비교하는 선행 interconnection 방식: pSSD/pnSSD(Kim et al. [15], packetization 기반 채널 대역폭·path diversity 증가), NoSSD/Network-on-SSD(Tavakkol et al. [7,38], 2D mesh + deterministic routing, Venice가 넘어야 할 최강 baseline). 평가에는 open-source multi-queue SSD simulator MQSim[57,58]을 사용했다.

Method Path Reservation: scout packet + router reservation table
Venice는 데이터 전송을 시작하기 전에 scout packet을 먼저 보내 conflict-free path를 예약한다. scout packet은 header flit과 tail flit 두 개의 8-bit flit으로 구성되며, header flit에는 destination flash chip ID(6-bit, 64 chip까지), tail flit에는 source flash controller ID(3-bit, 8 controller까지)가 담긴다. 각 router는 router reservation table을 두어 packet ID(=source flash controller ID), entry/exit port(각 2-bit), valid bit을 기록한다. scout가 destination에 도착하면 이미 예약된 forward(write)/backward(read) path를 이용해 즉시 되돌아가고, source controller가 그 경로로 실제 I/O 전송을 스케줄한다. 이 덕분에 NoSSD처럼 충돌 시 데이터를 담아둘 대용량 router buffer가 필요 없다.
Original §4.2, p.6
The scout packet consists of two 8-bit scout flits, a header flit, and a tail flit. ... The router reservation table keeps track of 1) the packet ID, which is the same as the source flash controller ID from which the packet was sent, and 2) which two ports (i.e., entry and exit ports) are connected bidirectionally (based on reservations that were made).
scout packet flit 구조
Header flit: 2-bit type + destination flash chip ID(6-bit)
Tail flit: 2-bit type + source flash controller ID(3-bit) + unused(3-bit)
Type info 2번째 bit: 0=cancel mode, 1=reserve mode
Method Non-Minimal Fully-Adaptive Routing + deadlock/livelock 회피
현재 router와 destination router의 X/Y 좌표 차이를 비교해 9가지 case로 분기하고, 각 case에서 free output port를 후보 목록에 추가한다. 후보가 2개면 2-bit LFSR pseudo-random으로 선택, 1개면 그대로 선택한다. 후보가 0개(모든 minimal 방향이 막힘)면 free한 ejection 이외의 포트로 misroute해 non-minimal path를 시도한다.

deadlock은 scout packet이 충돌을 만나면 upstream router로 backtracking해 다른 경로를 시도하므로 자원 미가용 때문에 영구히 막히는 일이 없다. livelock은 scout가 같은 router를 최대 3번(2D mesh에서 $4-1$)까지만 방문하도록 제한해 막고, 초과하면 최악의 경우 source controller로 복귀해 새 scout packet으로 재시도한다.
Original §4.3, p.7-8
However, if the output list is empty, the algorithm has failed to find any free output port that leads to a minimal path. In this case, the algorithm misroutes the scout packet via a free output port that leads to a non-minimal path.
Deadlock/livelock 처리 원문 요지
Deadlock: backtracking to the upstream router — resource unavailability로 인한 영구 대기가 없음.
Livelock: 같은 router 재방문 횟수 제한(최대 3회)으로 무한 순환 방지.
Memo 설계 결정: non-minimal path의 성능 오버헤드는 무시할 만한 수준
우회 경로는 hop이 늘어 command/data transfer latency가 증가한다. 하지만 I/O data transfer 크기(예: 16KB)와 flash operation latency(read/program/erase)가 총 service time을 지배하기 때문에, 늘어난 command transfer 시간이 전체에 미치는 영향은 negligible하다 — 그래서 Venice는 hop 수를 최소화하는 대신 conflict-free를 보장하는 것을 최우선으로 삼는 설계를 택했다.
Original §4.3, p.7
the longer command transfer time due to a non-minimal path has a negligible effect on the total service time of the I/O request.

Venice가 늘린 path diversity는 NDP(near-data processing) 시 여러 flash chip에서 operand를 효율적으로 모으는 데, 그리고 garbage collection(GC) 시 valid page 이동이 host I/O와 겹치며 생기는 path conflict를 줄이는 데도 활용될 수 있다. Related work로는 flash array parallelism을 늘리는 HLNAND·Decoupled SSD(둘 다 path diversity 부족)가 있고, FLIN/PAQ/PIQ 같은 I/O scheduling 기법들은 Venice의 interconnection network 설계와 orthogonal한 방향이라고 저자들은 밝힌다.
Original §7-8, p.13
Venice's improved parallelism can facilitate NDP inside the SSD by efficiently co-locating different operands required by the NDP operations. ... We believe Venice is orthogonal to these works and I/O scheduling for the Venice architecture is an interesting research direction.
Question 실패한 0.02%는 어떻게 되며, 네트워크가 커지면 scout packet 오버헤드는?
Venice는 I/O의 99.98%가 첫 시도에 conflict-free path를 잡지만, 나머지 0.02%는 모든 flash controller가 바쁘거나 scout가 free link를 못 찾아 대기해야 한다. 논문은 이 케이스의 추가 latency를 정량화하지 않았고, scout packet 재전송 최적화는 extended version[103]에 위임했다. $8\times8$(64 chip)보다 훨씬 큰 네트워크로 확장하면 scout packet 트래픽 자체가 오버헤드가 되지 않을지, backtracking 재시도 비용이 커지지 않을지가 궁금하다.
Gap / Idea path reservation + non-minimal adaptive routing = 일반적 NoC 배경지식
scout packet으로 데이터 전송 전에 경로를 예약해두는 방식과, minimal path가 막히면 idle link로 우회하는 non-minimal fully-adaptive routing은 SSD에 국한된 기법이 아니라 interconnection network / NoC(network-on-chip) 설계 전반에 쓰이는 일반적 아이디어다(Dally & Towles의 라우팅·deadlock 이론과 동일 계보). congestion을 라우팅 시점에 피하려는 이 두 기법은, CXL switch/fabric에서 여러 host-device 트래픽이 겹칠 때 경로를 어떻게 잡을지 고민할 때 참고할 만한 배경지식이 될 수 있다.
Memo 내 연구방향과의 연결: 스케일이 다른 문제 — 과대평가하지 말 것
Venice는 SSD 컨트롤러-flash chip 사이, 즉 보드 레벨의 작고 로컬한 mesh($8\times8$, flash chip 64개) 안에서 conflict-free routing을 푸는 문제다. 내가 보는 CXL disaggregation/multi-node coherence는 host-to-device, 혹은 여러 노드 사이의 memory fabric 문제로 스케일도, coherence protocol이 얽힌다는 점도 다르다. Venice에는 coherence 개념 자체가 없다 — 순수하게 경로 배정(routing) 문제다.

그래서 Venice를 CXL 연구에 직접 갖다 쓸 수는 없다 — 다만 scout packet 같은 저비용 경로 예약, non-minimal adaptive routing 같은 congestion-aware routing 아이디어는 CXL switch fabric의 라우팅/혼잡 문제를 생각할 때 참고할 배경(background) 정도로 남겨둔다. 이건 on-topic이 아니라 인접 분야(adjacent) 독서로 분류.
Memo Read/Write 비대칭의 latency 구조: tPROG가 write를 지배
Venice가 read 중심으로 routing을 최적화하고 write-time placement로 풀지 않는 이유는 두 연산의 latency 구성이 다르기 때문이다.

Read: CMD 전송 + flash read($t_R \approx 3\mu s$) + data 전송($\approx 4\mu s$, path를 사용) — data 전송 시간이 flash read latency와 맞먹어 path conflict에 민감하다.
Write: CMD 전송 + data 전송 + flash program($t_{PROG} \approx 100\mu s$, cost-optimized 구성에서는 $650\mu s$) — $t_{PROG}$가 전체 service time을 압도해서, path conflict로 인한 몇 $\mu s$의 지연은 상대적으로 무시할 수준이다. write의 병목은 path가 아니라 NAND cell 자체다.

'write-time에 관련 데이터를 인접 배치해서 read를 최적화하자'는 아이디어(FTL physical page allocation 계열)는 실제 연구 라인이지만, Venice는 이게 실전에서 잘 안 통한다고 지적한다 — 이유는 (1) random access pattern, (2) multi-app interference, (3) GC/wear leveling이 데이터를 계속 relocate하는 dynamic device condition 때문이다.
Gap / Idea Locality(hop 줄이기)와 Conflict 회피(striping)는 정반대 처방
이 논문을 이해하는 데 가장 중요한 반직관적 통찰: 관련 데이터를 인접 배치해서 hop을 줄이는 것과, conflict를 줄이기 위해 데이터를 흩뿌리는(striping) 것은 서로 반대 방향이다.

관련 데이터를 인접 배치하면(hop 감소) 그 데이터를 병렬로 읽을 때 오히려 같은 link를 두고 경합해서 parallelism이 오히려 줄어든다. 병렬성을 얻으려면 동시에 접근되는 데이터를 독립된 경로로 빠지도록 흩뿌려야 한다 — 실제로 baseline SSD의 FTL도 일부러 striping해서 병렬성을 뽑아낸다.

hop을 줄여서 얻는 이득도 미미하다: router의 hop당 latency는 나노초(ns) 단위, flash operation은 마이크로초($\mu s$) 단위라 그 격차가 압도적이다. 진짜 손해는 거리가 아니라 conflict로 인한 serialization이고, 그건 '비어있는 경로 하나를 더 만드는 것'으로만 풀린다 — 그래서 Venice는 필요하면 non-minimal path(우회)를 감수하고서라도 conflict를 피하는 쪽을 택한다.

설계 철학은 decoupling: FTL은 wear leveling·GC 효율 기준으로 자유롭게 배치하고, conflict 회피는 network가 access 시점에 동적으로 담당한다. placement에 read 성능까지 책임 지우면 multi-objective 충돌(배치 최적화 vs GC 효율)이 생기고, GC가 최적 배치를 계속 깨는 문제도 있다.

locality 직관(가까이 두면 좋다)은 latency·거리가 병목인 시스템(NoC, NUMA, cache line)에서는 정확한 처방이지만, SSD처럼 병목이 shared-channel 경합인 시스템에서는 반대 처방이 필요하다 — '어느 layer의 무엇이 병목인가'를 먼저 묻는 게 핵심이다.
Memo Reservation이 필요한 진짜 이유: 탐색이 아니라 buffer 회피
'그냥 broadcast로 데이터 위치를 찾아서 보내면 안 되나'라는 질문에 대한 답: controller는 FTL mapping table로 데이터 위치(channel/chip/block/page)를 이미 알고 있다. network의 역할은 '탐색(search)'이 아니라 '운반(transport)'이다. broadcast는 오히려 모든 link를 점유해 path diversity를 무력화시킨다.

reservation이 진짜 필요한 이유는 read의 대용량 데이터 전송 때문이다 — flash page 전송은 KB 단위의 길고 연속적인 burst로 link를 몇 $\mu s$ 동안 통째로 점유한다. 이 구간이 conflict에 가장 취약하다.

Venice는 circuit switching + bufferless 조합으로 이걸 해결한다: 작은 scout packet이 controller에서 target까지 경로 전체를 미리 예약하고, 성공하면 데이터가 중간에 멈추거나 버퍼에 저장되는 일 없이 그대로 흐른다. 만약 '예약 없이 그냥 흘려보내기'를 했다면 그건 packet-switched + router 버퍼 방식이 되는데, 그 버퍼 자체가 비용이다 — 논문 제목의 'at low cost'가 바로 이 버퍼를 피하는 데서 나온다.
Gap / Idea 보장의 사다리: Venice는 starvation-freedom을 보장하지 않는다
Venice의 circuit switching 설계는 deadlock-free(경로 예약 실패 시 backtracking으로 hold-and-wait 회피)와 livelock-free(router 재방문 횟수 제한으로 무한 배회 차단, 즉 forward progress = 시스템에서 적어도 하나는 항상 진전)까지는 보장한다.

하지만 starvation-freedom(모든 요청이 언젠가는 반드시 서비스된다는 보장)은 보장하지 않는다. 강도로 줄을 세우면:

$$\text{deadlock-free} < \text{livelock-free}(\exists) < \text{starvation-free}(\forall)$$

Venice의 fairness 관점은 egalitarian 'fair competition'이다 — priority 구분 없이 모든 I/O가 동등한 자격으로 경쟁한다(scout의 reserve/cancel 모드가 progress에는 우호적이지만 '밀린 요청 우대'는 아니다). 이게 언뜻 공정해 보이지만, 실제로는 aging·oldest-first·starvation counter 같은 고전 NoC arbitration 기법을 전혀 안 쓴다는 뜻이기도 하다.
Reference 후속 연구가 공략한 지점: GC bypass
Venice가 미보장하는 starvation-freedom($\forall$) 축을, 후속 논문 GC bypass가 정확히 공략한다 — Venice는 user I/O와 garbage collection(GC) 사이에 우선순위 차등이 없어, GC가 몰리는 구간에서 자원 경합이 생기면 GC-induced long-tail latency를 잡지 못한다. GC bypass는 전용 GC controller, priority 구분, valid page write preemption을 추가해 이 빈틈을 메운다.

이건 '논문 A가 무엇을 fair하다고 가정했고, 그 가정이 어디서 깨지며, 논문 B가 어떻게 메웠는가'라는 프레임의 실제 사례로 읽을 수 있다 — Venice가 보장하는 것(deadlock/livelock-free, egalitarian fairness)과 보장하지 않는 것(priority/QoS, starvation 방지)의 경계선이 정확히 다음 연구의 출발점이 됐다.
Memo 세미나 프레이밍: '어느 layer의 무엇이 병목인가'를 먼저 묻기
이 논문을 관통하는 하나의 질문법: 직관을 적용하기 전에, 그 직관이 통했던 시스템과 지금 시스템의 병목이 같은 종류인지부터 확인한다.

locality(가까이 두면 좋다)는 NoC·NUMA·cache line처럼 latency/거리가 병목인 시스템에서는 정확한 처방이다. 하지만 SSD처럼 병목이 shared-channel 경합(contention)인 시스템에서는 오히려 정반대(striping)가 답이다. hop을 줄이는 것과 conflict를 줄이는 것이 반대 방향이라는 이 논문의 핵심 통찰도 결국 이 질문법에서 나온다.

세미나에서 이 논문을 소개할 때 쓸 수 있는 프레임: '왜 SSD 문제인데 NoC(network-on-chip) 이론이 답이 되는가' — path conflict를 interconnection network의 path diversity 문제로 재해석한 것이 Venice의 진짜 기여이고, 그 재해석이 통한 이유는 병목의 위치(shared bus)를 정확히 짚었기 때문이다.
Method Backtracking 상세: DFS 스타일 예약 취소 + 물러나기
scout packet이 라우터를 하나씩 지나며 경로를 예약할 때, 매 라우터에서 '도착 port를 예약(hold)'하고 '다음 라우터로 넘어가려 시도'하는 과정을 반복한다. 특정 라우터에서 갈 수 있는 output port가 전부 막히면(minimal도 non-minimal misroute도 다 실패) 그 자리에서 계속 대기하지 않고:

1. 방금 그 라우터에서 만든 예약을 취소(cancel) — scout packet의 cancel 모드로 되돌아가는 방향에 예약 해제 메시지를 보냄
2. 한 단계 이전(upstream) 라우터로 물러남
3. 그 upstream 라우터에서 아직 안 시도해본 다른 output port로 재시도

미로 찾기(maze-solving)의 DFS backtracking과 구조가 같다 — 막다른 길이면 방금 걸어온 길의 예약을 지우고 한 걸음 물러나 다른 갈래를 시도한다. 한 라우터당 시도 가능한 output port는 최대 3개(2D mesh, 4포트 중 들어온 포트 제외)라서, 다 써봐도 안 되면 더 뒤로 backtrack한다. 최악의 경우 이를 반복하다 source controller까지 되돌아가고(사실상 NACK), controller가 새 scout로 재시도한다.
Gap / Idea Livelock-freedom은 측정이 아니라 유한성에서 나오는 논리적 보장
'적어도 하나는 결국 진전한다'(forward progress, livelock-freedom)는 latency를 재서 확인하는 통계적 사실이 아니라, 두 가지 유한성(finiteness)의 조합에서 논리적으로 유도되는 보장이다.

1. scout의 탐색 자체가 유한하게 끝난다: 재방문 횟수 제한(라우터당 최대 3번) + mesh 지름이 유한하니, 한 번의 scout 시도는 반드시 성공(예약 완료) 아니면 실패(source로 복귀)로 끝난다 — 무한히 헤매는 경우가 구조적으로 없다.
2. 한 번 점유된 link도 유한 시간 안에 반드시 풀린다: circuit switching으로 예약된 전송은 flash operation(수 $\mu s$)만큼만 link를 잡다가 끝나면 반드시 놓아준다 — 영원히 안 풀리는 점유가 없다.

이 둘을 합치면, 지금 당장 모든 scout가 실패하고 있어도 그건 일시적 backpressure일 뿐이다. 진행 중인 전송들이 유한 시간 안에 끝나며 link가 하나씩 풀리고, 그 순간 재시도하던 scout 중 하나는 반드시 그 빈 link를 잡는다. 논문의 '99.98% 첫 시도 성공' 같은 수치는 이 보장이 실제로도 잘 작동한다는 실증 데이터일 뿐이지, 보장 자체의 근거는 아니다 — 근거는 어디까지나 설계(bounded search + bounded holding time)에 있다.
Memo Hold-and-wait: lock 없는 하드웨어에도 적용되는 개념
Hold-and-wait는 deadlock의 4대 필요조건(Coffman conditions: mutual exclusion, hold-and-wait, no preemption, circular wait) 중 하나로, '자원을 이미 쥔 채로(hold) 다른 자원을 얻으려 대기(wait)하는' 상태를 말한다. scout가 라우터 A의 port를 예약해 쥔 채로 라우터 B의 port가 비기를 그 자리에서 기다린다면 이게 hold-and-wait다 — 여러 scout가 서로의 자원을 쥐고 서로를 기다리면 순환 대기(circular wait)가 생겨 deadlock이 된다.

Venice는 막히면 hold한 채 기다리는 대신 hold를 놓고(cancel) 물러난다(backtrack) — hold-and-wait 조건 자체가 애초에 성립하지 못하게 설계했다. Coffman 조건 4개 중 하나만 깨져도 deadlock은 원천적으로 불가능해지는데, Venice는 hold-and-wait를 깨는 쪽을 택한 것이다.

흥미로운 지점: hold-and-wait/deadlock 이론은 보통 OS의 software lock(mutex, semaphore) 맥락에서 배우지만, 여기엔 lock이라는 소프트웨어 동기화 기제가 전혀 없다 — 그냥 하드웨어 라우터의 reservation table 항목을 쥐고 있느냐 아니냐의 문제다. 즉 hold-and-wait는 'lock을 잡는다'는 특정 구현(mutex API)에 종속된 개념이 아니라, '자원을 배타적으로 점유한 채 다른 자원을 기다린다'는 더 일반적인 패턴 자체를 가리킨다 — lock이 있든 없든, 배타적 자원 점유가 존재하는 모든 시스템(회로 스위칭 네트워크, lock-free 분산 트랜잭션 등)에 똑같이 적용되는 순수 리소스-그래프 이론이라는 뜻이다.
